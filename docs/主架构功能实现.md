# 存储管理器框架的功能实现

## 连接与通讯

### 初始化与建立连接

MainUI.html 在加载布局模块和功能模块之前定义五组回调列表。模块通过注册
回调参与初始化、连接状态处理和消息处理：

| 回调列表 | 参数 | 调用时机 |
| --- | --- | --- |
| `onload_func_list` | 无 | 页面加载完成后、建立连接前 |
| `when_connect_func_list` | 无 | WebSocket 连接成功时 |
| `when_disconnect_func_list` | 无 | WebSocket 关闭时 |
| `message_proc_func_list` | `data` | 收到并解析 JSON 文本消息后 |
| `binary_message_proc_func_list` | `header, payload` | 收到并解析 HSV1 二进制消息后 |

`window.onload` 按注册顺序调用初始化回调，然后初始化服务器地址控件，恢复
上一次输入的地址并自动连接；没有记录时使用 `localhost:8768`。
根目录右侧的输入框接受 IP、主机名及端口（IPv6 使用方括号），省略端口时
使用 8768；也接受 HTTP/HTTPS、WS/WSS 地址，WebSocket 路径统一为 `/ws`。
HTTPS 页面只允许连接加密地址。客户端须填写服务端实际配置的端口。
`createAutoReconnectWebSocket(url, onMessage)` 创建原生 WebSocket，并将
`binaryType` 设为 `arraybuffer`。

每次 WebSocket 建立后进入版本验证状态，等待后端首条文本消息
`{"command":"BACKEND_VERSION","version":["TIPHERETH 1.0.0"]}`。
`version` 是后端支持的前端版本列表；与 ROLAND 相同，检查列表中是否存在
字符串，其去除首尾空白、按空白分隔后的第一段等于前端 `VERSION_NAME`。
因此按版本系列匹配，不要求完整版本号一致。验证成功才启用模块回调和业务
收发，版本消息由框架消费，不分发给模块。首条消息无效、不兼容或 5 秒内
没有收到版本信息时关闭连接并提示，停止自动重连。手动连接可再次尝试。
主动断开或切换地址会取消验证定时器，旧连接的版本消息不能启用新连接。
HTTP 服务信息只用于历史状态探测和资源查询，不参与连接版本校验。

连接成功时，框架先设置内部连接状态，再通过 `BasicEvent.when_connect()`
更新状态文字、启用根目录输入框，随后调用连接回调。各列表按数组顺序同步
调用回调，单个回调同步抛出的异常会被记录，不阻止后续回调执行；框架不等待
前端回调返回的 Promise。

### socket 接口与发送消息

全局变量 `socket` 保存连接管理器对象，初始为 `null`：

| 接口 | 行为 |
| --- | --- |
| `url` | 连接管理器的目标 WebSocket 地址，调用方应只读使用 |
| `send(data)` | 原生 WebSocket 处于 OPEN 时发送并返回 true，否则返回 false |
| `close()` | 关闭当前原生 WebSocket，并取消重连及连接超时定时器 |
| `reconnect()` | 立即尝试建立连接 |
| `isConnected()` | 返回内部连接状态 |
| `isActive()` | 当前管理器是否仍是页面使用的连接且未被主动停止 |

模块发送 JSON 命令时自行调用 `JSON.stringify()`，`send()` 不自动序列化，
也不缓存断线期间的消息。返回 true 表示已交给原生 WebSocket 发送，不表示
后端业务处理成功。

### 接收与分发消息

`messageProc(event)` 根据消息类型进行处理：

1. 文本消息通过 `JSON.parse()` 解析。如果 `command` 为 `SET_NOWPATH`，
   先用 `data.path` 更新根目录输入框，再把同一个 data 对象交给文本回调列表。
2. 二进制消息接受 ArrayBuffer 或 Blob；Blob 先转为 ArrayBuffer，再检查
   HSV1 魔数及 JSON 信息头长度。消息结构为：

   ```text
   4 字节魔数 0x48535631 | 4 字节无符号信息头长度（大端） | UTF-8 JSON 信息头 | 二进制载荷
   ```

   信息头解析为 header 对象，其余字节作为 payload（ArrayBuffer），依次
   传给二进制回调列表。

无法解析或结构错误的消息会被记录并丢弃。框架负责分发，模块自行检查
command、widgetId、streamId 等业务字段，判断消息是否属于自己。
同一连接的消息解析按到达顺序串行执行；关闭、重连或切换地址后，旧连接
事件及尚未完成的 Blob 解析结果不会再分发到模块。

### 地址历史与可用状态

合法输入、连接尝试和历史选择会写入浏览器 localStorage 的
`tiphereth.server-addresses.v1`，保存最近地址和最多 20 条去重历史。
刷新或重新打开页面恢复最近地址；记录属于当前浏览器，file:// 页面移动后
是否仍能访问原记录取决于浏览器。存储不可用时显示提示并退回内存记录。

输入框聚焦或点击箭头展开历史列表，每项最左侧显示状态圆点。列表打开时
通过各地址的 `/api/server-info` 检查协议版本及 `/ws` 路径；响应符合框架
协议时为绿色，请求失败或尚未确认时为红色，当前已建立的连接显示绿色。
每次最多并发探测 4 个地址，超时 2.5 秒，展开期间每 15 秒刷新；收起后
取消探测与刷新。圆点表示探测结果，不保证该地址的功能模块正常。
支持方向键选择、Enter 确认及 Escape 收起；选择历史只填入地址。

### 断线与自动重连

布局和模块初始化完成后，树状图与分类展示模块分别调用自己的未连接状态绘制函数，显示“⛔ 未连接后端，请检查服务是否启动”。这个初始提示不依赖断线回调，因此首次连接失败、失败后继续重试或手动停止连接时，提示仍保留。首次成功建立逻辑会话后，模块激活逻辑将提示替换为正常内容。网络传输断开但逻辑会话持续时，不重新绘制该提示，也不清空当前页面；逻辑会话主动结束时，模块通过原有断线回调恢复未连接提示。 布局模块记录逻辑会话是否已建立，只有会话持续时，从子页面返回首页才调用功能模块激活回调；尚未连接或会话已结束时，返回仅恢复页面可见性，保留未连接提示。

点击“连接”开始连接，按钮随即显示“断开”，连接中和等待重连时也可停止。
连接尝试超过 10 秒会关闭；意外断线后由 `schedule()` 固定等待 1 秒再尝试连接，
每次重试的等待时间相同，不随失败次数增加。`onerror` 只记录错误，由 `onclose` 统一
安排重连。曾建立成功的连接断开时调用一次 `BasicEvent.when_disconnect()`，
清空并禁用根目录输入框，执行断线回调。重连成功再次执行连接回调。

点击“断开”调用 `disconnect()`，取消定时器、关闭连接并清空全局 socket，
主动断开不重连。切换地址建立连接前会先停止旧管理器，旧事件不能改变新连接。
页面离开时也会停止连接和历史探测。框架不更改第三方模块的业务状态归属。

## 计划任务槽

所谓计划任务功能，是用来在服务器后台运行一些需要消耗一定时间的任务的功能，例如扫描目录建立数据库、自动下载弹幕评论数据等任务。一个任务可以由某个py脚本建立，也可以由功能模块调用接口将某个函数作为一个任务运行。一个任务可以立刻运行，也可以设置为定时任务定期执行。

普通任务之间可以采用串行策略，即一个任务结束后执行下一个任务，排队执行；有些任务有时效性，需要同时并发执行。为了管理不同任务的串行和并发策略，这里使用“队列”这个概念来管理任务的执行。“队列” 可以视作装载任务的有序容器，一个队列里的任务从前到后依次排队执行，队列之间并发同时执行。一个任务不能单独执行，必须将其放到现有或新建的队列里，然后使得该任务得到执行。队列里的任务在正常执行完毕后直接从队列里移除。定时任务的定时是指在所要求的时间将该任务加到某个队列里，即在该时间前队列里没有此任务。

框架默认只有一个主队列，用于执行多数任务。在创建任务时，默认将任务放到主队列里排队，也可以指定新建队列用于执行此任务以实现并发。这些新建的队列一旦其中不再有任务，就会被自动销毁。

### 界面设计

在 #upbar 里 IP 输入框和连接按钮的右侧设一内联 svg 按钮以作为计划任务功能的入口。点击次按钮出现一悬浮下拉框作为情况简报框，该下拉框固定600px高度，400px宽度。如果下拉框底部超出浏览器视口，那就把下拉框高度设为合适的值使得下拉框底部恰在浏览器视口内。如果下拉框宽度超过浏览器视口宽度的40%，那就把下拉框宽度设为视口宽度的40%。确保整个下拉框在视口内。

情况简报框顶部显示标题“任务情况简报”。下面前三行显示 “主队列有 x 个任务”、“当前有 y 个队列”、“正执行 z 个任务”这些字样，在这三行下面显示一个横向滚动框，框里从左到右依次水平排列表示主队列里任务的div块，即任务卡片。每个任务卡片的右上角是状态签，显示该任务目前的状态。状态签纯色底白色字，每种状态对应状态签一种背景颜色。一个任务可能具有的状态有执行中、暂停中、排队中、异常终止。如果任务结束且没有异常，那么该任务会直接从队列里移除；如果正在执行的任务被暂停或异常终止，那么队列会跳过该任务执行后面的任务，如果该任务后面不再有任务，那么队列会进入挂起状态，直到有新任务进来或暂停的任务恢复执行。然后任务的名称位于任务卡片中央。横向滚动框的滚动条要做适当的美化。

横向滚动框的下面是一用于展示主队列运行输出日志的div，要支持表示颜色的字符，例如 `033[31m` 表示红色，`033[32m` 表示绿色，`033[33m` 表示黄色等。然后日志最大行数为1000行，超出直接覆盖掉最早的输出。日志 div 由一个JS对象 `consoleDiv` 管理，详见[控制台控件](#控制台控件)。

日志div下面，情况简报框的右下角有一个“详细信息”按钮，点击调用 `new_page()` 打开计划任务管理页。“详细信息”按钮左边有一个“清空日志”按钮，点击后可以清除所有日志。

关于计划任务管理页，其上半部分是一个大滑动板块控件。第一行有字样“当前状态槽”，然后该字样右侧有“队列”下拉选择框，用于选择当前要查看的队列。默认选择主队列。下拉选择框里显示所有队列的名称，用户可以点击下拉选择框选择其他队列。这一行下面紧接着是装有任务卡片的横向滚动框，显示当前选中队列里的任务。每个任务卡片除了状态签、任务的名称外，在任务名称下面还要显示任务的创建时间，然后再下面一行要显示两个按钮，一个“暂停”按钮，点击暂停任务；一个“终止”按钮，点击弹出确认框，确认后终止任务。第一行的字样、下拉选择框和横向滚动框放在一个大的滑块div里，作为滑槽里第1页的内容。该滑块div在一个滑槽div里，滑槽div固定。滑槽div的左侧有“<”形、右侧有“>”形的svg按钮，点击分别使得滑块div右滑、左滑实现翻页(触屏移动端的话手指左右滑也可以实现该操作)。第一页“<”按钮失效变淡，第二页“>”按钮失效变淡。

滑槽里第2页的内容是所有的定时任务卡片。这些卡片也放在一个横向滚动框里。然后横向滚动框上方是字样“定时任务槽”。每个定时任务卡片在任务名称下面还要显示任务预定执行的时间，然后再下面一行要显示两个按钮，一个“更改”按钮，点击更改任务的时间设置；一个“删除”按钮，点击弹出确认框，确认后删除该定时任务。

滑动板块下面分成两列，左列较窄，右列较宽。右列是一个有边框的圆角容器框div，这个div里有当前选中队列的日志输出的div(类似控制台，`consoleDiv` 的另一实例)，同样要支持表示颜色的字符，最大行数为1000行。圆角容器框div里日志输出div的上方一行的最左侧是一个“清空日志” 按钮，点击清空日志输出div。然后左列添加一个大蓝底白字按钮，按钮左侧是大“+”符号，符号右侧是字样“新建任务”。点击新建任务按钮，会切换到新建任务页面。当前新建任务页面暂不开放，是一个带有布局模块返回菜单栏的空白页。

管理页按视口高度分配上方滑动板块与下方日志区域，页面本身不产生滚动条，任务卡片和控制台输出在各自区域内滚动。页面顶部只保留常规内边距，标题与右上角返回菜单位于同一高度范围。滑动板块采用无边框的半透明白色背景，左右翻页按钮使用较大的 SVG 箭头；“当前状态槽”和“定时任务槽”标题使用稍大的字号。任务卡片滚动框带可见边框和圆角，没有任务时提示文字在框内居中。

左侧“新建任务”按钮占满该列可用宽度，采用蓝色渐变背景和白色文字，文字为 28px，左侧加号采用约 48px 的 SVG，避免字体行高撑大按钮。鼠标悬停时按钮缩放至 1.025 倍，进入和移出均使用 280ms 的三次贝塞尔缓动 `cubic-bezier(.22, 1, .36, 1)`，先较快变化，再平滑减速至目标大小；开启系统减少动态效果设置时关闭放大动画。右侧日志容器的“清空日志”按钮位于容器内顶行左侧，控制台占据其余空间。窄屏下两列改为上下排列，按钮和日志仍保持在当前视口内。

### 控制台控件

控制台控件用于在一个 DIV 中展示文本输出并收集用户输入，由 JS 对象 `consoleDiv` 管理，输出、输入提示及错误提示共享同一个滚动区域；可编辑输入行紧接日志最后一行，在 `>` 后接受单行文字，没有底部独立输入栏或发送按钮。本节描述当前控件的接口、选项、默认值和运行行为。

`consoleDiv` 是通用控件，不保存任务或队列标识，不处理 WebSocket 消息，也不调用通知接口。调用方通过方法写入文本，通过构造选项传入输入回调，用户提交文字时由控件调用该回调。网络收发、业务对象选择和提醒均由使用控件的功能模块完成。

#### 构造选项

构造形式为 `new consoleDiv(container, options = {})`，其中 `container` 是挂载控件的 DOM 元素，`options` 包含以下全部选项，未传入的键使用表中默认值。非法类型或超出范围抛出 `TypeError` 或 `RangeError`，不能悄悄转成其他配置。

| 选项 | 类型及默认值 | 含义与生效范围 |
| --- | --- | --- |
| `maxLines` | 正整数，默认 `1000` | 本实例最多保留的逻辑行数，自动折行不另计行数 |
| `maxLineBytes` | 正整数，默认 `16384` | 每行最多保留的 UTF-8 正文字节数，超出截断并显示标记 |
| `ansi` | 布尔值，默认 `true` | 是否解释 SGR 颜色；关闭时剔除 ANSI 控制序列，仅显示普通文字 |
| `autoScroll` | 布尔值，默认 `true` | 用户位于底部时，新输出自动滚到底部；用户向上查看时暂停自动跟随 |
| `inputEnabled` | 布尔值，默认 `false` | 是否允许编辑和提交输入；没有 `onInput` 时，即使设为 true 也不能提交 |
| `prompt` | 字符串，默认 `""` | 输入区标签，纯文本显示，同时作为输入框的无障碍标签 |
| `placeholder` | 字符串，默认 `"请输入内容"` | 输入框为空时的提示文字，不代替输入区标签 |
| `maxInputBytes` | 正整数，默认 `16384` | 一次提交允许的 UTF-8 字节数，调用方仍进行业务校验 |
| `onInput` | 函数或 null，默认 `null` | 用户提交时调用 `onInput(text)`，可返回普通值或 Promise；抛出异常或 Promise 拒绝表示失败 |

例如，一个与服务器和任务都无关的本地回显控件可以这样建立：

```javascript
const consoleView = new consoleDiv(container, {
    maxLines: 500,
    inputEnabled: true,
    prompt: '请输入文字：',
    onInput: async (text) => {
        consoleView.write(`收到：${text}\n`);
    },
});
consoleView.write('控制台已准备好。\n');
```

其中 `onInput` 只接收输入字符串，不附加任何业务标识。返回值本身不作为输出显示，调用方需要回显时主动调用 `write()`；控件也不自动记录用户答案，避免调用方回显后重复出现。可调整的输入启用状态和提示文字通过下列方法更新，其余构造选项在本实例存续期间保持不变。

#### 文本与输入操作

文本行使用通用结构 `{id, text}` 表示，其中 `id` 为调用方提供或控件自动生成的本实例唯一字符串，`text` 为正文，不包含业务字段。一条记录可以表示尚未完成的输出行，后续用同一标识替换完整正文。控件只负责行标识查找，不识别日志游标、操作命令或服务器修订号。

| 接口 | 参数、返回和用途 |
| --- | --- |
| `new consoleDiv(container, options = {})` | 创建并返回控件实例，选项见上表 |
| `console.write(text)` | 将字符串按字符流写入，连续调用拼接当前未完成行，遇换行结束该行，返回 `undefined` |
| `console.setLines(lines)` | 使用 `{id, text}` 数组替换全部输出行，重建颜色解析状态并应用行数上限，返回 `undefined` |
| `console.appendLine(text, id)` | 追加一行完整正文，未传 id 时自动生成，返回实际行标识；重复 id 报错 |
| `console.replaceLine(id, text)` | 用完整正文替换现有行，返回是否找到并替换；缺失时不自动新增 |
| `console.setInputEnabled(enabled)` | 更新输入可用状态，禁用时保留草稿，返回 `undefined` |
| `console.setPrompt(text)` | 更新纯文本输入标签及无障碍标签，返回 `undefined` |
| `console.getInputValue()` / `console.setInputValue(text)` | 读取草稿字符串，或设置草稿并返回 `undefined`，不触发输入回调 |
| `console.focusInput()` | 尝试聚焦可编辑输入框，返回是否成功 |
| `console.clearView()` | 清除本地输出及未完成的 ANSI 解析状态，保留提示、草稿和输入启用状态，返回 `undefined` |
| `console.destroy()` | 移除本实例 DOM 和监听，丢弃本地数据，返回 `undefined`；不取消调用方的异步工作 |

`write()` 适合直接接收文本流，行方法适合显示调用方维护的文本记录，调用方选择一种方式组织一次输出。行方法的 `text` 不包含 CR/LF，换行记录由调用方拆分；调用行方法时如仍有 `write()` 的未完成行，先结束该行。自动生成的标识与调用方标识使用独立内部空间，避免碰撞。替换和快照方法从行首重新解析完整正文，不能把替换内容当作追加片段重复解析；各行颜色状态独立，需要跨行保留颜色时由调用方为下一行补上起始 SGR 状态。

输出区使用等宽字体，保留空格和换行，只解释允许的 ANSI SGR 颜色，例如 `\x1b[31m` 表示红色。`write()` 的 ANSI 序列可能跨片段，最多暂存 64 个字符，超过后丢弃未完成控制序列；普通文本通过文本节点显示，不能拼接为 HTML。第一版不模拟完整终端，单独的 `\r` 规范成换行，`\r\n` 作为一个换行处理，即使跨片段也不能产生两行；光标移动、退格和终端清屏序列不执行。

最大行数按逻辑行计算，当前未完成行也占一行。超限删除最早行，单行超过字节上限时截断并标记，此后丢弃该行剩余字符直到换行，不能无限缓存。用户向上查看时保留滚动位置，并显示“有新输出”按钮；点击该按钮滚到底部。`autoScroll=false` 时新输出始终不改变用户滚动位置。

#### 输入回调与控件生命周期

用户在日志末尾的 `>` 后输入文字并按 Enter 时，控件读取当前文本并调用 `onInput(text)`，中文输入法处于组合状态时 Enter 不提交。输入按一行处理，允许空字符串，拒绝 CR、LF、NUL 和超过 `maxInputBytes` 的内容；多行粘贴提示用户改成单行，不拆成多次提交。输入区显示校验失败原因，不能在校验失败时调用回调。

调用回调后，控件进入发送中状态，暂时锁定编辑和发送以防止重复点击，保留草稿。回调正常返回或 Promise 完成后清空本次草稿；异常则保留草稿，并用纯文本显示异常 message 或通用失败提示。回调开始后调用方仍可以通过 `setInputEnabled(false)` 禁用输入，回调完成不能覆盖这个新设置；最终能否编辑由调用方启用状态、回调是否存在及是否仍在发送共同决定。

输入行使用无边框、透明背景的原生单行编辑元素承接键盘、光标和输入法事件，视觉上与日志文字连续。追加日志时只更新日志行容器，输入行保持同一个 DOM 节点，不重新创建编辑元素，因此草稿、选区和输入法组合状态不被打断。新的输出始终放在当前编辑行之前；清空日志保留输入行和草稿，行数上限只统计输出记录。

发送期间如果调用方主动设置了新草稿，旧回调完成后不能清空新草稿。销毁后的异步回调可以继续由调用方处理，但其完成或失败不能再次修改 DOM 或重建控件。控件不保存输入历史到 localStorage，也不把清空输出解释为取消输入。业务请求已结束、连接中断等情况由调用方转换成启用状态和提示文字的变化。

#### 任务管理器与任务数据

任务管理器 `TaskManager` 用于保存当前队列、队列里的任务、尚未触发的定时计划和各队列的日志。`back.py` 在模块初始化之前建立唯一的管理器，功能模块通过 `from backend.backapi import get_task_manager` 取得该对象。启动入口统一包导入路径，避免同一文件被重复导入而产生不同的管理器。单纯导入 `backapi.py` 不启动调度，管理器尚未初始化时调用 `get_task_manager()` 抛出 `RuntimeError`。

关于任务和定时计划，需要区分“已经入队的一次执行”和“准备在未来建立任务的设置”。前者称为任务实例，由 `task_id` 标识；后者由 `schedule_id` 标识，保存触发时间、目标队列设置和按顺序排列的任务定义。任务定义记录任务名称、函数及参数，或本地 Python 脚本及其启动设置，每一项由 `entry_id` 标识。每次计划触发，都根据这些定义产生新的任务实例，因此同一项定义可以在不同轮次对应不同的 `task_id`。

队列使用 `queue_id` 标识，其中主队列固定为 `main`，显示名称为“主队列”。其他队列只在创建任务并将任务放入其中时一起创建，不能单独创建空队列。临时队列的最后一个任务被移除后，立即销毁队列及其日志；暂停和失败的任务仍保留在队列中，因此包含这些任务的队列不销毁。只有主队列可以一直为空。

这些数据第一版只保存在内存中，后端重启后不恢复任务、计划和日志。任务管理器不依赖某个客户端连接，前端断线不影响任务执行。业务结果由功能模块自行保存，任务函数的返回值不作为任务历史保留。

#### 创建任务并放入队列

`TaskManager.create_task()` 作为统一的创建入口，用于立即建立函数或本地脚本任务、登记定时任务，以及向一个定时计划追加后续任务定义。`func` 与 `script` 必须二选一，脚本任务不使用函数调用参数 `args`、`kwargs`。调用形式为：

```python
await tasks.create_task(
    name, func=None, *, script=None, args=(), kwargs=None,
    queue_id="main", new_queue_name=None,
    timing=None, after_schedule_id=None,
)
```

其中任务名称（`name` 参数）用于卡片显示，函数任务的任务函数（`func` 参数）是可调用对象，调用形式为 `func(ctx, *args, **kwargs)`。任务管理器注入任务上下文 `ctx`，供函数检查暂停、终止请求和记录日志。`args`、`kwargs` 在登记时复制外层容器，内部对象不深复制，调用方避免在提交后修改共享数据。

不传 `timing` 和 `after_schedule_id` 时，`create_task()` 立即建立一个任务实例，将它放到 `queue_id` 对应队列的末尾，默认放到主队列。如果需要新建队列，则传入 `queue_id=None` 和非空的 `new_queue_name`。此时建立队列和放入首个任务作为一次操作完成，不能先对外公布空队列。任务入队后才参与调度，创建方法不等待任务执行完成。

关于队列参数，`queue_id` 指向已有队列，`new_queue_name` 表示随任务新建队列，两者不能同时指定。已有队列在调用时不存在返回 `QueueNotFound`，不能自动创建同名队列，也不能改放到主队列。如果任务创建失败，新队列也不留下。要向这个新队列继续添加普通任务，可以从第一次调用的返回值读取实际的 `queue_id`，再调用 `create_task()`；如果该队列已经执行完并销毁，则后一次调用明确失败。

所有创建方式返回 `TaskCreation`，其内容用于区分任务是已经入队还是仍在等待触发。返回到前端时可表示为以下结构：

```json
{
    "task_id": null,
    "queue_id": null,
    "schedule_id": "schedule-1",
    "entry_id": "entry-1"
}
```

其中已经入队的任务返回实际的 `task_id` 和 `queue_id`，`schedule_id`、`entry_id` 为 null。示例表示登记了一个定时计划里的任务定义：此时尚未建立实例或选择实际队列，因此前两个字段为 null，后两个字段分别用于定位计划及其中的一项任务定义。即使计划将来要加入主队列，登记返回值中的 `queue_id` 也为 null，目标队列从计划设置读取，避免把未来的目标误认为已经入队的位置。

同一队列按任务排列顺序选择可以执行的实例，同时最多有一个任务占用执行位置。不同队列之间可以并发。暂停和失败的任务保留原位置，但不占用执行位置，调度器跳过这些任务继续选择后面的任务。正常完成和确认取消的任务从队列移除，恢复的任务在原位置重新参与选择，不抢占已经运行的任务。

协程任务在框架事件循环中执行，同步函数任务在线程数有上限的线程池中执行。因此协程不能直接进行阻塞 I/O 或长时间 CPU 运算，队列之间的实际并发也受线程池等执行资源限制。模块自行建立子进程时，负责子进程退出和资源清理。这里的脚本调用只指同一后端进程导入 API 后调用函数，独立运行的脚本不共享这个管理器。

#### 创建本地 Python 脚本任务

脚本任务保存本地脚本路径、命令行参数和工作目录，等到取得队列执行位置后才创建子进程。`create_task()` 的 `script` 参数为以下结构，路径及参数由后端模块指定，前端控制台不能提交路径启动脚本：

```python
result = await tasks.create_task(
    "执行目录扫描脚本",
    script={
        "path": r"D:\tools\scan.py",
        "argv": ["--mode", "full"],
        "cwd": r"D:\tools",
    },
    queue_id=None,
    new_queue_name="脚本扫描",
)
```

其中 `path` 指向已有的 `.py` 普通文件，命令行参数（`argv` 键）为字符串列表，工作目录（`cwd` 键）为已有目录，未传时默认脚本所在目录。相对路径相对于后端启动时确定的 backend 目录解析，并在登记时固定为绝对路径，不能随其他任务改变工作目录。登记时校验结构及路径，实际执行前再次检查，文件已删除或无法访问使本次实例失败。脚本内容不复制到计划中，同一路径的文件被修改后，未来执行使用修改后的文件。

子进程默认使用后端当前的 `sys.executable`，通过参数列表启动 `backapi.py --run-script` 子进程入口，设置无缓冲输出和 UTF-8 编码，不使用 shell 拼接命令。启动器在子进程中设置工作目录、`sys.argv` 和脚本导入目录，再通过 `runpy.run_path(path, run_name="__main__")` 执行脚本；这个入口模拟独立脚本执行，但不改变后端主进程的工作目录或导入路径。脚本的第三方依赖安装在当前解释器环境中，第一版不提供自选解释器或完整终端仿真。

脚本任务的控制进程在后端事件循环中异步管理，不占用函数任务的工作线程等待子进程退出。stdout/stderr 读取和输入请求控制通道分别持续处理，不能因为脚本正在等待回答就停止读取输出。启动或控制通道认证超过的 5 秒仍未完成时，终止本次子进程并记录失败。启动和控制通道认证失败、非零退出码使实例进入 failed；正常退出码 0 视为成功，用户终止导致的退出视为 cancelled，不能再报为业务异常。完整输出及退出摘要记入所属队列日志。

脚本定义与函数定义一样支持 `timing` 和 `after_schedule_id`：登记时只保存 `script` 设置，触发时才启动本轮实例，追加的函数和脚本可以混合排列。单个脚本进程中的所有线程共享同一个任务身份，但同一时刻只能有一次待输入请求。

第一版脚本实例开始运行后声明 `can_pause=false`，暂停按钮禁用，强制请求暂停返回 `InvalidTaskState`；尚未启动的排队脚本仍可暂停和恢复。`input()` 阻塞某个线程并不能证明整个脚本停止工作，所以等待输入不能作为安全暂停整个进程的依据，也不能在此时放开本队列的执行位置。原有函数任务的协作检查点规则继续适用。

终止脚本时，先撤销未回答的输入请求，关闭其输入通道并请求进程退出；等待 5 秒后仍未退出则强制结束受管理的进程树，随后回收进程、输出读取任务及控制 socket。Windows 使用 Job Object 管理进程树，并在脚本开始执行前完成绑定，不能只结束父进程而遗留其派生进程。管理器在确认受管进程退出后才移除任务并释放队列；强制退出可能不执行脚本 `finally`，不能承诺脚本自行完成业务回滚。服务停止时也走同一清理过程，不能遗留等待输入的脚本。

#### 脚本任务里调用的 input 函数

脚本的 `input()` 将提示交给父进程，由父进程登记输入请求并通知前端；用户在通用控制台提交文本后，计划任务模块把答案传回对应脚本调用。控件自身只调用 `onInput(text)`，不负责识别请求或唤醒脚本。

为了识别脚本确实在调用 `input()`，子进程通过框架启动器执行脚本。启动器在子进程内安装 `builtins.input` 适配函数，执行 `input(prompt)` 时先刷新已有 stdout/stderr，再通过专用控制通道发送输入请求并阻塞当前调用线程。提示文字随控制消息传递，由父进程写入队列日志并登记 `prompt`；适配函数不能再把相同提示输出一次。父进程收到前端回答后通过控制通道送回对应请求，适配函数返回不带换行的字符串，从而保持普通 `input()` 的返回习惯。EOF 或通道关闭抛出 `EOFError`，不能解释为空回答。

专用控制通道与 stdout/stderr 分开，避免把脚本输出中恰好类似 JSON 的文字误当成输入请求。使用仅监听本机回环地址的临时 socket，由父进程通过启动环境传递端口和一次性令牌，子进程认证后再交换带长度前缀的 UTF-8 JSON 帧；单帧最多 64 KiB，提示文字与回答分别最多 16 KiB UTF-8，重叠请求被拒绝。WebSocket 中的任务标识由父进程绑定，不能由脚本任意指定为其他任务。父进程通过异步 socket 等待消息，脚本的 `input()` 在线程内阻塞即可，不阻塞后端事件循环。

第一版明确支持普通 `builtins.input()`。直接读取 `sys.stdin`、`getpass()`、原生库终端输入以及脚本自己启动的子进程，不保证经过这个适配；启动器将普通 stdin 设为 EOF，避免不受管理的读取永久卡住。需要交互的脚本使用 `input()`，不尝试通过输出一个冒号来让框架猜测是否等待输入。脚本可以正常调用多次 `input()`，每一次都产生新的输入标识。例如，上述 `scan.py` 可以保留普通脚本写法：

```python
print("准备扫描目录", flush=True)
root = input("请输入扫描目录：")
print(f"即将扫描：{root}", flush=True)
```

其中第一行和最后一行进入任务所属队列的日志，中间一次调用创建输入请求；用户提交后，答案作为 `root` 的值交给脚本，脚本才能继续执行最后一行。

##### 输入请求与提醒

输入请求用于说明“哪个任务正等待哪一次回答”，由后端任务管理器保存，不能只存在于日志文字或通知里。一个待输入请求的前端结构如下：

```json
{
    "input_id": "input-7",
    "queue_id": "queue-2",
    "task_id": "task-9",
    "task_name": "扫描脚本",
    "prompt": "请输入扫描目录：",
    "created_at": "2026-11-18T02:01:00+08:00",
    "state": "pending"
}
```

其中输入标识（`input_id` 键）在一次服务运行中唯一，不能用任务标识替代，因为同一任务可以连续调用多次输入。队列、任务标识及名称用于定位控制台和显示来源，提示文字（`prompt` 键）用于输入区标签，创建时间用于显示等待时长，状态表示这次请求是否还可以回答。控制台输入框通过无障碍标签关联提示文字；没有待输入请求时隐藏 `>` 编辑行，显示“当前没有任务等待输入”，不能把用户提前键入的内容缓存为下一次回答。

任务管理前端模块收到新的 `TASK_INPUT_REQUEST` 后，先保存请求并更新对应控件，再调用现有的 `window.frame_show_notice('任务“扫描脚本”等待输入，请在对应队列控制台中回答。', 0, '#FFE69A', true, '#5C4300')`。该接口来自 `frontend/frame.js`，返回的句柄支持 `close()`，详见[经典布局模块的通用提示框接口](default_frame/功能实现描述.md#通用提示框接口)。前端按 `input_id` 保存通知句柄，同一页面的简报框和管理页不能分别弹出重复通知。通知文字只使用纯文本，不假定通知接口支持链接或点击跳转。

即使情况简报框没有展开，前端也提醒其他队列中的输入请求，并在任务入口显示等待输入数量；用户进入管理页后，能在队列下拉项看到等待标记，选择对应队列后输入。通知被手动关闭只隐藏提醒，不取消请求；收到完成、取消或任务结束事件时，关闭该请求的通知。重新连接时从快照恢复仍待回答的请求，同一页面已经提醒过的请求不重复弹出，新打开页面则提醒一次。

每个任务同一时刻只允许一个待输入请求；同一任务的多个线程同时请求输入时，后来的调用明确失败，不能互相抢占答案。同一队列通常只有正在执行的任务请求输入，但已暂停的函数也可能仍保留原请求，因此计划任务前端模块在控件外显示该队列的待输入请求列表，让用户明确选择任务，再通过 `setPrompt()` 和 `setInputEnabled()` 更新通用控件。暂停中的请求显示“恢复任务后可回答”并禁用提交，不能把它的回答发给当前运行任务。

##### 提交输入与多客户端处理

用户提交文字时，控件调用调用方传入的 `onInput(text)`。计划任务前端模块在回调开始时，读取并固定当前选中的 `queue_id`、`task_id`、`input_id`，再将这些标识和文本组装成请求；不能在异步发送结束时重新读取当前选择，否则切换队列后可能把回答关联到其他任务。该模块在初始化控件时设置 `inputEnabled=false`、`maxInputBytes=16384`，选定一个可以回答的请求后才启用输入。输入形式和控件内的发送状态处理见[输入回调与控件生命周期](#输入回调与控件生命周期)。

前端模块发送以下命令，其中连接内请求标识（`request_id`）用于匹配响应，输入请求标识（`input_id`）用于确定实际回答对象：

```json
{
    "command": "TASK_INPUT_SUBMIT",
    "request_id": "client-request-12",
    "queue_id": "queue-2",
    "task_id": "task-9",
    "input_id": "input-7",
    "text": "D:\\Videos"
}
```

后端核对任务仍属于该队列、输入请求仍待回答、任务未暂停且未请求终止，再原子地接受一份回答并唤醒调用方。前端与后端均校验单行文本、不含 NUL、UTF-8 编码后不超过 16 KiB，后端校验不能依赖控件配置。响应沿用 `TASK_RESULT`，成功数据包含 `input_id` 和 `accepted: true`。这里的成功只表示后端已接受回答，不表示脚本后续工作已经成功；脚本可能在收到回答之前退出，此时结束任务并记录输入交付失败，不能把同一回答转交给其他请求。

全部已连接客户端可以看到同一请求，先提交成功的回答生效，其他提交返回 `InputAlreadyResolved`。若请求已失效或标识不匹配，返回 `InputNotFound` 或 `InputTargetMismatch`；任务暂时不能接受输入时返回 `InvalidTaskState`。前端据此刷新状态，而不是自动把草稿提交给下一次输入。后端在请求解决后广播 `TASK_INPUT_RESOLVED`，携带三个对象标识及结果状态 accepted、cancelled 或 failed，所有控件收到后停止编辑该请求并关闭通知。通知和响应可能交错到达，发送端以二者共同确认的状态结束等待，不能因为解决事件先到达就误报失败。

连接中断时，控件保留本地草稿但禁止发送，后端请求继续等待。重连后查询实际待输入请求：原请求仍在才允许用户手动重发，否则提示该请求已结束。前端不能自动重放答案，因为断线前后端可能已经接收成功。已解决的输入标识在本次服务运行中保留一个有界的短期结果记录，方便识别迟到提交；记录淘汰后返回 `InputNotFound`，仍然不能重复唤醒调用方。

##### 普通任务等待控制台输入

函数任务通过 `await ctx.input(prompt="", timeout=None)` 请求输入，同步线程中的函数则通过 `ctx.input_sync(prompt="", timeout=None)`。这两个方法登记同一种待输入请求，先广播通知，再等待用户回答；正常返回值是用户提交的字符串，不带末尾换行。异步版本等待事件循环中的 Future，同步版本通过线程安全桥接等待这个 Future，不能在事件循环线程中调用同步版本。

因此不需要为每次输入再加一个“阻塞接收输入”的线程：同步任务原有的工作线程可以等待 Future，WebSocket 消费者继续接收提交并唤醒它；协程任务则只挂起自身。任务标识和输入标识决定回答归属，队列只是显示和串行调度的归属，不能把答案放进一个不区分任务的队列公共输入缓存。

等待输入期间，任务保持 `running`，设置 `waiting_for_input=true`，继续占用所属队列的执行位置，卡片可以显示“执行中·等待输入”，队列后面的任务不自动越过。超时默认不设置，传入正的有限秒数时从请求登记起按单调时钟计时；到期移除待输入状态并抛出 `InputTimeoutError`，由任务自行处理，未处理则转为失败。取消任务立即使等待失败，抛出任务专用取消异常，而不是返回空字符串。

普通函数任务在输入等待中收到暂停请求时，由输入等待逻辑完成暂停确认，释放执行位置并保留请求；恢复并重新取得执行位置后才能接收回答。暂停期间超时仍继续计时，超时可以关闭请求，但等到函数重新获得执行位置后再向它抛出超时异常；任务取消的退出清理仍按既有规则执行。控制台展示提示和等待状态，不能自行模拟暂停已经完成。

计划任务模块负责将断线映射为 `setInputEnabled(false)`，将队列日志快照映射为 `setLines()`，将日志 append/replace 事件映射为 `appendLine()`、`replaceLine()`。队列切换时，模块先保存旧请求的草稿，再销毁旧控件并创建新实例，避免旧回调完成后改动新队列的输入框。请求去重、修订号检查、等待标记、通知句柄和草稿所属请求都保存在模块中，不能交给控件识别。回调收到明确成功响应后返回；失败抛出带展示信息的异常，响应不明时重新查询请求状态，不自动重发。

#### 脚本的输出

脚本输出通过重定向子进程的标准输出和标准错误获取：创建子进程时设置 `stdout=asyncio.subprocess.PIPE`、`stderr=asyncio.subprocess.STDOUT`，使子进程的输出句柄连接到父进程读取的管道，而不是本地可见终端。这样既能取得普通 `print()` 的文字，也能取得写入标准错误的异常堆栈，以及仍向这些句柄写入的第三方库输出，不需要逐个替换 `print()`。脚本自行改写输出目标或直接向独立终端、文件输出时，不在此重定向范围内。

子进程以 `-u` 及 UTF-8 编码环境启动。父进程持续分块读取合并管道，并通过增量解码器处理跨块的 UTF-8 字符；非法字节以替代字符显示，不能使整个读取任务退出。合并管道不保留 stdout/stderr 来源标签，也不能保证多个线程缓冲输出的业务先后顺序。这样 `print(..., end="", flush=True)` 和不带换行的进度文字也能及时显示，不能使用逐行读取等待换行才展示。输入提示通过控制通道发送，因此不能承诺它与输出管道里最后几字的严格跨通道顺序；输入区仍完整显示提示，前端不能靠日志顺序绑定输入对象。

后端主进程不使用全局 `redirect_stdout` 或替换全局 `sys.stdout` 捕获这些脚本，因为主进程同时服务多个模块；重定向范围限定为本次脚本子进程。函数任务仍通过 `ctx.log()` 写出日志。

关于不带换行的输出，后端为每个任务保留当前未完成行，首次输出时建立稳定的 `row_id`，后续片段更新该行，遇到换行才结束。日志推送携带 `op`（append 或 replace）、`row_id` 和单调递增的变更序号 `seq`，计划任务前端模块先核对序号，再把 append/replace 转换为通用控件的 `appendLine(text, row_id)`、`replaceLine(row_id, text)`，不能把协议对象直接交给控件。每次 replace 携带完整行正文，不能每个片段新占一行。后端保存每行的起始 SGR 颜色状态，向控件传递正文时补在行首，使快照及替换从该行单独解析也能得到相同颜色，不要求控件依赖已经被覆盖的前一行。日志快照包含未完成行及对应序号；单行达到 16 KiB 时截断并标记，到换行后恢复记录，避免无换行输出无限占用内存。输出的任务退出时结束剩余行，并继续读取管道到 EOF 或清理期限后再完成任务收尾。

#### 登记定时任务与触发入队

定时任务通过向 `create_task()` 传入 `timing` 建立。此时管理器保存触发时间、队列设置和首项任务定义，返回相应的 `schedule_id`、`entry_id`，不建立任务实例，也不创建临时队列。例如，每小时在新队列里扫描一次目录，可以这样登记：

```python
plan = await tasks.create_task(
    "扫描目录", scan_directory, args=(root,),
    queue_id=None,
    new_queue_name="目录扫描",
    timing={
        "type": "interval",
        "start_at": "2026-11-18T02:00:00+08:00",
        "seconds": 3600,
    },
)
```

其中 `interval` 表示按固定间隔触发，第一次触发时间为 `start_at`，以后沿 `start_at + n * seconds` 计算，不以上次执行完成的时间作为起点。第一版还支持单次定时，例如 `{"type": "once", "run_at": "2026-11-18T02:00:00+08:00"}`。时间字符串必须带时区，后端转成 UTC 比较；间隔秒数为至少 1 秒的有限数值，不接受布尔值。新登记或更改的单次时间、周期起点晚于服务端当前时间，过去时间返回参数错误。第一版暂不加入 cron 和本地日历规则。

到了触发时间，调度器先读取该计划当时保存的任务定义列表，确认目标队列仍然有效，然后为每一项建立任务实例。内部复用 `create_task()` 的即时创建处理：不传入 `timing` 和 `after_schedule_id`，首项按计划保存的队列参数创建，后续项全部传入首项实际取得的 `queue_id`。调度器为这些实例补上来源 `schedule_id`、`entry_id` 和本轮 `run_id`，这些来源标识不作为模块可自行填写的参数。

这整批创建在同一次状态提交中完成，全部成功后才允许任务开始执行。若其中一项失败，回滚本轮建立的全部实例及新队列；创建通知也在整批提交后再发送。这样首项即使很快结束，也不会在后续项入队之前使临时队列被销毁。这里复用的是 `create_task()` 内部的创建逻辑，不能由定时器逐次调用对外方法并在中间放开调度。

如果计划指定 `new_queue_name`，则每一轮实际触发都建立一个新的队列，队列里的任务全部移除后照常销毁。如果计划指定 `queue_id`，则在触发时把本轮任务作为连续的一组追加到已有队列末尾，原先的任务仍排在它们前面。计划本身不延长临时队列的寿命，目标队列提前销毁时把计划标为 `blocked` 并记录原因，不静默更换目标。

周期计划以整轮任务为单位判断是否重叠。上一轮中只要还有一个任务实例保留在任一队列中，包括排队、执行、暂停或失败状态，就跳过本次触发，并记录跳过次数和原因。只有上一轮全部实例都被移除后，后续时刻才可以产生新一轮。事件循环延迟导致错过多个触发时刻时，只尝试合并触发一轮，其余时刻跳过，下一次仍按原节拍计算。

单次计划整批入队成功后从定时任务槽移除，周期计划则保留并更新下次触发时间。入队失败的计划保留为 `blocked`，不自动重试；用户更改时间时重新校验目标，校验成功后才重新启用。如果原目标队列已销毁，则需要删除该计划并重新登记。

#### 向定时计划追加后续任务

为了让一个任务排在某个定时任务未来将创建或将加入的队列后面，`create_task()` 接受 `after_schedule_id`。这个参数指向的是尚未结束的定时计划，表示将本次函数调用保存到该计划的任务定义列表末尾。例如，在前面的扫描计划之后追加更新索引：

```python
following = await tasks.create_task(
    "更新索引", rebuild_index, args=(root,),
    queue_id=None,
    after_schedule_id=plan.schedule_id,
)
```

其中 `after_schedule_id` 与 `timing`、`new_queue_name` 互斥，并且要求 `queue_id=None`，因为追加项的触发时间和目标队列都由所属计划决定。调用后返回所属 `schedule_id` 和新生成的 `entry_id`，`task_id`、`queue_id` 仍为 null。计划不存在或已经作为单次计划成功触发并移除时，返回 `ScheduleNotFound`，不能把任务转为立即执行。

追加项从下一次尚未提交的触发开始生效。对于单次计划，它只随该计划执行一轮；对于周期计划，它保存在定义列表中，以后每一轮都跟随创建。连续追加多项时按成功提交的顺序排列，追加到同一计划的最后一项后面。多个模块同时追加时，也由管理器串行提交，以确定最终顺序。

假设计划中原有“扫描目录”，之后追加“更新索引”和“下载弹幕”，则触发时一次建立这三个实例，顺序为扫描、更新索引、下载弹幕。如果目标是主队列且已有两个任务，本轮三个实例追加在这两个任务后面；如果目标是新队列，则三个实例都进入本轮新建的同一队列。登记追加项时队列尚不存在也没有关系，因为保存的是将来入队的定义，而不是向空队列预先放入任务。

这里的“后面”只约定同一队列中的排列顺序，不表示前项成功后才执行。前项暂停或失败时，队列仍按既有规则跳过它执行后项；需要依赖前项业务结果的模块在后项函数里检查结果。追加定义也不改变已经触发入队的任何一轮；要往当前这一轮继续添加任务，使用该轮实际的 `queue_id` 调用即时创建方式，并接受队列可能已销毁的情况。

追加与触发在同一事件循环中串行提交。如果追加先提交，本轮包含新项；如果触发先提交，本轮使用旧列表，新项从下一轮生效。单次计划触发先提交时，随后追加因计划已移除而失败。这样不需要用“下次队列”这样的临时队列 ID，也不会把任务意外追加到上一轮的队列。

#### 查询和更改任务设置

任务实例快照 `TaskInfo` 用于生成当前状态槽的卡片，保存任务标识（`task_id`）、名称（`name`）、所在队列（`queue_id`）、来源计划及定义（`schedule_id`、`entry_id`）、所属轮次（`run_id`）、状态（`state`）、创建时间（`created_at`）、首次开始时间（`started_at`）、暂停时间（`paused_at`）、错误摘要（`error`），以及暂停和终止请求标记（`pause_requested`、`cancel_requested`）、任务类型（`kind`，function 或 python_script）、当前能否暂停（`can_pause`）、是否等待输入（`waiting_for_input`）和当前输入标识（`input_id`）。普通即时任务的来源字段为 null，尚未发生的时间为 null，其他时间使用带 UTC 偏移的 ISO 8601 字符串。

任务状态包括排队中（`queued`）、执行中（`running`）、暂停中（`paused`）和异常终止（`failed`）。成功（`succeeded`）和取消（`cancelled`）只作为最终状态通知，随后移除卡片。运行实例尚未确认暂停或终止时，保留原状态并设置请求标记，前端据此显示“正在暂停”或“正在终止”。

计划快照 `ScheduleInfo` 用于生成定时任务槽卡片，保存计划标识（`schedule_id`）、显示名称（`name`，取首项名称）、登记时间（`created_at`）、时间设置（`timing`）、目标队列参数（`queue_id`、`new_queue_name`）、有序任务定义摘要（`entries`）、下次触发时间（`next_run_at`）、上次触发时间（`last_triggered_at`）、上一轮标识（`last_run_id`）、上一轮产生的任务标识列表（`last_task_ids`）、跳过次数（`skipped_count`）、状态（`state`，active 或 blocked）、错误摘要（`error`）和修改版本（`revision`）。每项定义摘要包含 `entry_id`、`name` 和排列序号，不向前端发送 Python 函数及其参数对象或脚本启动环境。

功能模块通过 `get_task(task_id)` 读取一个仍在队列中的实例，通过 `list_tasks(queue_id="main")` 按队列顺序读取任务。`list_queues()` 返回全部队列，主队列在首位，其余按创建时间排列；`list_schedules()` 按下次触发时间返回计划，没有下次时间的计划排在最后。`get_snapshot()` 一次返回全部队列、任务、计划、待输入请求、统计和当前全局修订号，供界面初始化和重连使用。这些方法均通过 `await` 调用，返回的数据为快照，修改返回值不能更改管理器状态。

更改计划时间调用 `await update_schedule(schedule_id, timing=..., expected_revision=...)`，返回更新后的 `ScheduleInfo` 快照；删除计划调用 `await delete_schedule(schedule_id, expected_revision=...)`，返回被删除计划的最终快照。界面传入读取到的计划修改版本，版本不匹配时返回 `RevisionConflict`，重新获取设置后再操作。追加定义也增加该计划的修改版本。更改时间作用于整组未来任务，删除计划同时删除全部尚未触发的定义，两者均不影响已经入队的实例。第一版暂不提供单独删除或改排某项定义的接口。

#### 暂停、恢复和终止任务

功能模块或前端管理命令分别通过 `pause_task(task_id)`、`resume_task(task_id)`、`cancel_task(task_id)` 请求暂停、恢复和终止，这些方法通过 `await` 调用并返回操作后的任务快照。尚未开始的排队任务可以立即暂停或取消；运行中的任务先记录请求，等待任务主动检查。失败实例可以通过终止操作清理，不能恢复为原函数继续执行。已经移除的实例返回 `TaskNotFound`，已请求终止的实例不能再暂停或恢复。

任务上下文 `ctx` 提供只读的 `task_id`、`queue_id`、`schedule_id`、`entry_id`、`run_id`。协程任务在可中断的工作单元之前调用 `await ctx.checkpoint()`，同步任务则在线程中调用 `ctx.checkpoint_sync()`。检查点用于确认暂停或抛出专用取消异常；模块通过 `try/finally` 清理资源，不得吞掉取消异常。等待间隔可以使用 `await ctx.sleep(seconds)` 或同步的 `ctx.sleep_sync(seconds)`，以便等待期间也能响应控制请求。

暂停只有到达检查点后才释放队列执行位置。任务恢复时先重新取得位置，然后从原检查点继续，不能重新调用整个函数。暂停期间函数栈仍然存在，因此模块在检查点前释放不适合长期持有的锁、事务等资源。暂停的同步函数仍会占用线程池工作线程，执行资源不足时，其他队列的同步任务可能继续等待。

取消一个已经开始后又暂停的任务时，管理器唤醒它完成退出清理，清理结束前保留实例及队列，不能提前宣告移除。清理期间暂缓启动该队列的新任务，已经运行的后继任务则不被中断，模块确保清理可以与后继任务安全共存。没有检查点的函数只能在返回时响应控制请求，框架不能安全地强杀 Python 线程。只有暂停请求时函数自然返回仍算成功；终止请求与正常返回竞态时，以管理器首先提交的最终状态为准。

#### 队列日志与前端显示

队列日志用于情况简报框和管理页的控制台显示，按队列分别保存最近 1000 行。任务通过线程安全的 `ctx.log(text, level="info")` 写入所属队列，管理器自动附加稳定行标识（`row_id`）、最近变更序号（`seq`）、时间（`time`）、任务标识（`task_id`）、任务名称（`task_name`）和等级（`level`），正文保存在 `text` 中。多行输入按行拆分，单行最多保留 16 KiB UTF-8 文本，超出截断并标记。

日志支持真正的 ANSI SGR 颜色序列，例如 Python 字符串 `"\x1b[31m红色文字\x1b[0m"`。前端只解释允许的 SGR 颜色，丢弃其他控制序列，并对普通文本进行 HTML 转义。框架不重定向整个进程的 stdout/stderr，以免并发任务的输出混在一起；函数任务未处理异常的完整堆栈由管理器写入日志；脚本的标准输出和标准错误则由子进程管道单独收集，任务卡片只显示摘要。线程输出通过有界缓冲交给事件循环，满时丢弃日志并累计数量，恢复后补一行提示。

读取日志调用 `await read_logs(queue_id="main", after_seq=None, limit=1000)`，返回记录列表 `entries`、下一次读取游标 `next_seq` 和是否缺失早期记录的 `truncated`。初次返回最近记录及当前未完成行，后续按变更序号返回 append/replace 事件。后端除最近 1000 行外，另保留每队列最近 2000 条变更事件供增量查询；快照中的每行携带最近一次变更序号，返回游标为整个快照的边界序号，不能以最后一行的序号代替。结果增加 `mode`（snapshot 或 delta），让前端区分替换快照与应用增量；增量达到 `limit` 时，`next_seq` 只能推进到本次实际返回的最后一个事件，不能跳过尚未返回的变更。增量事件缺失时设置 `truncated=true` 并返回完整保留行快照，由前端替换显示。清空调用 `await clear_logs(queue_id="main")`，移除当前保留行并返回清空边界序号。同一队列存续期间序号单调递增，清空不能重置序号或沿用旧 `row_id`，同时清除未完成行及解析状态，清空后的后续输出建立新行；游标落在已覆盖或清空的范围时，返回 `truncated=true`，让前端用仍保留的记录重建显示。

队列快照 `QueueInfo` 保存队列标识（`queue_id`）、名称（`name`）、创建时间（`created_at`）、是否主队列（`is_main`）、任务数量（`task_count`）、当前执行实例（`running_task_id`）和状态（`state`）。状态区分空闲（idle，仅主队列可持续为空）、执行中（running）、等待调度（waiting，例如恢复后等待线程资源）和挂起（suspended，仅剩暂停或失败实例）。简报的主队列任务数包括全部卡片，队列总数包括主队列，执行数只统计 running 实例，计划及其中尚未入队的定义不计入这三项任务统计。

前端通过 `TASK_GET_SNAPSHOT`、`TASK_READ_LOGS` 查询，通过 `TASK_PAUSE`、`TASK_RESUME`、`TASK_CANCEL`、`TASK_CLEAR_LOGS`、`TASK_SCHEDULE_UPDATE`、`TASK_SCHEDULE_DELETE` 管理现有数据，通过 `TASK_INPUT_SUBMIT` 回答输入请求。每个请求带本连接内唯一的 `request_id`，响应命令统一为 `TASK_RESULT`，回传该标识、成功标记 `ok`，以及 `data` 或 `error: {code, message}`。第一版前端不提交 Python 函数、任意脚本路径或远程创建任务。

输入请求的建立和解决分别广播 `TASK_INPUT_REQUEST`、`TASK_INPUT_RESOLVED`，并更新全局修订号；输入文本第一版按普通非敏感回答处理，回显时使用纯文本日志，不支持密码输入。状态变化广播 `TASK_CHANGED` 并携带递增的全局修订号，提示重新获取快照；日志增量通过 `TASK_LOGS` 发送队列标识、变更序号和带 `row_id`、`op` 的记录，清空广播 `TASK_LOGS_CLEARED`。前端在连接成功时读取快照和当前查看队列的日志，缓存查询期间收到的增量，按修订号和序号去重后应用；发现缺口或重新连接时重新查询。全部客户端管理同一份状态，清空日志也同步到查看该队列的其他界面。推送可以合并，慢客户端沿用框架的发送超时和断开机制，不积累无限量的通知。

#### 错误处理和服务退出

参数类型或组合不合法返回 `TypeError` 或 `ValueError`；任务、队列、计划不存在分别使用 `TaskNotFound`、`QueueNotFound`、`ScheduleNotFound`。不允许的状态操作、修改版本冲突、服务正在退出分别使用 `InvalidTaskState`、`RevisionConflict`、`ServiceStopping`，输入相关错误另包括 `InputAlreadyResolved`、`InputNotFound`、`InputTargetMismatch`、`InputTimeoutError`，这些领域错误统一继承 `TaskAPIError`。WebSocket 适配层将预期错误转换为 `TASK_RESULT` 响应，不因无效管理操作关闭连接，也不向客户端发送异常堆栈。

服务退出时，管理器先停止定时触发，拒绝新建、追加、修改及恢复操作，再向全部任务发出终止请求并唤醒暂停任务。退出时还解决全部输入等待并回收脚本进程树。任务清理安排在模块 `shutdown()` 之前，避免任务继续使用已经关闭的模块资源。默认等待 10 秒，超时记录未退出实例；协程可以请求取消，同步线程无法安全强杀，因此该等待时间不是进程退出的硬期限。仍有任务使用模块资源时，不能仅因窗口超时就直接关闭这些资源。


#### Windows 与 Linux 运行

后端任务 API 同时支持 Windows 和 Linux，队列、定时计划、协程及线程任务、日志和输入等待共用相同实现。脚本通过当前后端的 `sys.executable` 启动，不调用 Windows 专用命令或依赖某个固定的 Python 路径；本机输入通道使用回环 socket，标准输出和标准错误通过子进程管道重定向。Linux 上使用实际存在的 Linux 路径，例如 `script={"path": "/srv/scripts/scan.py", "cwd": "/srv/scripts", "argv": []}`，不能直接使用文档示例中的 Windows 盘符路径。

进程清理按系统分别处理。Windows 使用 Job Object 约束脚本及其派生进程，相关 Win32 API 只在 Windows 分支调用。Linux 创建脚本时传入 `start_new_session=True`，使脚本进入独立会话及进程组；终止时先向该进程组发送 SIGTERM，最多等待 5 秒，再用 SIGKILL 清理仍存活的组内进程。脚本主进程已经退出时，管理器仍清理本次进程组中的后代，再读完剩余输出，避免后代继承管道写端使任务永久无法结束。主动创建新会话或脱离原进程组的 Linux 后代不在这个进程组清理范围内，脚本自行转为守护进程后，管理器无法保证其脱离进程组的后代随任务一起终止。

运行环境仍遵循主框架的 Python 3.8 及以上要求，脚本自身的第三方依赖安装在后端使用的解释器环境里。Linux 验收可运行 `python3 -m unittest discover -s tests -p test_tasks.py -v`，该组后端测试不依赖 Edge 或 Playwright。当前开发机器的实际执行验证环境为 Windows；Linux 信号分支已有模拟测试，实际 Linux 运行仍需在 Linux 环境执行上述命令确认。

#### 当前实现与验证

计划任务后端集中实现在 `backend/backapi.py`。其中 `TaskManager` 和 `TaskContext` 提供模块调用入口、队列调度及输入等待，`TaskBridge` 接收 WebSocket 管理命令并维护每连接的有界推送缓冲，`run_script()` 管理子进程、输出管道和输入控制连接。框架在模块初始化前登记管理器，在应用启动时启动调度，在模块退出清理前终止任务。推送缓冲溢出时，适配层通知客户端重新读取状态和日志。

同一个 `backapi.py` 也提供脚本子进程入口。父进程通过 `sys.executable -u backapi.py --run-script <脚本路径> [参数...]` 启动独立进程，子进程执行 `_script_main()`，建立输入控制通道、适配 `input()` 并调用 `runpy.run_path()`。普通模块导入该文件不会执行这个入口，也不会创建工作线程或启动调度；脚本仍在独立进程内运行。

通用控制台与计划任务前端均内联在 `MainUI.html` 中：`<script id="ui-console">` 实现不依赖任务和连接状态的控制台，`<script id="task-slot">` 将任务快照、日志及输入请求转换为界面数据，`<style id="task-slot-styles">` 提供顶部入口、情况简报框和管理页的样式。管理页沿用布局模块的 `new_page()` 和返回菜单。新建任务页按本节约定暂为空白，实际任务由后端模块通过 `create_task()` 建立。

运行 `python -m unittest tests.test_tasks -v` 验证串并行队列、暂停恢复、定时整批创建、周期跳过、目标队列失效、线程及协程输入、输入超时、日志游标和真实脚本子进程。另运行 `python -m unittest tests.test_tasks_browser -v`，在安装 Playwright 和本机 Edge 的环境中验证真实前端的脚本输入、暂停恢复、定时计划更改及删除、控件回调和视口边界；未安装 Playwright 时跳过浏览器测试。测试使用临时配置、临时脚本和临时本机监听端口，不加载真实业务模块。


# 后端 back.py

## 连接与通讯

### 启动与配置

主框架支持 Python 3.8 或更新版本。`requirements.txt` 按 Python 版本选择依赖：
Python 3.8/3.9 使用 aiohttp 3.10.11，Python 3.10 及以上使用 aiohttp 3.14.3。
功能模块及其依赖的 Python 版本要求由各模块自行确定。
主框架由 aiohttp 创建应用、监听端口并处理 WebSocket 连接。

启动时读取 `backend/config/global_config.json` 的 `base-port`：

- 缺少键时补写 `8768`；文件不存在时创建包含 `base_dir: ["./"]` 的默认配置。
- 缺少整个 `http-url-config` 字段时，自动补写 `max-blob-bytes: 104857600` 和
  `tmp-blob-file: false`；已有该字段时保留原配置，不覆盖自定义值。
- 端口必须是整数且在 1～65535 范围内，不接受布尔值或字符串。
- 配置补写采用同目录临时文件和原子替换，保留其他键及原有相对路径。
- JSON 错误、回写失败、监听失败会报错并以非零状态退出，不自动换端口。
- 监听 `0.0.0.0:<base-port>`，HTTP 和 `/ws` 共用此端口，不提供前端页面。

配置加载和模块初始化在启动时发生，单纯 import back 不产生这些副作用。

### HTTP 服务信息与资源访问

| 路由 | 方法 | 用途 |
| --- | --- | --- |
| `/api/server-info` | GET、HEAD、OPTIONS | 版本、协议版本、端口、能力和资源根目录列表 |
| `/resources/{rootId}/{relativePath}` | GET、HEAD、OPTIONS | 读取允许目录内的文件 |
| `/blobs/{token}/{data_name}` | GET、HEAD、OPTIONS | 读取连接登记的临时内存数据 |
| `/ws` | GET（WebSocket 升级） | 模块命令和二进制消息 |

服务信息返回 `version`、`protocol_version`（1）、`base_port`、
`websocket_path`（`/ws`）、`capabilities` 和 `resource_roots`。
capabilities 包含 http_resources、byte_ranges、websocket 三个布尔字段；
resource_roots 是 `[{"id": "0", "name": "目录名"}]`，不包含磁盘绝对路径。
服务信息使用 `Cache-Control: no-store`。

`ResourceRegistry` 在启动时按 global_config.json 中 `base_dir` 的原始列表索引
登记有效目录。rootId 从 0 开始，以规范十进制字符串表示，例如 `0`、`1`、`12`，
不接受前导零、正负号等其他写法。不存在、不可访问或受保护的目录不登记，
但保留其编号空位，后面的索引不前移；无效或未登记的 rootId 返回 404。
文件属于多个根目录时，生成 URL 优先选择层级最深的根目录；重复目录选择最小索引。
例如 `base_dir[2]` 下的 `动画/第一集.mp4` 映射到
`/resources/2/动画/第一集.mp4`（发送时对相对路径做 URL 百分号编码，不使用 Base64）。
反向解析由 rootId 定位根目录，再拼接相对路径并执行访问校验。

映射在应用启动时建立，运行期间不随配置文件变化，重启后读取新配置。
调整列表顺序或更换某项目录可能使旧 URL 失效或指向不同文件，客户端不应将
资源 URL 作为长期文件标识。rootId 仅用于定位，不是认证凭据。

资源请求只接受登记标识和相对路径。路径只解码一次，拒绝空段、`.`、`..`、
反斜杠、冒号、控制字符及以空格或点结尾的路径段，防止 Windows 路径别名和
备用数据流访问。最终路径经过 resolve 后必须仍在对应根目录内，符号链接
及 Windows 目录联接不能通向范围外。仅提供普通文件，不列出目录。
项目自身目录、运行后端目录和全局配置文件受到保护，即使 base_dir 配置了
其上级目录也不会通过资源接口发布。默认 base_dir 为 `./` 时指向后端目录，
不会登记成可下载资源根；需要在配置中指定实际的外部资源目录。

路径检查在线程中执行，文件响应使用 aiohttp `FileResponse`。它处理 HEAD、
单段 Range（起止范围、开放尾部、后缀范围）、206、416、ETag、Last-Modified
及条件请求。文件以有界缓冲传输，不整段载入内存；原生 sendfile 不可用时
由 aiohttp 回退至分块发送。字体和常见媒体类型明确指定 MIME，其余由 aiohttp
推断。文件使用 `Cache-Control: no-cache`，允许缓存但要求再次校验。
本接口不转码、不验证视频编码；播放支持取决于客户端及文件本身。

资源缺失、目录请求或未知 rootId 返回 404；非法路径或无权限返回 403；
不支持的方法返回 405。`/`、`/MainUI.html`、`/frontend/...` 均不注册。

只读 HTTP 接口允许无凭据跨源访问，`Access-Control-Allow-Origin` 为 `*`，
可供 file:// 页面使用。OPTIONS 接受 GET/HEAD，以及 Range、If-Range、
If-None-Match、If-Modified-Since 请求头；其他预检请求返回 403。
Content-Length、Content-Range、Accept-Ranges、ETag、Last-Modified 被暴露给
客户端。aiohttp 的 on_response_prepare 在发送响应头前添加这些字段，覆盖
文件响应在 prepare 时生成的 206/304/416 和 HTTP 错误响应。
不发送 Allow-Credentials，WebSocket 不走这套 CORS 流程。

### 模块接口与连接生命周期

`ModuleManager` 按 `backend/config/module_config.json` 中的配置顺序加载启用的
模块，通过 `create_module(global_config, back_version)` 创建实例；后端版本为
`TIPHERETH 1.0.0`。返回空值表示模块不支持该版本，此时跳过加载。

传给模块回调的 websocket 参数是 `backend/back.py` 中定义的
`FrameworkConnection`。每个客户端连接对应一个稳定对象，可用作模块自己的
字典键，并提供：

- `await send(str | bytes | bytearray | memoryview)`：发送一条消息，二进制不改写。
- `await close(code=1000, reason='')`：关闭该连接。
- `closed`：连接是否已关闭。
- `resource_url(file_path)`：将登记资源目录内的文件路径转换为
  `http(s)://主机:端口/resources/...` 绝对 URL，应用同样的路径校验；不属于允许目录时抛出异常。
  协议、主机和端口取自该客户端 WebSocket 升级时的 HTTP 请求地址，不使用监听地址
  `0.0.0.0`，也不使用客户端页面的 Origin。默认不根据转发请求头推断代理外部地址。
  该方法同步访问文件系统，耗时的网络盘调用可由模块放入工作线程执行。
- `recv()` 供框架唯一业务消费者使用，模块回调不得另外读取消息。
- `blob_url(data_name, data: bytes)`：同步登记内存数据，返回绝对 HTTP(S)
  URL `/blobs/{随机标识}/{data_name}`，协议与主机来源同 `resource_url()`。名称为非空字符串，
  每次调用均创建新 URL，名称或内容相同也不覆盖。不同连接独立登记；
  URL 末段为百分号编码后的名称，不允许名称为点路径、包含路径分隔符或控制字符。
  请求中的随机标识和名称均须匹配登记内容，否则返回 404。
  名称的扩展名用于推断 MIME，未知时为 application/octet-stream。
- `delete_blob_url(blob_url: str)`：按创建时返回的完整 URL 同步删除本连接数据，返回是否存在；
  已删除、不匹配或其他连接的 URL 返回 False，非字符串参数抛出 TypeError。
  删除后旧地址返回 404，再次登记生成新地址。连接关闭或处理协程退出时清理全部登记。

blob 由应用共享的 `BLOBS_KEY`（BlobStore）登记，所有连接合计计算内存中 bytes 的总长度。
`global_config.json` 的 `http-url-config` 控制容量，缺省配置如下：

```json
"http-url-config": {
    "max-blob-bytes": 104857600,
    "tmp-blob-file": false
}
```

`max-blob-bytes` 为非负整数，默认 100 MiB；`tmp-blob-file` 为布尔值，默认 false。
启动时验证配置，修改后重启生效。未超限时数据保存在内存；新增后将超限且不允许临时文件时，
`blob_url()` 抛出 MemoryError，不登记新 URL、不改变现有资源。
允许临时文件时，按所有连接合并后的创建顺序，从最早仍驻留内存的 blob 开始，
逐个写入 `backend/classify_shower/temp/http-blob-*.bin`，直到内存能容纳新数据。
读取不改变该顺序，已转存的数据跳过；转存后原 URL、名称和 MIME 不变。
单个新 blob 大于限额时直接写入临时文件，不强制转存旧数据；限额为 0 时非空数据均需落盘。
临时文件写入失败则抛出 OSError，新 URL 不登记；此前成功转存的旧数据继续有效，
当前转存失败的数据仍保留在内存中。

该限额统计登记表持有的内存数据，不包括调用方仍持有的 bytes、正在发送的响应及对象开销，
不是进程总内存上限。blob_url() 保持同步，转存涉及同步磁盘写入，应避免频繁登记大块数据。
显式删除、断线及正常服务退出时同时释放内存和相应临时文件，不删除 temp 下其他文件。
强制终止进程可能遗留临时文件，当前不会在启动时扫描删除历史文件，也未限制磁盘总用量。
HTTP 支持 GET/HEAD、跨源 OPTIONS，使用 no-store；内存响应不实现 Range，
落盘响应由 FileResponse 提供 Range，调用方不应依赖 blob 一定支持 Range。
已有响应不会因删除而撤回。方法须在框架事件循环中调用，关闭的连接不能再登记资源。
持有 URL 即可读取数据，不检查下载者是否为创建该资源的 WebSocket 客户端。

先发送 `BACKEND_VERSION`（`version` 为支持的前端版本列表），然后发送
`SET_NOWPATH`，再按模块配置顺序调用 `when_connect(connection)`；
每条 JSON 对象按顺序调用 `message_proc(connection, data)`。上行消息须为
JSON 对象文本；下行 HSV1 由模块构造，适配层原样发送，前端负责解析和分发。

运行时的资源根目录相对于 backend 目录解析为绝对路径，不存在的路径记录
警告并跳过。有效路径通过 `SET_NOWPATH` 发送到前端，不回写这些绝对路径。

### 并发收发与连接限制

网络读取任务独立于业务分发任务，业务 await 时仍能处理 Ping/Pong、断线。
每连接最多排队 32 条上行消息，单条上限 1 MiB；超限或非法数据关闭该连接。
心跳参数为 30 秒，使用 aiohttp 的 Ping/Pong 与超时检测；关闭握手超时设为 5 秒。
发送使用每连接锁及 aiohttp 64 KiB 写缓冲水位（不是消息大小上限），等待锁
和发送合计超过 30 秒时关闭慢连接；适配层不另建无界输出队列。

不同连接具有各自的读取任务、分发任务、接收队列和发送锁；同一连接的消息
由单个业务消费者依次处理。模块实例由所有连接共享，框架不改变模块内部
状态的归属，也不替模块实现业务并发控制。模块中的同步阻塞操作仍会阻塞
共用的事件循环。

| 异常情况 | 关闭码 |
| --- | --- |
| 上行文本不是合法 JSON 对象 | 1007 |
| 上行消息为二进制 | 1003 |
| 上行消息超过大小限制 | 1009 |
| 接收队列已满或发送超时 | 1013 |
| 模块连接或消息回调发生未处理的普通异常（ConnectionError 除外） | 1011 |
| 服务停止 | 1001 |

### 断线与服务退出

网络读取或业务分发任务结束时，框架取消该连接其余未完成的任务，然后按
模块顺序调用一次 `when_disconnect(connection)`，关闭连接并移除连接登记。
每个断线回调使用 5 秒超时，失败会记录日志并继续清理其他模块。

服务停止时拒绝新的 WebSocket 连接，关闭已登记连接并等待其清理完成，随后
按模块顺序调用可选的 `shutdown()`。每个 shutdown 使用 10 秒超时，单个模块
失败不阻止其他模块清理。协程超时依赖模块响应取消请求。
