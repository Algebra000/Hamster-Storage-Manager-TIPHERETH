# 存储管理器框架的功能实现

## 连接与通讯

### 初始化与建立连接

MainUI.html 在加载布局模块和功能模块之前定义五组回调列表。模块通过注册
回调参与初始化、连接状态处理和消息处理：

| 回调列表 | 参数 | 调用时机 |
| --- | --- | --- |
| `onload_func_list` | 无 | 页面加载完成后、建立连接前 |
| `when_connect_func_list` | 无 | WebSocket 连接成功时 |
| `when_disconnect_func_list` | 无 | WebSocket 关闭时 |
| `message_proc_func_list` | `data` | 收到并解析 JSON 文本消息后 |
| `binary_message_proc_func_list` | `header, payload` | 收到并解析 HSV1 二进制消息后 |

`window.onload` 按注册顺序调用初始化回调，然后初始化服务器地址控件，恢复
上一次输入的地址并自动连接；没有记录时使用 `localhost:8768`。
根目录右侧的输入框接受 IP、主机名及端口（IPv6 使用方括号），省略端口时
使用 8768；也接受 HTTP/HTTPS、WS/WSS 地址，WebSocket 路径统一为 `/ws`。
HTTPS 页面只允许连接加密地址。客户端须填写服务端实际配置的端口。
`createAutoReconnectWebSocket(url, onMessage)` 创建原生 WebSocket，并将
`binaryType` 设为 `arraybuffer`。

每次 WebSocket 建立后进入版本验证状态，等待后端首条文本消息
`{"command":"BACKEND_VERSION","version":["TIPHERETH 1.0.0"]}`。
`version` 是后端支持的前端版本列表；与 ROLAND 相同，检查列表中是否存在
字符串，其去除首尾空白、按空白分隔后的第一段等于前端 `VERSION_NAME`。
因此按版本系列匹配，不要求完整版本号一致。验证成功才启用模块回调和业务
收发，版本消息由框架消费，不分发给模块。首条消息无效、不兼容或 5 秒内
没有收到版本信息时关闭连接并提示，停止自动重连。手动连接可再次尝试。
主动断开或切换地址会取消验证定时器，旧连接的版本消息不能启用新连接。
HTTP 服务信息只用于历史状态探测和资源查询，不参与连接版本校验。

连接成功时，框架先设置内部连接状态，再通过 `BasicEvent.when_connect()`
更新状态文字、启用根目录输入框，随后调用连接回调。各列表按数组顺序同步
调用回调，单个回调同步抛出的异常会被记录，不阻止后续回调执行；框架不等待
前端回调返回的 Promise。

### socket 接口与发送消息

全局变量 `socket` 保存连接管理器对象，初始为 `null`：

| 接口 | 行为 |
| --- | --- |
| `url` | 连接管理器的目标 WebSocket 地址，调用方应只读使用 |
| `send(data)` | 原生 WebSocket 处于 OPEN 时发送并返回 true，否则返回 false |
| `close()` | 关闭当前原生 WebSocket，并取消重连及连接超时定时器 |
| `reconnect()` | 立即尝试建立连接 |
| `isConnected()` | 返回内部连接状态 |
| `isActive()` | 当前管理器是否仍是页面使用的连接且未被主动停止 |

模块发送 JSON 命令时自行调用 `JSON.stringify()`，`send()` 不自动序列化，
也不缓存断线期间的消息。返回 true 表示已交给原生 WebSocket 发送，不表示
后端业务处理成功。

### 接收与分发消息

`messageProc(event)` 根据消息类型进行处理：

1. 文本消息通过 `JSON.parse()` 解析。如果 `command` 为 `SET_NOWPATH`，
   先用 `data.path` 更新根目录输入框，再把同一个 data 对象交给文本回调列表。
2. 二进制消息接受 ArrayBuffer 或 Blob；Blob 先转为 ArrayBuffer，再检查
   HSV1 魔数及 JSON 信息头长度。消息结构为：

   ```text
   4 字节魔数 0x48535631 | 4 字节无符号信息头长度（大端） | UTF-8 JSON 信息头 | 二进制载荷
   ```

   信息头解析为 header 对象，其余字节作为 payload（ArrayBuffer），依次
   传给二进制回调列表。

无法解析或结构错误的消息会被记录并丢弃。框架负责分发，模块自行检查
command、widgetId、streamId 等业务字段，判断消息是否属于自己。
同一连接的消息解析按到达顺序串行执行；关闭、重连或切换地址后，旧连接
事件及尚未完成的 Blob 解析结果不会再分发到模块。

### 地址历史与可用状态

合法输入、连接尝试和历史选择会写入浏览器 localStorage 的
`tiphereth.server-addresses.v1`，保存最近地址和最多 20 条去重历史。
刷新或重新打开页面恢复最近地址；记录属于当前浏览器，file:// 页面移动后
是否仍能访问原记录取决于浏览器。存储不可用时显示提示并退回内存记录。

输入框聚焦或点击箭头展开历史列表，每项最左侧显示状态圆点。列表打开时
通过各地址的 `/api/server-info` 检查协议版本及 `/ws` 路径；响应符合框架
协议时为绿色，请求失败或尚未确认时为红色，当前已建立的连接显示绿色。
每次最多并发探测 4 个地址，超时 2.5 秒，展开期间每 15 秒刷新；收起后
取消探测与刷新。圆点表示探测结果，不保证该地址的功能模块正常。
支持方向键选择、Enter 确认及 Escape 收起；选择历史只填入地址。

### 断线与自动重连

点击“连接”开始连接，按钮随即显示“断开”，连接中和等待重连时也可停止。
连接尝试超过 10 秒会关闭；意外断线后由 `schedule()` 固定等待 1 秒再尝试连接，
每次重试的等待时间相同，不随失败次数增加。`onerror` 只记录错误，由 `onclose` 统一
安排重连。曾建立成功的连接断开时调用一次 `BasicEvent.when_disconnect()`，
清空并禁用根目录输入框，执行断线回调。重连成功再次执行连接回调。

点击“断开”调用 `disconnect()`，取消定时器、关闭连接并清空全局 socket，
主动断开不重连。切换地址建立连接前会先停止旧管理器，旧事件不能改变新连接。
页面离开时也会停止连接和历史探测。框架不更改第三方模块的业务状态归属。

## 计划任务槽

所谓计划任务功能，是用来在服务器后台运行一些需要消耗一定时间的任务的功能，例如扫描目录建立数据库、自动下载弹幕评论数据等任务。一个任务可以由某个py脚本建立，也可以由功能模块调用接口将某个函数作为一个任务运行。一个任务可以立刻运行，也可以设置为定时任务定期执行。

普通任务之间可以采用串行策略，即一个任务结束后执行下一个任务，排队执行；有些任务有时效性，需要同时并发执行。为了管理不同任务的串行和并发策略，这里使用“队列”这个概念来管理任务的执行。“队列” 可以视作装载任务的有序容器，一个队列里的任务从前到后依次排队执行，队列之间并发同时执行。一个任务不能单独执行，必须将其放到现有或新建的队列里，然后使得该任务得到执行。队列里的任务在正常执行完毕后直接从队列里移除。定时任务的定时是指在所要求的时间将该任务加到某个队列里，即在该时间前队列里没有此任务。

框架默认只有一个主队列，用于执行多数任务。在创建任务时，默认将任务放到主队列里排队，也可以指定新建队列用于执行此任务以实现并发。这些新建的队列一旦其中不再有任务，就会被自动销毁。

### 界面设计

在 #upbar 里 IP 输入框和连接按钮的右侧设一内联 svg 按钮以作为计划任务功能的入口。点击次按钮出现一悬浮下拉框作为情况简报框，该下拉框固定600px高度，400px宽度。如果下拉框底部超出浏览器视口，那就把下拉框高度设为合适的值使得下拉框底部恰在浏览器视口内。如果下拉框宽度超过浏览器视口宽度的40%，那就把下拉框宽度设为视口宽度的40%。应当确保整个下拉框在视口内。

情况简报框前三行显示 “主队列有 x 个任务”、“当前有 y 个队列”、“正执行 z 个任务”这些字样，在这三行下面显示一个横向滚动框，框里从左到右依次水平排列表示主队列里任务的div块，即任务卡片。每个任务卡片的右上角是状态签，显示该任务目前的状态。状态签纯色底白色字，每种状态对应状态签一种背景颜色。一个任务可能具有的状态有执行中、暂停中、排队中、异常终止。如果任务结束且没有异常，那么该任务会直接从队列里移除；如果正在执行的任务被暂停或异常终止，那么队列会跳过该任务执行后面的任务，如果该任务后面不再有任务，那么队列会进入挂起状态，直到有新任务进来或暂停的任务恢复执行。然后任务的名称位于任务卡片中央。横向滚动框的滚动条要做适当的美化。

横向滚动框的下面是一用于展示主队列运行输出日志的div，要支持表示颜色的字符，例如 `033[31m` 表示红色，`033[32m` 表示绿色，`033[33m` 表示黄色等。然后日志最大行数为1000行，超出直接覆盖掉最早的输出。日志 div 由一个JS对象 `cs_consoleDiv` 管理，详见[控制台控件](#控制台控件)。

日志div下面，情况简报框的右下角有一个“详细信息”按钮，点击调用 `new_page()` 打开计划任务管理页。“详细信息”按钮左边有一个“清空日志”按钮，点击后可以清除所有日志。

关于计划任务管理页，其上半部分是一个大滑动板块控件。第一行有字样“当前状态槽”，然后该字样右侧有“队列”下拉选择框，用于选择当前要查看的队列。默认选择主队列。下拉选择框里显示所有队列的名称，用户可以点击下拉选择框选择其他队列。这一行下面紧接着是装有任务卡片的横向滚动框，显示当前选中队列里的任务。每个任务卡片除了状态签、任务的名称外，在任务名称下面还要显示任务的创建时间，然后再下面一行要显示两个按钮，一个“暂停”按钮，点击暂停任务；一个“终止”按钮，点击弹出确认框，确认后终止任务。第一行的字样、下拉选择框和横向滚动框放在一个大的滑块div里，作为滑槽里第1页的内容。该滑块div在一个滑槽div里，滑槽div固定。滑槽div的左侧有“<”形、右侧有“>”形的svg按钮，点击分别使得滑块div右滑、左滑实现翻页(触屏移动端的话手指左右滑也可以实现该操作)。第一页“<”按钮失效变淡，第二页“>”按钮失效变淡。

滑槽里第2页的内容是所有的定时任务卡片。这些卡片也放在一个横向滚动框里。然后横向滚动框上方是字样“定时任务槽”。每个定时任务卡片在任务名称下面还要显示任务预定执行的时间，然后再下面一行要显示两个按钮，一个“更改”按钮，点击更改任务的时间设置；一个“删除”按钮，点击弹出确认框，确认后删除该定时任务。

滑动板块下面分成两列，左列较窄，右列较宽。右列是当前选中队列的日志输出的div(类似控制台，`cs_consoleDiv` 的另一实例)，同样要支持表示颜色的字符，最大行数为1000行。然后左列添加一个大按钮，按钮左侧是大“+”符号，符号右侧是字样“新建任务”。点击新建任务按钮，会切换到新建任务页面。当前新建任务页面暂不开放，是一个带有布局模块返回菜单栏的空白页。

### 控制台控件

控制台控件是一种用于在界面上展示日志和接受用户输入的控件DIV，就像控制台一样。其由一个JS对象 `cs_consoleDiv` 管理，支持表示颜色的ASCII字符，可以设置最大行数，超出直接覆盖掉最早的输出。

### 后端任务相关API

相关 API 计划实现在项目根目录下的 `backend/backapi.py`，供后端功能模块在同一进程内调用。本节是待实现的设计约定，以下参数默认值、返回结构和错误处理均为拟定行为。

以下是后端 Python API 清单。`tasks` 表示 `get_task_manager()` 返回的管理器，`ctx` 表示任务函数收到的上下文；标有 `await` 的方法应在框架事件循环中调用。同一函数的不同用法合并在同一行说明，完整参数及互斥规则见后文。

| API | 参数简述 | 返回 | 用法与详细描述 |
| --- | --- | --- | --- |
| `get_task_manager()` | 无参数 | 当前唯一的 `TaskManager` | 功能模块取得管理器；未初始化时抛出异常。（对应实现见[任务管理器与任务数据](#任务管理器与任务数据)） |
| `await tasks.create_task(name, func, ...)` | `name`、`func` 为名称和函数，`args=()`、`kwargs=None` 为调用参数。即时创建默认放入 `queue_id="main"`；新建队列应传 `queue_id=None`、`new_queue_name`。传 `timing` 登记定时计划；传 `after_schedule_id` 向已有计划追加定义，此时须传 `queue_id=None`，且不可同时传 `timing` 或 `new_queue_name` | `TaskCreation`：即时创建时含实际 `task_id`、`queue_id`，计划及定义标识为 null；定时登记或追加时含 `schedule_id`、`entry_id`，实例及实际队列标识为 null | 即时入队或随首项任务新建队列（对应实现见[创建任务并放入队列](#创建任务并放入队列)）；登记计划，触发时才整批入队（对应实现见[登记定时任务与触发入队](#登记定时任务与触发入队)）；向计划未来每轮的定义末尾追加一项，不影响已入队实例（对应实现见[向定时计划追加后续任务](#向定时计划追加后续任务)） |
| `await tasks.get_task(task_id)` | 已入队且尚未移除的任务标识 | `TaskInfo` 快照 | 查询一张任务卡片的数据。（对应实现见[查询和更改任务设置](#查询和更改任务设置)） |
| `await tasks.list_tasks(queue_id="main")` | 要查看的队列标识，默认主队列 | 按队列顺序排列的 `TaskInfo` 列表 | 读取该队列全部卡片，包括暂停和失败任务。（对应实现见[查询和更改任务设置](#查询和更改任务设置)） |
| `await tasks.list_queues()` | 无参数 | `QueueInfo` 列表，主队列在首位 | 填充队列选择框，其余队列按创建时间排列。（对应实现见[查询和更改任务设置](#查询和更改任务设置)及[队列日志与前端显示](#队列日志与前端显示)） |
| `await tasks.list_schedules()` | 无参数 | 按下次触发时间排序的 `ScheduleInfo` 列表 | 读取定时任务槽，暂无下次时间的计划排在最后。（对应实现见[查询和更改任务设置](#查询和更改任务设置)） |
| `await tasks.get_snapshot()` | 无参数 | 全部队列、实例、计划、统计及全局修订号组成的快照 | 初始化界面或在重连后重建状态。（对应实现见[查询和更改任务设置](#查询和更改任务设置)） |
| `await tasks.update_schedule(schedule_id, timing=..., expected_revision=...)` | 计划标识、新时间设置及读取到的计划修改版本 | 更新后的 `ScheduleInfo` 快照 | 更改整组未来任务的时间，版本冲突时报错。（对应实现见[查询和更改任务设置](#查询和更改任务设置)） |
| `await tasks.delete_schedule(schedule_id, expected_revision=...)` | 计划标识及读取到的计划修改版本 | 被删除计划的最终 `ScheduleInfo` 快照 | 删除计划和全部未触发定义，保留已入队实例。（对应实现见[查询和更改任务设置](#查询和更改任务设置)） |
| `await tasks.pause_task(task_id)` | 任务实例标识 | 操作后的 `TaskInfo` 快照 | 暂停排队实例，或向运行实例发出暂停请求。（对应实现见[暂停恢复和终止任务](#暂停恢复和终止任务)） |
| `await tasks.resume_task(task_id)` | 任务实例标识 | 操作后的 `TaskInfo` 快照 | 恢复暂停实例，使其在原位置重新参与调度。（对应实现见[暂停恢复和终止任务](#暂停恢复和终止任务)） |
| `await tasks.cancel_task(task_id)` | 任务实例标识 | 操作后的 `TaskInfo`；立即移除时为带 `cancelled` 状态的最终快照 | 请求终止实例，也用于清理失败卡片；运行实例须等待清理完成。（对应实现见[暂停恢复和终止任务](#暂停恢复和终止任务)） |
| `await ctx.checkpoint()` / `ctx.checkpoint_sync()` | 无参数；前者用于协程，后者用于同步工作线程 | 正常继续时返回 `None`；确认终止时抛出专用取消异常 | 在可中断单元前检查控制请求，暂停时等待恢复及重新取得执行位置。（对应实现见[暂停恢复和终止任务](#暂停恢复和终止任务)） |
| `await ctx.sleep(seconds)` / `ctx.sleep_sync(seconds)` | 等待秒数；分别用于协程和同步工作线程 | 正常结束等待时返回 `None`；确认终止时抛出专用取消异常 | 在等待期间继续响应暂停和终止。（对应实现见[暂停恢复和终止任务](#暂停恢复和终止任务)） |
| `ctx.log(text, level="info")` | 日志正文和等级，默认 info | `None` | 线程安全地向所属队列写日志，自动附加任务及时间信息。（对应实现见[队列日志与前端显示](#队列日志与前端显示)） |
| `await tasks.read_logs(queue_id="main", after_seq=None, limit=1000)` | 队列标识、已读取序号及返回行数上限；默认读取主队列最近日志 | 包含 `entries`、`next_seq`、`truncated` 的结果 | 初次加载或按游标增量读取，记录缺失时重建显示。（对应实现见[队列日志与前端显示](#队列日志与前端显示)） |
| `await tasks.clear_logs(queue_id="main")` | 队列标识，默认主队列 | 清空边界序号 | 清除该队列日志并通知其他客户端，不重置行序号。（对应实现见[队列日志与前端显示](#队列日志与前端显示)） |

#### 任务管理器与任务数据

任务管理器 `TaskManager` 用于保存当前队列、队列里的任务、尚未触发的定时计划和各队列的日志。`back.py` 应在模块初始化之前建立唯一的管理器，功能模块通过 `from backend.backapi import get_task_manager` 取得该对象。启动入口应统一包导入路径，避免同一文件被重复导入而产生不同的管理器。单纯导入 `backapi.py` 不启动调度，管理器尚未初始化时调用 `get_task_manager()` 应抛出 `RuntimeError`。

关于任务和定时计划，需要区分“已经入队的一次执行”和“准备在未来建立任务的设置”。前者称为任务实例，由 `task_id` 标识；后者由 `schedule_id` 标识，保存触发时间、目标队列设置和按顺序排列的任务定义。任务定义记录任务名称、函数及参数，每一项由 `entry_id` 标识。每次计划触发，都应根据这些定义产生新的任务实例，因此同一项定义可以在不同轮次对应不同的 `task_id`。

队列使用 `queue_id` 标识，其中主队列固定为 `main`，显示名称为“主队列”。其他队列只应在创建任务并将任务放入其中时一起创建，不能单独创建空队列。临时队列的最后一个任务被移除后，应立即销毁队列及其日志；暂停和失败的任务仍保留在队列中，因此包含这些任务的队列不销毁。只有主队列可以一直为空。

这些数据第一版只保存在内存中，后端重启后不恢复任务、计划和日志。任务管理器不依赖某个客户端连接，前端断线不影响任务执行。业务结果应由功能模块自行保存，任务函数的返回值不作为任务历史保留。

#### 创建任务并放入队列

`TaskManager.create_task()` 应作为统一的创建入口，用于立即建立任务、登记定时任务，以及向一个定时计划追加后续任务定义。调用形式拟定为：

```python
await tasks.create_task(
    name, func, *, args=(), kwargs=None,
    queue_id="main", new_queue_name=None,
    timing=None, after_schedule_id=None,
)
```

其中任务名称（`name` 参数）用于卡片显示，任务函数（`func` 参数）应是可调用对象，调用形式为 `func(ctx, *args, **kwargs)`。任务管理器应注入任务上下文 `ctx`，供函数检查暂停、终止请求和记录日志。`args`、`kwargs` 应在登记时复制外层容器，内部对象不深复制，调用方应避免在提交后修改共享数据。

不传 `timing` 和 `after_schedule_id` 时，`create_task()` 应立即建立一个任务实例，将它放到 `queue_id` 对应队列的末尾，默认放到主队列。如果需要新建队列，则应传入 `queue_id=None` 和非空的 `new_queue_name`。此时建立队列和放入首个任务应作为一次操作完成，不能先对外公布空队列。任务入队后才应参与调度，创建方法不等待任务执行完成。

关于队列参数，`queue_id` 指向已有队列，`new_queue_name` 表示随任务新建队列，两者不能同时指定。已有队列在调用时不存在应返回 `QueueNotFound`，不能自动创建同名队列，也不能改放到主队列。如果任务创建失败，新队列也不应留下。要向这个新队列继续添加普通任务，可以从第一次调用的返回值读取实际的 `queue_id`，再调用 `create_task()`；如果该队列已经执行完并销毁，则后一次调用应明确失败。

所有创建方式应返回 `TaskCreation`，其内容用于区分任务是已经入队还是仍在等待触发。返回到前端时可表示为以下结构：

```json
{
    "task_id": null,
    "queue_id": null,
    "schedule_id": "schedule-1",
    "entry_id": "entry-1"
}
```

其中已经入队的任务应返回实际的 `task_id` 和 `queue_id`，`schedule_id`、`entry_id` 为 null。示例表示登记了一个定时计划里的任务定义：此时尚未建立实例或选择实际队列，因此前两个字段为 null，后两个字段分别用于定位计划及其中的一项任务定义。即使计划将来要加入主队列，登记返回值中的 `queue_id` 也应为 null，目标队列应从计划设置读取，避免把未来的目标误认为已经入队的位置。

同一队列应按任务排列顺序选择可以执行的实例，同时最多有一个任务占用执行位置。不同队列之间可以并发。暂停和失败的任务应保留原位置，但不占用执行位置，调度器应跳过这些任务继续选择后面的任务。正常完成和确认取消的任务应从队列移除，恢复的任务应在原位置重新参与选择，不抢占已经运行的任务。

协程任务应在框架事件循环中执行，同步任务应在线程数有上限的线程池中执行。因此协程不能直接进行阻塞 I/O 或长时间 CPU 运算，队列之间的实际并发也受线程池等执行资源限制。模块自行建立子进程时，应负责子进程退出和资源清理。这里的脚本调用只指同一后端进程导入 API 后调用函数，独立运行的脚本不共享这个管理器。

#### 登记定时任务与触发入队

定时任务应通过向 `create_task()` 传入 `timing` 建立。此时管理器应保存触发时间、队列设置和首项任务定义，返回相应的 `schedule_id`、`entry_id`，不建立任务实例，也不创建临时队列。例如，每小时在新队列里扫描一次目录，可以这样登记：

```python
plan = await tasks.create_task(
    "扫描目录", scan_directory, args=(root,),
    queue_id=None,
    new_queue_name="目录扫描",
    timing={
        "type": "interval",
        "start_at": "2026-11-18T02:00:00+08:00",
        "seconds": 3600,
    },
)
```

其中 `interval` 表示按固定间隔触发，第一次触发时间为 `start_at`，以后沿 `start_at + n * seconds` 计算，不以上次执行完成的时间作为起点。第一版还应支持单次定时，例如 `{"type": "once", "run_at": "2026-11-18T02:00:00+08:00"}`。时间字符串必须带时区，后端应转成 UTC 比较；间隔秒数应为至少 1 秒的有限数值，不接受布尔值。新登记或更改的单次时间、周期起点应晚于服务端当前时间，过去时间应返回参数错误。第一版暂不加入 cron 和本地日历规则。

到了触发时间，调度器应先读取该计划当时保存的任务定义列表，确认目标队列仍然有效，然后为每一项建立任务实例。内部应复用 `create_task()` 的即时创建处理：不传入 `timing` 和 `after_schedule_id`，首项按计划保存的队列参数创建，后续项全部传入首项实际取得的 `queue_id`。调度器应为这些实例补上来源 `schedule_id`、`entry_id` 和本轮 `run_id`，这些来源标识不作为模块可自行填写的参数。

这整批创建应在同一次状态提交中完成，全部成功后才允许任务开始执行。若其中一项失败，应回滚本轮建立的全部实例及新队列；创建通知也应在整批提交后再发送。这样首项即使很快结束，也不会在后续项入队之前使临时队列被销毁。这里复用的是 `create_task()` 内部的创建逻辑，不能由定时器逐次调用对外方法并在中间放开调度。

如果计划指定 `new_queue_name`，则每一轮实际触发都应建立一个新的队列，队列里的任务全部移除后照常销毁。如果计划指定 `queue_id`，则应在触发时把本轮任务作为连续的一组追加到已有队列末尾，原先的任务仍排在它们前面。计划本身不延长临时队列的寿命，目标队列提前销毁时应把计划标为 `blocked` 并记录原因，不应静默更换目标。

周期计划应以整轮任务为单位判断是否重叠。上一轮中只要还有一个任务实例保留在任一队列中，包括排队、执行、暂停或失败状态，就应跳过本次触发，并记录跳过次数和原因。只有上一轮全部实例都被移除后，后续时刻才可以产生新一轮。事件循环延迟导致错过多个触发时刻时，只应尝试合并触发一轮，其余时刻跳过，下一次仍按原节拍计算。

单次计划整批入队成功后应从定时任务槽移除，周期计划则应保留并更新下次触发时间。入队失败的计划应保留为 `blocked`，不自动重试；用户更改时间时应重新校验目标，校验成功后才重新启用。如果原目标队列已销毁，则需要删除该计划并重新登记。

#### 向定时计划追加后续任务

为了让一个任务排在某个定时任务未来将创建或将加入的队列后面，`create_task()` 应接受 `after_schedule_id`。这个参数指向的是尚未结束的定时计划，表示将本次函数调用保存到该计划的任务定义列表末尾。例如，在前面的扫描计划之后追加更新索引：

```python
following = await tasks.create_task(
    "更新索引", rebuild_index, args=(root,),
    queue_id=None,
    after_schedule_id=plan.schedule_id,
)
```

其中 `after_schedule_id` 应与 `timing`、`new_queue_name` 互斥，并且要求 `queue_id=None`，因为追加项的触发时间和目标队列都应由所属计划决定。调用后应返回所属 `schedule_id` 和新生成的 `entry_id`，`task_id`、`queue_id` 仍为 null。计划不存在或已经作为单次计划成功触发并移除时，应返回 `ScheduleNotFound`，不能把任务转为立即执行。

追加项应从下一次尚未提交的触发开始生效。对于单次计划，它只随该计划执行一轮；对于周期计划，它应保存在定义列表中，以后每一轮都跟随创建。连续追加多项时应按成功提交的顺序排列，追加到同一计划的最后一项后面。多个模块同时追加时，也应由管理器串行提交，以确定最终顺序。

假设计划中原有“扫描目录”，之后追加“更新索引”和“下载弹幕”，则触发时应一次建立这三个实例，顺序为扫描、更新索引、下载弹幕。如果目标是主队列且已有两个任务，本轮三个实例应追加在这两个任务后面；如果目标是新队列，则三个实例都应进入本轮新建的同一队列。登记追加项时队列尚不存在也没有关系，因为保存的是将来入队的定义，而不是向空队列预先放入任务。

这里的“后面”只约定同一队列中的排列顺序，不表示前项成功后才执行。前项暂停或失败时，队列仍应按既有规则跳过它执行后项；需要依赖前项业务结果的模块应在后项函数里检查结果。追加定义也不应改变已经触发入队的任何一轮；要往当前这一轮继续添加任务，应使用该轮实际的 `queue_id` 调用即时创建方式，并接受队列可能已销毁的情况。

追加与触发应在同一事件循环中串行提交。如果追加先提交，本轮应包含新项；如果触发先提交，本轮应使用旧列表，新项从下一轮生效。单次计划触发先提交时，随后追加应因计划已移除而失败。这样不需要用“下次队列”这样的临时队列 ID，也不会把任务意外追加到上一轮的队列。

#### 查询和更改任务设置

任务实例快照 `TaskInfo` 用于生成当前状态槽的卡片，应保存任务标识（`task_id`）、名称（`name`）、所在队列（`queue_id`）、来源计划及定义（`schedule_id`、`entry_id`）、所属轮次（`run_id`）、状态（`state`）、创建时间（`created_at`）、首次开始时间（`started_at`）、暂停时间（`paused_at`）、错误摘要（`error`），以及暂停和终止请求标记（`pause_requested`、`cancel_requested`）。普通任务的来源字段应为 null，尚未发生的时间应为 null，其他时间应使用带 UTC 偏移的 ISO 8601 字符串。

任务状态应包括排队中（`queued`）、执行中（`running`）、暂停中（`paused`）和异常终止（`failed`）。成功（`succeeded`）和取消（`cancelled`）只应作为最终状态通知，随后移除卡片。运行实例尚未确认暂停或终止时，应保留原状态并设置请求标记，前端据此显示“正在暂停”或“正在终止”。

计划快照 `ScheduleInfo` 用于生成定时任务槽卡片，应保存计划标识（`schedule_id`）、显示名称（`name`，取首项名称）、登记时间（`created_at`）、时间设置（`timing`）、目标队列参数（`queue_id`、`new_queue_name`）、有序任务定义摘要（`entries`）、下次触发时间（`next_run_at`）、上次触发时间（`last_triggered_at`）、上一轮标识（`last_run_id`）、上一轮产生的任务标识列表（`last_task_ids`）、跳过次数（`skipped_count`）、状态（`state`，active 或 blocked）、错误摘要（`error`）和修改版本（`revision`）。每项定义摘要应包含 `entry_id`、`name` 和排列序号，不向前端发送 Python 函数及其参数对象。

功能模块应通过 `get_task(task_id)` 读取一个仍在队列中的实例，通过 `list_tasks(queue_id="main")` 按队列顺序读取任务。`list_queues()` 应返回全部队列，主队列在首位，其余按创建时间排列；`list_schedules()` 应按下次触发时间返回计划，没有下次时间的计划排在最后。`get_snapshot()` 应一次返回全部队列、任务、计划、统计和当前全局修订号，供界面初始化和重连使用。这些方法均应通过 `await` 调用，返回的数据应为快照，修改返回值不能更改管理器状态。

更改计划时间应调用 `await update_schedule(schedule_id, timing=..., expected_revision=...)`，返回更新后的 `ScheduleInfo` 快照；删除计划应调用 `await delete_schedule(schedule_id, expected_revision=...)`，返回被删除计划的最终快照。界面应传入读取到的计划修改版本，版本不匹配时返回 `RevisionConflict`，重新获取设置后再操作。追加定义也应增加该计划的修改版本。更改时间应作用于整组未来任务，删除计划应同时删除全部尚未触发的定义，两者均不影响已经入队的实例。第一版暂不提供单独删除或改排某项定义的接口。

#### 暂停、恢复和终止任务

功能模块或前端管理命令应分别通过 `pause_task(task_id)`、`resume_task(task_id)`、`cancel_task(task_id)` 请求暂停、恢复和终止，这些方法应通过 `await` 调用并返回操作后的任务快照。尚未开始的排队任务可以立即暂停或取消；运行中的任务应先记录请求，等待任务主动检查。失败实例可以通过终止操作清理，不能恢复为原函数继续执行。已经移除的实例应返回 `TaskNotFound`，已请求终止的实例不能再暂停或恢复。

任务上下文 `ctx` 应提供只读的 `task_id`、`queue_id`、`schedule_id`、`entry_id`、`run_id`。协程任务应在可中断的工作单元之前调用 `await ctx.checkpoint()`，同步任务则应在线程中调用 `ctx.checkpoint_sync()`。检查点用于确认暂停或抛出专用取消异常；模块应通过 `try/finally` 清理资源，不得吞掉取消异常。等待间隔可以使用 `await ctx.sleep(seconds)` 或同步的 `ctx.sleep_sync(seconds)`，以便等待期间也能响应控制请求。

暂停只有到达检查点后才应释放队列执行位置。任务恢复时应先重新取得位置，然后从原检查点继续，不能重新调用整个函数。暂停期间函数栈仍然存在，因此模块应在检查点前释放不适合长期持有的锁、事务等资源。暂停的同步函数仍会占用线程池工作线程，执行资源不足时，其他队列的同步任务可能继续等待。

取消一个已经开始后又暂停的任务时，管理器应唤醒它完成退出清理，清理结束前保留实例及队列，不能提前宣告移除。清理期间应暂缓启动该队列的新任务，已经运行的后继任务则不被中断，模块应确保清理可以与后继任务安全共存。没有检查点的函数只能在返回时响应控制请求，框架不能安全地强杀 Python 线程。只有暂停请求时函数自然返回仍应算成功；终止请求与正常返回竞态时，应以管理器首先提交的最终状态为准。

#### 队列日志与前端显示

队列日志用于情况简报框和管理页的控制台显示，应按队列分别保存最近 1000 行。任务应通过线程安全的 `ctx.log(text, level="info")` 写入所属队列，管理器应自动附加行序号（`seq`）、时间（`time`）、任务标识（`task_id`）、任务名称（`task_name`）和等级（`level`），正文保存在 `text` 中。多行输入应按行拆分，单行最多保留 16 KiB UTF-8 文本，超出应截断并标记。

日志应支持真正的 ANSI SGR 颜色序列，例如 Python 字符串 `"\x1b[31m红色文字\x1b[0m"`。前端应只解释允许的 SGR 颜色，丢弃其他控制序列，并对普通文本进行 HTML 转义。框架不应重定向整个进程的 stdout/stderr，以免并发任务的输出混在一起；未处理异常的完整堆栈应由管理器写入日志，任务卡片只显示摘要。线程输出应通过有界缓冲交给事件循环，满时丢弃日志并累计数量，恢复后补一行提示。

读取日志应调用 `await read_logs(queue_id="main", after_seq=None, limit=1000)`，返回记录列表 `entries`、下一次读取游标 `next_seq` 和是否缺失早期记录的 `truncated`。初次应返回最近记录，后续按序号增量读取。清空应调用 `await clear_logs(queue_id="main")`，移除当前保留行并返回清空边界序号。同一队列存续期间序号应单调递增，清空不能重置序号；游标落在已覆盖或清空的范围时，应返回 `truncated=true`，让前端用仍保留的记录重建显示。

队列快照 `QueueInfo` 应保存队列标识（`queue_id`）、名称（`name`）、创建时间（`created_at`）、是否主队列（`is_main`）、任务数量（`task_count`）、当前执行实例（`running_task_id`）和状态（`state`）。状态应区分空闲（idle，仅主队列可持续为空）、执行中（running）、等待调度（waiting，例如恢复后等待线程资源）和挂起（suspended，仅剩暂停或失败实例）。简报的主队列任务数应包括全部卡片，队列总数应包括主队列，执行数只应统计 running 实例，计划及其中尚未入队的定义不应计入这三项任务统计。

前端应通过 `TASK_GET_SNAPSHOT`、`TASK_READ_LOGS` 查询，通过 `TASK_PAUSE`、`TASK_RESUME`、`TASK_CANCEL`、`TASK_CLEAR_LOGS`、`TASK_SCHEDULE_UPDATE`、`TASK_SCHEDULE_DELETE` 管理现有数据。每个请求应带本连接内唯一的 `request_id`，响应命令统一为 `TASK_RESULT`，回传该标识、成功标记 `ok`，以及 `data` 或 `error: {code, message}`。第一版前端不应提交 Python 函数、任意脚本路径或远程创建任务。

状态变化应广播 `TASK_CHANGED` 并携带递增的全局修订号，提示重新获取快照；日志增量应通过 `TASK_LOGS` 发送队列标识、序号和记录，清空应广播 `TASK_LOGS_CLEARED`。前端应在连接成功时读取快照和当前查看队列的日志，缓存查询期间收到的增量，按修订号和序号去重后应用；发现缺口或重新连接时重新查询。全部客户端应管理同一份状态，清空日志也应同步到查看该队列的其他界面。推送可以合并，慢客户端应沿用框架的发送超时和断开机制，不积累无限量的通知。

#### 错误处理和服务退出

参数类型或组合不合法应返回 `TypeError` 或 `ValueError`；任务、队列、计划不存在应分别使用 `TaskNotFound`、`QueueNotFound`、`ScheduleNotFound`。不允许的状态操作、修改版本冲突、服务正在退出应分别使用 `InvalidTaskState`、`RevisionConflict`、`ServiceStopping`，这些领域错误应统一继承 `TaskAPIError`。WebSocket 适配层应将预期错误转换为 `TASK_RESULT` 响应，不因无效管理操作关闭连接，也不向客户端发送异常堆栈。

服务退出时，管理器应先停止定时触发，拒绝新建、追加、修改及恢复操作，再向全部任务发出终止请求并唤醒暂停任务。任务清理应安排在模块 `shutdown()` 之前，避免任务继续使用已经关闭的模块资源。拟定默认等待 10 秒，超时记录未退出实例；协程可以请求取消，同步线程无法安全强杀，因此该等待时间不应被视为进程退出的硬期限。仍有任务使用模块资源时，不能仅因窗口超时就直接关闭这些资源。


# 后端 back.py

## 连接与通讯

### 启动与配置

主框架支持 Python 3.8 或更新版本。`requirements.txt` 按 Python 版本选择依赖：
Python 3.8/3.9 使用 aiohttp 3.10.11，Python 3.10 及以上使用 aiohttp 3.14.3。
功能模块及其依赖的 Python 版本要求由各模块自行确定。
主框架由 aiohttp 创建应用、监听端口并处理 WebSocket 连接。

启动时读取 `backend/config/global_config.json` 的 `base-port`：

- 缺少键时补写 `8768`；文件不存在时创建包含 `base_dir: ["./"]` 的默认配置。
- 缺少整个 `http-url-config` 字段时，自动补写 `max-blob-bytes: 104857600` 和
  `tmp-blob-file: false`；已有该字段时保留原配置，不覆盖自定义值。
- 端口必须是整数且在 1～65535 范围内，不接受布尔值或字符串。
- 配置补写采用同目录临时文件和原子替换，保留其他键及原有相对路径。
- JSON 错误、回写失败、监听失败会报错并以非零状态退出，不自动换端口。
- 监听 `0.0.0.0:<base-port>`，HTTP 和 `/ws` 共用此端口，不提供前端页面。

配置加载和模块初始化在启动时发生，单纯 import back 不产生这些副作用。

### HTTP 服务信息与资源访问

| 路由 | 方法 | 用途 |
| --- | --- | --- |
| `/api/server-info` | GET、HEAD、OPTIONS | 版本、协议版本、端口、能力和资源根目录列表 |
| `/resources/{rootId}/{relativePath}` | GET、HEAD、OPTIONS | 读取允许目录内的文件 |
| `/blobs/{token}/{data_name}` | GET、HEAD、OPTIONS | 读取连接登记的临时内存数据 |
| `/ws` | GET（WebSocket 升级） | 模块命令和二进制消息 |

服务信息返回 `version`、`protocol_version`（1）、`base_port`、
`websocket_path`（`/ws`）、`capabilities` 和 `resource_roots`。
capabilities 包含 http_resources、byte_ranges、websocket 三个布尔字段；
resource_roots 是 `[{"id": "0", "name": "目录名"}]`，不包含磁盘绝对路径。
服务信息使用 `Cache-Control: no-store`。

`ResourceRegistry` 在启动时按 global_config.json 中 `base_dir` 的原始列表索引
登记有效目录。rootId 从 0 开始，以规范十进制字符串表示，例如 `0`、`1`、`12`，
不接受前导零、正负号等其他写法。不存在、不可访问或受保护的目录不登记，
但保留其编号空位，后面的索引不前移；无效或未登记的 rootId 返回 404。
文件属于多个根目录时，生成 URL 优先选择层级最深的根目录；重复目录选择最小索引。
例如 `base_dir[2]` 下的 `动画/第一集.mp4` 映射到
`/resources/2/动画/第一集.mp4`（发送时对相对路径做 URL 百分号编码，不使用 Base64）。
反向解析由 rootId 定位根目录，再拼接相对路径并执行访问校验。

映射在应用启动时建立，运行期间不随配置文件变化，重启后读取新配置。
调整列表顺序或更换某项目录可能使旧 URL 失效或指向不同文件，客户端不应将
资源 URL 作为长期文件标识。rootId 仅用于定位，不是认证凭据。

资源请求只接受登记标识和相对路径。路径只解码一次，拒绝空段、`.`、`..`、
反斜杠、冒号、控制字符及以空格或点结尾的路径段，防止 Windows 路径别名和
备用数据流访问。最终路径经过 resolve 后必须仍在对应根目录内，符号链接
及 Windows 目录联接不能通向范围外。仅提供普通文件，不列出目录。
项目自身目录、运行后端目录和全局配置文件受到保护，即使 base_dir 配置了
其上级目录也不会通过资源接口发布。默认 base_dir 为 `./` 时指向后端目录，
不会登记成可下载资源根；需要在配置中指定实际的外部资源目录。

路径检查在线程中执行，文件响应使用 aiohttp `FileResponse`。它处理 HEAD、
单段 Range（起止范围、开放尾部、后缀范围）、206、416、ETag、Last-Modified
及条件请求。文件以有界缓冲传输，不整段载入内存；原生 sendfile 不可用时
由 aiohttp 回退至分块发送。字体和常见媒体类型明确指定 MIME，其余由 aiohttp
推断。文件使用 `Cache-Control: no-cache`，允许缓存但要求再次校验。
本接口不转码、不验证视频编码；播放支持取决于客户端及文件本身。

资源缺失、目录请求或未知 rootId 返回 404；非法路径或无权限返回 403；
不支持的方法返回 405。`/`、`/MainUI.html`、`/frontend/...` 均不注册。

只读 HTTP 接口允许无凭据跨源访问，`Access-Control-Allow-Origin` 为 `*`，
可供 file:// 页面使用。OPTIONS 接受 GET/HEAD，以及 Range、If-Range、
If-None-Match、If-Modified-Since 请求头；其他预检请求返回 403。
Content-Length、Content-Range、Accept-Ranges、ETag、Last-Modified 被暴露给
客户端。aiohttp 的 on_response_prepare 在发送响应头前添加这些字段，覆盖
文件响应在 prepare 时生成的 206/304/416 和 HTTP 错误响应。
不发送 Allow-Credentials，WebSocket 不走这套 CORS 流程。

### 模块接口与连接生命周期

`ModuleManager` 按 `backend/config/module_config.json` 中的配置顺序加载启用的
模块，通过 `create_module(global_config, back_version)` 创建实例；后端版本为
`TIPHERETH 1.0.0`。返回空值表示模块不支持该版本，此时跳过加载。

传给模块回调的 websocket 参数是 `backend/back.py` 中定义的
`FrameworkConnection`。每个客户端连接对应一个稳定对象，可用作模块自己的
字典键，并提供：

- `await send(str | bytes | bytearray | memoryview)`：发送一条消息，二进制不改写。
- `await close(code=1000, reason='')`：关闭该连接。
- `closed`：连接是否已关闭。
- `resource_url(file_path)`：将登记资源目录内的文件路径转换为
  `http(s)://主机:端口/resources/...` 绝对 URL，应用同样的路径校验；不属于允许目录时抛出异常。
  协议、主机和端口取自该客户端 WebSocket 升级时的 HTTP 请求地址，不使用监听地址
  `0.0.0.0`，也不使用客户端页面的 Origin。默认不根据转发请求头推断代理外部地址。
  该方法同步访问文件系统，耗时的网络盘调用可由模块放入工作线程执行。
- `recv()` 供框架唯一业务消费者使用，模块回调不得另外读取消息。
- `blob_url(data_name, data: bytes)`：同步登记内存数据，返回绝对 HTTP(S)
  URL `/blobs/{随机标识}/{data_name}`，协议与主机来源同 `resource_url()`。名称为非空字符串，
  每次调用均创建新 URL，名称或内容相同也不覆盖。不同连接独立登记；
  URL 末段为百分号编码后的名称，不允许名称为点路径、包含路径分隔符或控制字符。
  请求中的随机标识和名称均须匹配登记内容，否则返回 404。
  名称的扩展名用于推断 MIME，未知时为 application/octet-stream。
- `delete_blob_url(blob_url: str)`：按创建时返回的完整 URL 同步删除本连接数据，返回是否存在；
  已删除、不匹配或其他连接的 URL 返回 False，非字符串参数抛出 TypeError。
  删除后旧地址返回 404，再次登记生成新地址。连接关闭或处理协程退出时清理全部登记。

blob 由应用共享的 `BLOBS_KEY`（BlobStore）登记，所有连接合计计算内存中 bytes 的总长度。
`global_config.json` 的 `http-url-config` 控制容量，缺省配置如下：

```json
"http-url-config": {
    "max-blob-bytes": 104857600,
    "tmp-blob-file": false
}
```

`max-blob-bytes` 为非负整数，默认 100 MiB；`tmp-blob-file` 为布尔值，默认 false。
启动时验证配置，修改后重启生效。未超限时数据保存在内存；新增后将超限且不允许临时文件时，
`blob_url()` 抛出 MemoryError，不登记新 URL、不改变现有资源。
允许临时文件时，按所有连接合并后的创建顺序，从最早仍驻留内存的 blob 开始，
逐个写入 `backend/classify_shower/temp/http-blob-*.bin`，直到内存能容纳新数据。
读取不改变该顺序，已转存的数据跳过；转存后原 URL、名称和 MIME 不变。
单个新 blob 大于限额时直接写入临时文件，不强制转存旧数据；限额为 0 时非空数据均需落盘。
临时文件写入失败则抛出 OSError，新 URL 不登记；此前成功转存的旧数据继续有效，
当前转存失败的数据仍保留在内存中。

该限额统计登记表持有的内存数据，不包括调用方仍持有的 bytes、正在发送的响应及对象开销，
不是进程总内存上限。blob_url() 保持同步，转存涉及同步磁盘写入，应避免频繁登记大块数据。
显式删除、断线及正常服务退出时同时释放内存和相应临时文件，不删除 temp 下其他文件。
强制终止进程可能遗留临时文件，当前不会在启动时扫描删除历史文件，也未限制磁盘总用量。
HTTP 支持 GET/HEAD、跨源 OPTIONS，使用 no-store；内存响应不实现 Range，
落盘响应由 FileResponse 提供 Range，调用方不应依赖 blob 一定支持 Range。
已有响应不会因删除而撤回。方法须在框架事件循环中调用，关闭的连接不能再登记资源。
持有 URL 即可读取数据，不检查下载者是否为创建该资源的 WebSocket 客户端。

先发送 `BACKEND_VERSION`（`version` 为支持的前端版本列表），然后发送
`SET_NOWPATH`，再按模块配置顺序调用 `when_connect(connection)`；
每条 JSON 对象按顺序调用 `message_proc(connection, data)`。上行消息须为
JSON 对象文本；下行 HSV1 由模块构造，适配层原样发送，前端负责解析和分发。

运行时的资源根目录相对于 backend 目录解析为绝对路径，不存在的路径记录
警告并跳过。有效路径通过 `SET_NOWPATH` 发送到前端，不回写这些绝对路径。

### 并发收发与连接限制

网络读取任务独立于业务分发任务，业务 await 时仍能处理 Ping/Pong、断线。
每连接最多排队 32 条上行消息，单条上限 1 MiB；超限或非法数据关闭该连接。
心跳参数为 30 秒，使用 aiohttp 的 Ping/Pong 与超时检测；关闭握手超时设为 5 秒。
发送使用每连接锁及 aiohttp 64 KiB 写缓冲水位（不是消息大小上限），等待锁
和发送合计超过 30 秒时关闭慢连接；适配层不另建无界输出队列。

不同连接具有各自的读取任务、分发任务、接收队列和发送锁；同一连接的消息
由单个业务消费者依次处理。模块实例由所有连接共享，框架不改变模块内部
状态的归属，也不替模块实现业务并发控制。模块中的同步阻塞操作仍会阻塞
共用的事件循环。

| 异常情况 | 关闭码 |
| --- | --- |
| 上行文本不是合法 JSON 对象 | 1007 |
| 上行消息为二进制 | 1003 |
| 上行消息超过大小限制 | 1009 |
| 接收队列已满或发送超时 | 1013 |
| 模块连接或消息回调发生未处理的普通异常（ConnectionError 除外） | 1011 |
| 服务停止 | 1001 |

### 断线与服务退出

网络读取或业务分发任务结束时，框架取消该连接其余未完成的任务，然后按
模块顺序调用一次 `when_disconnect(connection)`，关闭连接并移除连接登记。
每个断线回调使用 5 秒超时，失败会记录日志并继续清理其他模块。

服务停止时拒绝新的 WebSocket 连接，关闭已登记连接并等待其清理完成，随后
按模块顺序调用可选的 `shutdown()`。每个 shutdown 使用 10 秒超时，单个模块
失败不阻止其他模块清理。协程超时依赖模块响应取消请求。
