# 模块化设计思路的编写

风格参考：[模块化设计思路.md](../总设计文档/模块化设计思路.md)。尤其参考用户将全局事件说明融入“功能模块的前端部分”和“MainUI.html 带有的接口”的写法，以及它与[全局事件.md](../总设计文档/全局事件.md)之间的内容分工。本技能用于维护框架的模块化设计说明，不把功能开发记录的写法直接套入总设计文档。

## 内容放在所属章节

修改前先阅读目标文档的章节结构、相关段落及相邻内容。新增机制应按它在框架中的职责放入已有章节：模块如何接入框架放在模块部分，框架提供的调用接口放在接口部分，调用先后放在回调顺序部分。一个机制可以分别补充到几个相关位置，不必为了集中介绍它而在文末另建一套说明。

优先续写现有列表、补充现有段落。只有现有章节确实不能容纳独立主题时才新增章节。避免同一签名、注册方式和生命周期规则在多个章节重复解释；整理已有的重复章节时，先将仍需保留的内容归入适当位置，再移除重复说明。

一组接口围绕同一个对象工作时，可以在所属部分增加简短的“关于……”概念小节，说明对象是什么、由哪些部分组成，以及为什么提供这组公共接口。接口条目介绍操作，概念小节介绍共同背景，两者不重复。例如“关于菜单栏”先定义基础页面菜单与外加按钮列表，再说明布局模块提供接口是为了统一各功能模块菜单栏的外观。不要把“避免重复章节”理解成不能增加必要的概念说明。

在接口首次引用概念或接口集的位置就提供页内链接，例如 `new_page()` 链接到“关于页面管理栈”，菜单栏接口集的起始条目链接到“关于菜单栏”。关联的一组接口可以注明编号范围，但之后增删条目时必须同步维护。标题采用简洁的概念名称，修改标题后核对锚点，不照搬旧标题的尾部标点。

例如，新增 `event_handler_list` 时，在其他处理函数列表的说明后接着写它的函数形式和参数含义；在原有“框架遍历列表、模块加入函数”的段落中补充事件触发与清理要求；在接口章节介绍 `frame_dispatch_event`。不要另在文末追加一个重复上述内容的“全局事件处理标准”。

## 从模块使用者的角度解释

先说明框架提供什么、模块应怎样使用，再补充正确使用所需的约定。介绍处理函数时给出函数形式，并紧接着解释参数类型、用途和含义由谁规定。介绍接口时将签名与动作放在一起，用一两句话说明它对哪些对象做什么。

将形参名直接对应到操作对象，说明对象的来源和包含关系，避免只写泛称。例如写“向 `createBackButtons` 返回的菜单栏 `menuBar` 的外加按钮列表里索引 `index` 对应的位置插入 HTML 元素 `button`”，而不只写“向菜单栏指定位置插入元素”。描述索引时说清是哪一个对象、哪一个列表的索引；描述返回值时说清是新建、插入还是被移除的那个元素。

区分创建对象、插入页面与返回对象这几个动作，接口实际完成哪些就说明哪些。按钮名称优先使用界面上的完整含义，如“返回上一页”“回首页”。描述行为以语义为准，不用实现中的经验数值冒充保证：例如“回首页”应说明弹出所有可弹出的页面，而不能仅用 `pop_page(256)` 代替这个语义。学习修订时不据此自动修改代码；需要核实实现是否符合设计时另行确认。

沿用相邻内容的编号和行内代码格式。例如：

> `event_handler_list` 里的函数形如 `function(event, wParam, lParam)`，`event` 为一字符串，是事件名称。`wParam`、`lParam` 都是事件的参数，具体含义取决于具体事件。

> `frame_dispatch_event(event, wParam, lParam)`：广播一个事件 `event`。`wParam`、`lParam` 是填入此事件的参数。即是以这个事件和参数调用一遍 `event_handler_list` 里的函数。

使用直接的中文叙述，例如“往这些列表里加入自己的函数”“调用一遍……里的函数”。抽象名称之后可以用“即是……”解释具体动作，让读者知道调用会产生什么结果，不堆叠术语，也不机械模仿固定句式。函数名、参数名、文件名和列表名保留准确拼写并使用行内代码。

相关的使用责任放在一起说明。若页面向框架列表注册函数，就在注册说明附近交代页面需要通过 `cleanFuncList` 移除函数，不让读者到另一节寻找配套的清理要求。涉及其他资源时按实际生命周期说明，不把这一具体清理方式推广到所有对象。

## 总体机制与专项定义分开维护

总设计文档说明通用机制及模块的接入方法；具体事件名称、各事件参数、触发条件等放在全局事件文档中。正文在读者需要具体定义的位置给出相对链接，能定位到对应标题时优先链接该标题，例如 `[预定义的事件](全局事件.md#预定义的事件)`（此路径用于总设计文档内）。不要在主文档复制一份完整事件表或参数说明。

选择细节以读者能否正确编写模块为准。接口约束、必要的调用顺序、默认值、失败行为及资源释放要求有助于正确使用时应保留；内部遍历实现、异常捕获方式等细节不必仅因代码中存在就逐项写入总说明。若属于必须遵守的公共约定，则在所属章节或专项文档中准确说明。

不要在接口列表之后机械附加一段集中罗列错误类型、重复登记检查、加载顺序和通用清理要求的文字。已经在其他位置说明的内容用链接衔接；特定操作的重要后果则留在该接口条目内，例如移除按钮仍保留监听器，调用方可以重新使用该元素。用户删去一段校验细节，不代表所有接口都不应说明失败行为，应判断该细节是否属于本节需要表达的使用约定。

新增公共接口时，同时检查文档后面的“功能模块中可以使用的接口、预定义全局变量”等面向调用方的清单。定义处保留完整说明，清单处列出签名并链接回定义处；同步更新编号及“接口 2-16”这类引用范围。只更新实现方的接口定义而漏掉调用方清单，会使文档给出不完整的可用接口范围。

简明不等于删除全部细节。已有的资源路径示例、数据结构、调用流程等若承担解释作用，应继续保留。不要将这次事件章节的精简理解为所有章节都只能写成短接口列表。

## 保持设计文档的稳定表述

正文描述最终设计和当前可用的机制，不记录“这次新增”“之前方案”“下一步准备”等对话或开发过程。某个业务功能尚未接入事件系统之类的进度信息，不附在框架通用接口说明末尾；需要记录时放到相应功能文档。

从用户修订中提炼组织方式、解释顺序和详略取舍，不把偶然的空格、标点或特定事件参数固定成通用规则。学习写作风格本身不意味着修改接口行为；更新设计内容时，参数、默认值和执行顺序仍须依据确认后的设计与实际实现核对。

完成后通读修改处：新增内容是否归入所属章节，是否重复已有说明，读者是否能找到签名、参数含义及接入和清理方式，专项链接是否有效，是否夹带开发进度或不影响使用的实现细节。保持用户未要求修改的内容和文档范围。

再检查参数对象从哪里取得、索引属于哪个列表、操作是否改变 DOM 归属、返回的是哪个对象；概念小节是否解释了组成和目的，接口定义与调用方清单是否一致。保留接口条目内必要的分段，让返回值或接口集链接独立成段时仍明确属于该条目，不机械复制空格或缩进。
