## 保存某视频剧集上一次观看到的位置

`CS_VIDEO_DATA` 响应命令下有`auto-seek-time`键，值为用户上次观看到什么时间点。

剧集元数据目录位于视频同级，命名为 `<完整视频文件名（含扩展名）>@meta/`。例如，`xxx.mp4` 对应 `xxx.mp4@meta/`，`xxx.ts` 对应 `xxx.ts@meta/`，观看记录和评论阅读记录分别保存在各自的目录内。

该值通过读取剧集元数据目录下的文件 `__RECORD__.json`（例如 `xxx.mp4@meta/__RECORD__.json`）的内容，尝试读取`video-time`键值作为`auto-seek-time`键值，若读取失败设为0。文件`__RECORD__.json` 的内容参考示例：

```json
{
    "view-time":1778569079,
    "video-time":1708.0
}
```

然后前端部分使用`auto-seek-time`键值来初始化播放器，`new NPlayer.Player()`传入的json参数相关文档：

> “...... autoSeekTime	视频加载成功时自动跳转到的时间点（跳转后该参数会自动设为 0），你可以用这个参数实现记忆上次用户观看时间......”

然后在退出播放器页面调用的清理函数里加上通知后端保存目前观看记录的函数。new NPlayer.Player()建立的对象所拥有的属性的文档：

> ”
> ......
> currentTime: number \[get/set]#
> 获取和设置当前视频时间。\[get/set] 表示该属性可以同时被获取和设置新的值。
> “

这个保存方法除了要更新`__RECORD__.json`，还要创建或更新目录下的`__HISTORY__`文件，该文件(json)格式要记录最后一次用户访问该番剧(等视频集合)观看的是第几集(“order”键)、这个对应的视频文件相对地址、当前时间戳、以及当前视频时间。

所以后端的数据库番剧表的每一条番剧除了现有的这些项外还要加上最后一次用户访问该番剧观看的是第几集、上一次访问时间，以及看到的视频时间，这些数据通过扫描`__HISTORY__`文件得到。除此之外再加上“是否有弹幕”这一项，只要番剧的这些剧集里有一集是有弹幕的（即dm\_dir下“rmcf.json”存在）那就算这个番剧有弹幕。

## 弹幕重映射功能

弹幕重映射用于解决在视频播放时，弹幕来源的时间轴与本地视频时间不一致导致弹幕发送时机错位的问题。

### 读取并执行逻辑

`CS_VIDEO_DATA` 响应命令下有 `has-danmaku` 和 `danmaku-data` 两个键，分别表示本次是否成功生成弹幕配置，以及交给前端弹幕插件使用的数据。前端发送 `GET_CS_VIDEO_DATA` 请求后，后端根据 `rootPath` 和 `videoPath` 找到视频同级的 `<完整视频文件名（含扩展名）>@meta/` 目录，例如 `xxx.mp4@meta/`，尝试读取其中的 `rmcf.json` 文件，然后将读出的配置列表和这个目录传给 `backend/classify_shower_back.py` 里的 `make_danmaku_data(remap_config_list, dm_dir)` 方法。

文件 `rmcf.json` 的内容是一个列表，每一项指定一个弹幕源文件及其时间重映射方式，可以给同一个文件设置多项配置。内容参考示例：

```json
[
    {
        "dmsrc-file": "dm1.json",
        "time_filter": [[10, 30], [50, 70]],
        "cut_time": 5,
        "add_time": [[20, 25], [40, 50]],
    }
]
```
其中 `time_filter` 、`cut_time` 、`add_time` 这三个键值决定了该弹幕源的弹幕完整的重映射方式。在设计中这三个参数的具体含义如下：

1. `time_filter`：**弹幕筛选器**。主要具有按时间段筛选弹幕、自动将范围内的最早弹幕时间对齐到该视频(本地的要往其上加这个来源弹幕的视频，即目标视频，后续不再赘述) 0s 处这两个功能。示例中值为 `[[10, 30], [50, 70]]`，给出了10-30秒、第50-70秒这两个范围，不在范围里的弹幕会被过滤掉，然后把所有弹幕时间减去10，也就是将第10秒的弹幕移到第0秒。

    例如有6个弹幕的时间分别为 `[10, 20, 30, 40, 50, 60]`，经过 `time_filter` 后会变成 `[0, 10, 20, 40, 50]`。

    如果不希望将选择器选择范围的最早时间对齐到 0，那就额外加入一个负值范围，例如 `[-1,-1]`，这样 `[10, 20, 30, 40, 50, 60]` -> `[10, 20, 30, 50, 60]`。

    如果其中的时间范围有交集，例如 `[10, 30]` 和 `[20, 40]`，那么筛选器采取并集策略，即这两个范围实际上与 `[10, 40]` 等效。

    若 `time_filter` 为空列表，既不筛选也不移动时间起点。

2. `cut_time`：**多余片头时间**。即是网上的弹幕源视频相较目标视频在开头多出一部分片段，这部分片段的长度，单位为秒。例如同样一幅画面，在目标视频里是第0秒，在弹幕源视频里是第x秒，然后这是由于弹幕源视频多了x秒的开头，那么 `cut_time` 就是x。在目标视频里不存在的这x秒开头内的弹幕将通过抛物线映射到目标视频的开头 `[0,x/4]` 秒的区间内，然后目标视频的前x秒即原弹幕 `[x,2x]` 秒的区间内的弹幕将会通过抛物线映射被挤压到目标视频的 `[x/4,x]` 秒的区间内。

    假设某个弹幕在弹幕源视频里 $t$ 秒出现，那么其在目标视频里出现的时间 $T$ 将为:

    $$
    T =
    \begin{cases}
    \dfrac{t^2}{4x}, & t < 2x \\[6pt]
    t - x, & t \ge 2x
    \end{cases}
    $$

3. `add_time`：**空白段**。即是在连续的弹幕源列表中插入一些没有弹幕的空白时间段，原先在这些时间里以及该段时间之后的弹幕会被相应延迟，常用于弹幕源视频相较目标视频有删减的情况。

    示例中值为 `[[20, 25], [40, 50]]`，如果目标视频的第20-25秒、第40-50秒这两段被删掉了，剩下的视频段依次拼接后与弹幕源视频可以一一对应，那么这时应用该空白段后为视频添加此来源弹幕，弹幕与视频内容的对应关系将仍然是正确的。目标视频的第20-25秒、第40-50秒这两段不会出现此来源的弹幕，因为这两段在弹幕源视频里被删掉了。

以上重映射逻辑的具体实现在 `backend/classify_shower_back.py` 里的 `make_danmaku_data` 方法。以下是具体的实现逻辑：

1. 首先，后端读取文件 `rmcf.json` ，将 `dmsrc-file` 和元数据目录拼接得到弹幕源文件地址，例如 `xxx.mp4@meta/dm1.json`，以 UTF-8 编码读取该文件中的 JSON 弹幕列表。源文件不存在时输出错误信息并跳过这一项，继续处理后面的配置。每条弹幕通过 `time` 键记录播放时间，单位为秒；该值缺失或为 `null` 时补为0，可以转换成数字的值按浮点数处理，转换时发生 `ValueError` 或 `TypeError` 则按0处理。

2. 然后该方法的子函数 `apply_time_filter` 根据 `rmcf.json` 里 `time_filter` 的键值筛选需要的弹幕，该键缺省为空列表，即不筛选也不移动时间起点。如果设置了若干个 `[开始时间, 结束时间]` 区间，只保留原始时间落在任意区间内的弹幕，包含区间的两个端点；同一条弹幕即使落在多个区间内也只保留一次。同时把所有区间中最小的开始时间作为统一起点，从保留下来的弹幕时间里减去这个起点。例如上面的配置会把原始第10秒、第30秒、第50秒的弹幕分别移到第0秒、第20秒、第40秒，两个区间之间的空档仍然保留，不会把各个区间首尾拼接起来。

3. 筛选后的弹幕先按时间升序排列，再逐条使用 `apply_remap` 子函数应用 `cut_time` 和 `add_time`。先执行多余片头时间的抛物映射，将小于 `2 * cut_time` 的时间改成 `time * time / (4 * cut_time)`，其余时间再减去 `cut_time`。

    接下来执行 `add_time`，该键缺省为空列表。后端先把其中的 `[start, end]` 区间按 `start` 升序排列，再依次比较已经变换过的弹幕时间；只有当前时间严格大于 `start` 时，才增加 `end - start` 秒，等于 `start` 时不移动。每一次增加后的结果继续参与下一个区间的判断。例如上面的配置中，原始第50秒的弹幕筛选后变为40秒，裁剪后变为35秒，经过 `[20, 25]` 后变为40秒，因等于下一个区间的起点而不再增加；原始第51秒的弹幕则依次变为41秒、36秒、41秒、51秒。这些时间变换只更新弹幕的 `time` 字段，正文、来源等其他字段沿用原始内容。

### 生成 `dm-info.json` 并发送

`dm-info.json` 用于保存本视频所有弹幕来源的一些基本信息，内容参考示例：

```json
{
    "dm-src": [
        {
            "name": "B站",
            "url": "",
            "update-time": 1784354475,
            "dm-count": 3064
        },
        {
            "name": "B站",
            "url": "",
            "update-time": 1784743053,
            "dm-count": 5576
        },
        {
            "name": "B站",
            "url": "",
            "update-time": 1784731059,
            "dm-count": 1796
        }
    ],
    "dmjs-build-time": 1788278078,
    "dm-count": 12953
}
```

其中 `dm-src` 键保存所有弹幕来源的来源名称(`name`键)、URL(`url`键)、更新时间(`update-time`键)、弹幕数量(`dm-count`键)等信息。这些信息是在每个弹幕数据文件经重映射处理完后，调用`make_danmaku_data` 方法的子函数 `get_source_info` 从重映射完成的这个弹幕数据文件弹幕列表里统计出每个来源的相关信息得到的。在此之后将该文件重映射完的弹幕列表并入总输出弹幕列表。

关于子函数 `get_source_info`，它的实现逻辑是统计列表中每条弹幕的 `src` 键，将同一src划为一个来源，不同src划为不同来源。对每个来源的 `src` 键值作为来源名称(`name`键)，缺少 `src` 时使用“未知”，并统计该来源的弹幕数量填入`dm-count`键。然后 `url` 当前恒为空字符串(保留)，`update-time` 取该来源弹幕最大的 `send-time` 值（缺少 `send-time` 时按0）。

所有的弹幕数据文件执行完这一套逻辑后，再把总输出弹幕列表按变换后的时间升序排列，并创建或覆盖元数据目录下的 `dm-info.json`。将每个弹幕数据文件重映射并 `get_source_info` 获取到的列表简单合并，填入 `dm-src` 字段，`dmjs-build-time` 键保存本次生成时的整数时间戳，`dm-count` 键保存合并后的弹幕总数。重映射后的弹幕列表不写入磁盘。

最后从后端配置的 `video-config.danmaku-config` 中取得 `speed`、`fontsizeScale`、`area`，连同保存总弹幕列表的 `items` 键组成返回值，作为 `CS_VIDEO_DATA` 的 `danmaku-data`。整个 `danmaku-config` 缺失时这三个值分别为0.75、1.0、0.75；如果该字典已经存在但缺少某个键，逐键回退值分别为0.75、16、0.75。前端 `CS_VideoPlayerWidget` 收到响应后保存这份数据，在启用弹幕且插件可用时传给 `new NPlayerDanmaku(this.danmakuData)`，用于初始化播放器的弹幕插件。

如果 `rmcf.json` 不存在，或者读取配置、处理源数据、写入信息文件的过程中抛出异常，调用方会保持 `has-danmaku` 为 `false`、`danmaku-data` 为空列表；异常时同时输出失败日志。只有 `make_danmaku_data()` 正常返回后才把 `has-danmaku` 设为 `true`，因此配置列表为空、所有源文件都被跳过或筛选结果为空时，只要后续写入等步骤成功，该值仍会是 `true`，不代表弹幕数量一定大于0。

## 添加播放其他格式容器视频的支持

这里的“支持其他格式容器”不是把整个视频预先转换成一个临时文件，也不是在前端直接解析 TS、MKV、AVI 等容器，而是采用“后端 FFmpeg 实时重封装为 fragmented MP4（fMP4）→ Python 从 stdout 管道读取 → 仍通过原 WebSocket 发送二进制数据 → 前端 MediaSource/SourceBuffer 喂给 CS\_VideoPlayerWidget.player.video(即是MSE接口，而 CS\_VideoPlayerWidget.player 是nPlayer对象实例，video成员为HTMLElement)”的方式实现。

这个功能的预期实际效果为，如果各种格式的视频浏览器不直接支持，但是其中的视频流编码在浏览器支持时，直接提取流传递给浏览器播放。然后如果是不支持的视频流(像是DivX，Xvid)，那么不再向前端发送二进制数据，而是向前端发送对应信息，然后前端直接显示“不支持该视频的视频编码格式”；如果视频流支持，但是音频流不支持(像amr)那么就实时转码音频流到aac并和视频流一起向前端发送。

需要特别说明：本功能最初的主体代码是在项目执行 git init 之前完成的。后面的 c3b62c2 是把当时已经存在的工作区整理并纳入首次 Git 提交，不是从该提交才开始实现视频重封装。Git 初始化前已经按照上面的5点要求，完成了 MainUI.html 的 WebSocket 二进制入口、frontend/classify\_shower\_video.js 的 MediaSource 播放器、backend/classify\_shower\_back.py 的 FFmpeg 管道和流会话管理，以及 FFmpeg 配置读取。后续 Git 提交是在这个第一版基础上根据实际03.ts测试逐步修正兼容性、卡顿、Seek、同步、懒加载和回收问题。本项目就是在添加这个功能的时候首次引入了git作为源代码管理工具。

根据 视频格式容器重封装思路.txt 作为思路：

### 1.二进制比特流仍然使用websocket传输 (MainUI.html 和 backend/classify\_shower\_back.py)

MainUI.html 在全局事件列表区域增加 binary\_message\_proc\_func\_list，WebSocket 建立后设置 ws.binaryType='arraybuffer'。messageProc(event) 在原 JSON 消息处理之前增加二进制分支，兼容 ArrayBuffer 和 Blob。第一版就定义了 HSV1 封包：4字节魔数、4字节 JSON 头长度、JSON 头、媒体 payload。JSON 头至少带 type、streamId、widgetId、sequence，前端拆包后依次把 header 和 payload 传参给 binary\_message\_proc\_func\_list 里注册的函数。这样没有改变原有 JSON 命令的 WebSocket，也没有再监听一个新端口；控制命令、番剧数据、弹幕数据和视频二进制都在同一个连接上传输。

backend/classify\_shower\_back.py 第一版增加 struct、subprocess、uuid、asyncio 等依赖，并实现 pack\_video\_chunk()。pack\_video\_chunk() 把 FFmpeg stdout 读到的 bytes 和 streamId、widgetId、sequence 一起封装为 HSV1 消息，然后直接 await websocket.send(binary\_message)。streamId 在每次 START/SEEK 时用 uuid.uuid4().hex 生成，目的是让前端识别某个二进制块属于哪一次流请求；widgetId 用来区分同一连接上的播放器实例；sequence 用来表示块顺序。

### 2.接受媒体流的video元素是CS\_VideoPlayerWidget.player.video (于 frontend/classify\_shower\_video.js 的 CS\_VideoPlayerWidget)

第一版在构造函数中加入 mediaSource、sourceBuffer、streamObjectUrl、activeStreamId、streamQueue、streamEnded、streamStartTime、streamDuration、streamSeekTimer、streamSeekingHandler、restartingStream、resumeAfterStreamOpen 等成员。render() 注册 VIDEO\_STREAM\_READY、VIDEO\_STREAM\_ENDED、VIDEO\_STREAM\_ERROR 文本消息和 VIDEO\_STREAM\_CHUNK 二进制消息处理函数 (详见 《通信协议.md》 中“后端 → 前端响应”的第7点)，并在播放页 cleanFuncList 中注册移除这些 handler 函数的函数。

initPlayer() 仍然先创建并 mount NPlayer。对于需要重封装的视频，NPlayer 初始化时不再直接使用 TS/AVI/MKV 文件 URL，player.mount() 执行完成后调用 setupRemuxStream()；setupRemuxStream() 通过 const video = this.player && this.player.video 取得 NPlayer 内部真实的 HTMLVideoElement，后续 MediaSource Object URL、currentTime、buffered、play()、pause() 和 seeking 事件都直接作用于这个 video。因此媒体流的最终接收者确实是 CS\_VideoPlayerWidget.player.video，而不是另建一个脱离 NPlayer 的 video 标签。

openRemuxMediaSource() 在第一版中已经负责 new MediaSource()、URL.createObjectURL(mediaSource) 并设置 video.src。它等待 sourceopen 后才向后端发流请求。VIDEO\_STREAM\_READY 返回后，handleVideoStreamReady() 根据 mimeType 创建 SourceBuffer，设置 mode='segments' 和 timestampOffset，把后端二进制 payload 排队 appendBuffer；updateend 后继续写下一块。后端返回 duration 时设置 mediaSource.duration，从而让 NPlayer 显示整部视频总时长；收到 VIDEO\_STREAM\_ENDED 且队列清空后调用 mediaSource.endOfStream()。

### 3.CS\_VideoPlayerWidget.initPlayer()在创建播放器时候如果发现文件后缀不为.mp4和webm这类原生支持格式，这时才向后端发送请求，后端重新封装并实时向前端发送对应时间所在的那一段视频流。(在 frontend/classify\_shower\_video.js 的 isNativeVideo() 和 initPlayer())

isNativeVideo(path) 读取文件扩展名并转成小写，第一版把 mp4、m4v、webm、ogv、ogg 视为浏览器原生播放格式。initPlayer() 使用这个结果决定 videoPath：原生格式继续调用 getVideoUrl()，直接交给 NPlayer/浏览器；非原生格式把 NPlayer 的初始视频地址留空，在 mount 后执行 setupRemuxStream(autoSeekTime || 0)，发送 START\_VIDEO\_STREAM。也就是说，原有 MP4/WebM 播放路径没有经过 FFmpeg，不会给所有视频额外增加后端进程；只有 TS、MKV、AVI 等容器才进入重封装链路。

后端的 START\_VIDEO\_STREAM 由 ClassifyShowerModule.message\_proc() 分派到 start\_video\_stream()。start\_video\_stream() 第一版先 cancel\_video\_stream(websocket, widgetId)，保证同一播放器旧流被替换；然后解析 rootPath/videoPath，读取 FFmpeg 路径，探测 duration、videoCodec、audioCodec 和 MSE MIME；向前端发 VIDEO\_STREAM\_READY；最后建立 session 并用 asyncio.create\_task() 后台运行 stream\_ffmpeg\_output()。长时间读取 FFmpeg 管道不会把 WebSocket 的其他命令处理永久堵住。

### 4.要考虑用户拖动视频进度条的情况。(于 setupRemuxStream()、openRemuxMediaSource() 和后端 START/SEEK 共用入口)

setupRemuxStream() 给 player.video 注册 seeking 监听。用户改变 currentTime 时，代码先判断当前是否正处于流重启，以及目标时间是否已经在 video.buffered 中；已缓冲位置由浏览器直接完成 Seek。未缓冲位置读取 video.currentTime 作为 seekTime，使用180毫秒 setTimeout 防抖，随后调用 openRemuxMediaSource(seekTime, 'SEEK\_VIDEO\_STREAM')。防抖用于避免用户按住进度条拖动时每一个细小位置变化都向后端创建 FFmpeg。

SEEK\_VIDEO\_STREAM 和 START\_VIDEO\_STREAM 在后端都进入 start\_video\_stream()。后端先取消相同 widgetId 的旧 Task/FFmpeg，再把 startTime 放在 FFmpeg 输入参数 -ss 中，从该时间附近重新输出一条 fMP4 流。前端为 Seek 创建新的 MediaSource、SourceBuffer 和 streamId 状态，旧流迟到的二进制块因为 streamId 不相等被忽略。第一版还通过 SourceBuffer.timestampOffset=streamStartTime，把中途生成的片段放回整部视频的时间轴，并在首段可用后设置 player.video.currentTime=streamStartTime；如果 Seek 前视频正在播放，则通过 resumeAfterStreamOpen 记住状态，缓冲建立后自动恢复播放。

退出播放页和切换剧集在第一版中也已调用 disposeRemuxStream()。该函数清除 Seek 定时器和 seeking 监听，发送 CANCEL\_VIDEO\_STREAM，abort 正在更新的 SourceBuffer，结束 MediaSource，撤销 Object URL，并清空流ID和队列。switchEpisode() 在销毁旧 NPlayer 和请求新剧集前先执行该清理，因此换集不会让上一集继续占用 FFmpeg。

### 5.后端与ffmpeg.exe交互，使用管道传输转换后的二进制流到python (于 get\_ffmpeg\_path()、probe\_video() 和 stream\_ffmpeg\_output())

读取 backend/config/classify\_shower\_config.json 中 video-config.ffmpeg-path 键值作为本机 FFmpeg.exe 地址；对应 example 配置也提供该字段。get\_ffmpeg\_path() 每次启动流时读取这个键，执行 expandvars/expanduser，并检查文件存在，不在 Python 代码中写死 C盘工具目录。真实 classify\_shower\_config.json 是机器本地配置，Git 初始化时被 .gitignore 排除，仓库只保留 example。

probe\_video() 第一版通过 subprocess.run(\[ffmpeg\_path, '-hide\_banner', '-i', video\_path]) 进行短时探测，从 stderr 中解析 Duration、Video 和 Audio，建立 codec 到 RFC 6381/MSE MIME 的映射，再把 duration、videoCodec、audioCodec、mimeType 返回给 start\_video\_stream()。该探测放入 run\_in\_executor，避免同步 subprocess.run 阻塞 asyncio WebSocket 循环。

stream\_ffmpeg\_output() 第一版使用 asyncio.create\_subprocess\_exec() 启动 FFmpeg，stdin=DEVNULL、stdout=PIPE、stderr=PIPE，Windows 下带 CREATE\_NO\_WINDOW。初始命令开头带有按真实速度读取的 -re，随后包含 -ss、-i、-map 0:v:0、-map 0:a:0?、-sn、-dn、-c copy、-avoid\_negative\_ts make\_zero、frag\_keyframe+empty\_moov+default\_base\_moof、-frag\_duration 2000000、-f mp4、pipe:1。这里的 -c copy 表示第一版只做容器重封装，不重新编码视频和音频；pipe:1 表示 fMP4 从 FFmpeg 标准输出直接进入 Python内存，不生成中间 MP4 文件。后续真实播放发现 -re 会让预缓冲也只能按1倍速增长，才在后面的性能优化中移除。

第一版为 stderr 建立独立 collect\_stderr() 任务，防止错误输出管道填满后卡住 FFmpeg；主任务循环 await process.stdout.read(256\*1024)，每读到一块就 pack\_video\_chunk() 后通过 WebSocket 发送。FFmpeg 返回0时发送 VIDEO\_STREAM\_ENDED，非0或 Python 异常时发送 VIDEO\_STREAM\_ERROR。cancel\_video\_stream()、when\_disconnect() 和 Task finally 会终止进程、取消 stderr 任务，并把 session 从 video\_streams 删除。

### 一、WebSocket 二进制传输总入口

MainUI.html 12 行附近增加 binary\_message\_proc\_func\_list，作用与原先处理 JSON 消息的 message\_proc\_func\_list 类似，但专门保存二进制消息处理函数。

MainUI.html 231 行附近将 WebSocket 的 binaryType 设为 arraybuffer。MainUI.html 287-312 行附近的 messageProc(event) 现在会先判断 event.data 是否为 ArrayBuffer 或 Blob：如果是二进制消息，就不再尝试 JSON.parse 整条消息，而是按自定义包格式拆包；如果是文本消息，仍走原有 JSON 命令分发逻辑，因此番剧分页、详情、弹幕和观看记录等旧协议不受影响。

二进制包格式为：前4字节固定魔数 HSV1（数值0x48535631），接下来4字节是大端序 JSON 头长度，然后是 UTF-8 JSON 头，剩余内容才是真正的 fMP4 数据。JSON 头里包含 type=VIDEO\_STREAM\_CHUNK、streamId、widgetId、sequence 和 segmentType。MainUI.html 会检查魔数、头长度和消息完整性，然后把 header 与 payload 分开，依次调用 binary\_message\_proc\_func\_list 中的处理函数。

这里没有为视频另开第二条 WebSocket，控制消息和媒体二进制块仍共用 ws\://localhost:8768。widgetId 用于把消息交给正确的播放器组件，streamId 用于区分同一个播放器前后创建的不同流，sequence 表示当前流内的分段顺序；即使旧 FFmpeg 流取消后还有迟到的数据，前端也会因为 streamId 不一致而丢弃，不会写入新流的 SourceBuffer。

### 二、`CS_VideoPlayerWidget` 前端播放流程

frontend/classify\_shower\_video.js 1126 行开始的 CS\_VideoPlayerWidget 构造函数增加了整套流播放状态，包括 messageHandler、binaryMessageHandler、mediaSource、sourceBuffer、streamObjectUrl、activeStreamId、streamQueue、currentStreamSegment、streamStartTime、streamDuration、Seek 定时器、预缓冲参数、水位参数和错误状态等。每个播放器实例仍使用自己唯一的 widgetId，因此同一连接上不同组件的消息不会串流。

frontend/classify\_shower\_video.js 1230 行附近的 binaryMessageHandler 只接收同时满足以下条件的消息：type 为 VIDEO\_STREAM\_CHUNK、widgetId 等于当前组件、streamId 等于 activeStreamId，并且当前流没有进入失败状态。收到的数据不是立刻无条件 appendBuffer，而是连同 sequence 和 segmentType 放进 streamQueue，再由 appendNextStreamChunk() 串行写入。这样避免在 SourceBuffer.updating 为 true 时并发 appendBuffer，也能在报错日志里指出失败的是 init 分段还是 media 分段、序号和字节数。

frontend/classify\_shower\_video.js 1560 行附近的 initPlayer() 会先通过 isNativeVideo() 判断扩展名。mp4、m4v、webm、ogv、ogg 继续沿用 NPlayer/浏览器的原生 URL 播放；TS、MKV、AVI 等非原生容器初始化 NPlayer 时不再直接给一个浏览器无法识别的 src，而是在 player.mount() 后调用 setupRemuxStream()。真正接收媒体数据的 video 元素就是 this.player.video，即 CS\_VideoPlayerWidget.player.video。

setupRemuxStream() 位于 frontend/classify\_shower\_video.js 1662 行附近。这里检查 window\.MediaSource 是否存在，并在 player.video 上注册 seeking、play、timeupdate、waiting 四类事件。首次打开使用 START\_VIDEO\_STREAM；用户拖到当前 MSE 缓冲区之外时，在180毫秒防抖后使用 SEEK\_VIDEO\_STREAM，避免拖动过程中连续创建大量请求；如果目标时间本来就在已缓冲范围内，则让浏览器直接 Seek，不重新启动后端流。流已失败时也不再响应 seeking，避免不支持编码的视频反复重试。

openRemuxMediaSource() 位于1704行附近。每次首次播放或非缓冲区 Seek 都会清空旧队列和旧状态、释放旧 MediaSource，创建新的 MediaSource 和 Object URL，再把这个 Object URL 设置给 player.video.src。必须等待 MediaSource 的 sourceopen 事件后才向后端发送 START\_VIDEO\_STREAM 或 SEEK\_VIDEO\_STREAM，请求参数包括 rootPath、当前剧集相对路径 videoPath 和 startTime。

handleVideoStreamReady() 位于1734行附近。收到后端的 VIDEO\_STREAM\_READY 后，先用 MediaSource.isTypeSupported(data.mimeType) 做浏览器侧最后检查，再创建 SourceBuffer，设置 mode='segments'。SourceBuffer.timestampOffset 使用后端实际对齐后的 streamStartTime，使从中途重新生成、内部时间从0开始的 fMP4 正确落到整部视频时间轴对应位置。后端返回的 duration 会设置给 MediaSource，所以 NPlayer 可以显示完整总时长，而不是只显示当前片段长度。

SourceBuffer 的 updateend 事件负责串联以下动作：检查初始预缓冲是否达到要求、按需删除过旧缓冲、继续写入队列中的下一段、检查是否需要请求后续数据，以及在后端真正结束且队列写空时调用 endOfStream。解析失败、appendBuffer 失败、MIME 不支持等错误统一进入 failRemuxStream()，该函数只处理一次错误，清空队列、通知后端取消流、释放 MediaSource，并通过 NPlayer toast 输出错误，避免 SourceBuffer 已被移除后还重复写入产生大量连锁报错。

### 三、后端 FFmpeg 探测、路径校验和流会话管理

backend/classify\_shower\_back.py 39 行附近的 self.video\_streams 是流会话表，按“WebSocket对象 → widgetId → session”两层索引保存。一个 session 中保存 streamId、asyncio Task、FFmpeg Process、视频总时长、当前允许输出到的 bufferUntil 和用于唤醒懒加载的 flowEvent。同一 WebSocket、同一 widgetId 最多保留一条活动流；启动或 Seek 新流前会先取消旧流。

FFmpeg.exe 没有硬编码在 Python 源码里。backend/classify\_shower\_back.py 152 行附近的 get\_ffmpeg\_path() 从 backend/config/classify\_shower\_config.json 的 video-config.ffmpeg-path 读取，支持环境变量和用户目录展开，并在使用前检查文件是否真实存在。backend/config/classify\_shower\_config.example.json 中也补有 ffmpeg-path 示例，机器相关的真实配置文件由 .gitignore 排除，不提交到 Git。

resolve\_video\_path() 位于132行附近。它把 rootPath 和 videoPath 转为 realpath/abspath，先保证视频没有用“..”等方式越出当前番剧目录，再保证最终文件位于 global\_config.json 配置的 base\_dir 之一，最后检查文件存在。最初直接使用 os.path.commonpath 比较路径，在番剧位于 G 盘而某个配置根目录位于 D 盘或 UNC 路径时会抛出“Paths don't have the same drive”。为此增加 is\_path\_within()：统一大小写和真实路径，并捕获 Windows 不同盘符或本地路径/UNC 混用产生的 ValueError，把该根目录视为不匹配后继续检查其他根目录，而不是终止整个播放请求。

probe\_video() 位于213行附近，通过一个短时 FFmpeg 探测进程读取输入的 duration、第一条视频轨和第一条音频轨，生成后续 MSE 所需的 videoCodec、sourceAudioCodec、audioCodec、audioTranscoded、mimeType 等信息。探测在 run\_in\_executor 中执行，避免阻塞 WebSocket 事件循环，单次探测设有15秒超时。

H.264 不能只固定写成 avc1.640028，因为真实视频的 profile、compatibility 和 level 可能不同，MSE 声明的 codec 与初始化段 avcC 不一致时 Chromium 会直接拒绝 SourceBuffer。backend/classify\_shower\_back.py 161 行附近的 probe\_h264\_codec\_string() 会让 FFmpeg 流复制一帧到内存中的 MP4，从 avcC box 提取三个字节，生成真实的 RFC 6381 codec 字符串，例如测试文件得到 avc1.42C028。这个值随后写入 VIDEO\_STREAM\_READY.mimeType，保证前端声明与 fMP4 初始化段一致。

start\_video\_stream() 位于620行附近，是 START\_VIDEO\_STREAM 和 SEEK\_VIDEO\_STREAM 的统一入口。其流程为：取消相同 widgetId 的旧流；解析和校验路径；读取 FFmpeg 配置；探测媒体；判断视频编码是否支持；限制 startTime 不超过视频结尾；必要时把 Seek 时间对齐到关键帧；先发送 VIDEO\_STREAM\_READY；建立 session；最后异步启动 stream\_ffmpeg\_output()。由于长时间输出放在独立 asyncio Task 中，主 WebSocket 仍可继续处理 BUFFER\_VIDEO\_STREAM、CANCEL\_VIDEO\_STREAM 和其他模块命令。

### 四、FFmpeg 命令和 fMP4 管道分段

stream\_ffmpeg\_output() 位于 backend/classify\_shower\_back.py 460 行附近。FFmpeg 从配置路径启动，stdin 关闭，stdout 和 stderr 都使用管道，Windows 下使用 CREATE\_NO\_WINDOW，避免每条流弹出控制台窗口。startTime 大于0时使用 -ss 从对应位置开始；只选择第一条视频和可选的第一条音频，丢弃字幕和数据轨。视频默认使用 -c:v copy，不进行耗时、损画质的视频重编码。输出参数使用 fragmented MP4：frag\_keyframe、empty\_moov、default\_base\_moof、delay\_moov，分片目标约2秒，最终写到 pipe:1。

TS 中 AAC 往往是 ADTS 比特流，不能原样作为 MP4 音轨配置。对于已经是 AAC 的输入，命令增加 aac\_adtstoasc bitstream filter；同时使用 delay\_moov，等首个媒体包经过 bitstream filter、拿到 AudioSpecificConfig 后再生成 moov。这个修复解决了初始化段虽然存在、但 esds 缺少 AAC 配置而被 Chromium 判定为不可解析的问题。

Python 从 stdout.read(256\*1024) 得到的只是任意管道读取块，并不保证一次 read 恰好是一个 MP4 分段。直接把每次 read 的结果发给 appendBuffer 会把 box 从中间切断，造成“浏览器解析 FFmpeg 视频流失败”。因此 backend/classify\_shower\_back.py 275 行附近实现 extract\_mp4\_boxes()，按照 ISO-BMFF box 的32位/64位长度字段从累积 bytearray 中切出完整顶层 box，并对非法长度、超过128MB的单 box、流在 box 中途结束等情况报错。

后端把 ftyp/moov 等初始化信息组合成 segmentType='init' 的逻辑分段；把 moof 与对应 mdat 组合成 segmentType='media' 的逻辑分段；mfra 是文件尾随机访问索引，实时 MSE 不需要，直接忽略。只有完整逻辑分段才经 pack\_video\_chunk() 加上 HSV1 消息头后发送。这样 SourceBuffer 每次收到的都是完整 init 或 media 分段，不再依赖 WebSocket 包大小或操作系统管道切块方式。

stderr 由单独任务持续读取并限制保留量，避免 FFmpeg 因 stderr 管道写满而阻塞；FFmpeg 异常退出时取最后一行作为 VIDEO\_STREAM\_ERROR。正常结束发送 VIDEO\_STREAM\_ENDED。任务取消、协议异常或其他异常都会终止 FFmpeg、排空 stdout、取消并等待 stderr 任务，并从 video\_streams 删除当前 session。

### 五、拖动进度条、音画同步与黑屏等待优化

最初 Seek 直接把用户指定秒数传给 FFmpeg。流复制不能从任意非关键帧可靠开始，视频轨可能等到后面的关键帧才出现，而音频轨已从用户指定位置开始，反复拖动后会出现声音与画面相差1至3秒。backend/classify\_shower\_back.py 182 行附近增加 align\_seek\_to\_video\_keyframe()：用短时 FFmpeg -debug\_ts 探测从请求位置开始实际可输出的第一帧视频时间，把 requestedStartTime 对齐到下一关键帧，再用这个实际 startTime 启动正式流。VIDEO\_STREAM\_READY 同时返回 requestedStartTime 和 startTime，前端记录“请求时间 → 关键帧时间”的变化。视频和音频从同一段有效时间线开始，解决多次 Seek 后音画不同步。

前端最初只要缓冲区有一点数据就恢复播放，FFmpeg 使用 -re 又被限制为1倍速读取，因此播放器边播放边等数据，表现为明显卡顿。随后在 CS\_VideoPlayerWidget 中加入预缓冲：streamPrebufferSeconds 最初为6秒，实际测试后延长为12秒。setInitialStreamPositionIfReady() 会计算从 streamStartTime 开始已连续缓存的秒数，未达到12秒时暂停 video 但记住用户的播放意图；达到目标或视频剩余长度不足目标时才设置 currentTime 并恢复播放。play 事件会阻止用户在预缓冲未完成时提前消耗缓冲，并用 toast 提示“正在预缓冲”。

为解决每次 Seek 后黑屏6至8秒的问题，后端去掉 FFmpeg 的 -re，不再强制按真实播放速度读取。实现过程中曾加入“先突发读取18秒，再按媒体时间节流”的过渡方案，并为此增加了 MP4 box 的嵌套解析：list\_mp4\_boxes()、read\_mp4\_track\_timescales() 从 moov 的 tkhd/mdhd 建立 track id 与 timescale 映射，read\_mp4\_fragment\_start() 从 moof/traf/tfdt 得到每个媒体片段的准确时间。最终按照需求改为水位驱动懒加载，不再按墙上时钟做1倍速节流，但这些 tfdt 解析函数继续用于判断每个分段在整部视频中的时间位置。

### 六、单 FFmpeg 进程的水位懒加载

最终方案位于 backend/classify\_shower\_back.py 17、443-458、460-618 行附近，以及 frontend/classify\_shower\_video.js 1904-1956 行附近。后端高水位 VIDEO\_STREAM\_HIGH\_WATER\_SECONDS 为30秒；前端初始预缓冲为12秒、低水位为10秒、高水位为30秒、向后保留旧缓冲60秒。

新流启动后，后端先允许同一个 FFmpeg 进程尽快读取到 startTime+30秒。stream\_ffmpeg\_output() 根据 fMP4 media 分段的 tfdt 算出 fragment\_time\_in\_video；当下一段超过 session.bufferUntil 时，不结束 FFmpeg，也不重复创建进程，而是在 flowEvent 上等待。前端播放位置接近缓冲边缘、timeupdate 检测到前方缓冲低于10秒，或者 video 触发 waiting 时，requestMoreStreamData() 发送 BUFFER\_VIDEO\_STREAM，携带同一个 streamId 和新的 bufferUntil。后端 extend\_video\_stream\_buffer() 校验连接、widgetId、streamId 和视频总时长后提高水位并 set flowEvent，原 FFmpeg 立即继续高倍率读取。

因此正常顺序播放时只保持一个 FFmpeg 进程，既取消了 -re 的1倍速限制，也避免每补一小段就重复创建进程。只有用户跳到当前 MSE 缓冲范围之外时，才必须取消旧进程并从新关键帧位置创建新的 FFmpeg 流。前端用 streamRequestedUntil 防止反复请求相同范围；到达视频末尾时确保发出最后一次请求。trimOldStreamBuffer() 会在队列为空且 SourceBuffer 空闲时删除当前播放位置60秒以前的数据，并且至少推进10秒才再次删除，避免长视频持续播放造成浏览器内存无限增长。

### 七、不支持的视频编码和音频实时转码

backend/classify\_shower\_back.py 20-29 行附近增加视频编码白名单和 MIME 映射。当前允许直接流复制到 fMP4/MSE 链路的视频编码为 H.264、HEVC、AV1、VP9。DivX、Xvid 通常被 FFmpeg 识别为 MPEG-4 Part 2，即 videoCodec='mpeg4'，不在白名单中。

start\_video\_stream() 在启动长驻 FFmpeg 之前检查 probe\_video() 返回的 videoSupported。若视频编码不支持，只发送文本命令 VIDEO\_STREAM\_UNSUPPORTED，其中包含 mediaType='video'、videoCodec、supportedVideoCodecs、videoPath 和固定提示“不支持该视频的视频编码格式”，随后直接 return：不会建立 video\_streams session，不会启动长驻 FFmpeg，更不会发送 VIDEO\_STREAM\_CHUNK 二进制数据。

frontend/classify\_shower\_video.js 1214、1798-1841 行附近处理 VIDEO\_STREAM\_UNSUPPORTED。前端停止并清空当前流状态、移除 video.src、释放 MediaSource，在播放器容器上覆盖一个持续显示的深色提示层，主文字为“不支持该视频的视频编码格式”，下方显示实际检测到的编码。提示层会在重新打开流、切换剧集或销毁播放器时移除。

音频采用与视频不同的策略。probe\_video() 同时区分 sourceAudioCodec（输入编码）、audioCodec（实际输出编码）和 audioTranscoded（是否转码）。当前 fMP4/MSE 链路把 AAC 作为保证兼容的音频格式：输入本来就是 AAC 时只做 bitstream filter 和流复制；AMR、PCM、Opus、AC3、MP3 等非 AAC 输入则保持 -c:v copy，只对音频执行 -c:a aac -profile:a aac\_low -ar:a 48000 -b:a 128k，实时转换成48kHz AAC-LC，再和原视频轨一起封装进 fMP4。由于没有 -re，音频转码也会按缓冲水位尽快完成，不被限制为1倍速。

### 八、正常退出、换集、断线和服务退出时的资源回收

frontend/classify\_shower\_video.js 1404 行附近的播放页 cleanFuncList 在退出播放页时先保存观看记录，再调用 disposeRemuxStream()，然后 player.dispose()，最后从文本和二进制消息处理列表中移除本组件的 handler。switchEpisode() 位于1643行附近，选择其他剧集时也先 disposeRemuxStream()、销毁旧 NPlayer，再请求新剧集数据。

disposeRemuxStream() 位于1984行附近：清除 Seek 防抖计时器；从 video 移除 seeking、play、timeupdate、waiting 监听；若存在活动流则发送 CANCEL\_VIDEO\_STREAM；如果 SourceBuffer 正在更新则尝试 abort；对打开的 MediaSource 调用 endOfStream；撤销 Object URL；清空 activeStreamId、队列、当前分段和错误状态。这样退出页面和换集时前端不会留下事件监听、MSE 缓冲或 Blob URL。

backend/classify\_shower\_back.py 409 行附近的 stop\_ffmpeg\_process() 采用幂等回收：进程仍存活时先 terminate，最多等待2秒，仍未结束则 kill 并等待最终退出。cancel\_video\_stream() 会先从 session 表移除对应 widgetId，再取消并等待 asyncio Task，由 Task 的异常/取消路径统一回收 stdout、stderr 和 FFmpeg 进程；重复调用不会误杀其他 widgetId 或其他 WebSocket 的流。

backend/back.py 106-155 行附近把模块 when\_disconnect() 调用移到连接 handler 的 finally。现在无论是正常关闭、websockets ConnectionClosed、协议处理异常还是 handler 任务被取消，都会逐模块执行断线清理，不再只覆盖某一个 ConnectionClosed 分支。backend/classify\_shower\_back.py 1371 行附近的 when\_disconnect() 会取消属于该 WebSocket 的全部视频流。

backend/back.py 的 main() 也增加 finally，并调用模块可选的 shutdown()。ClassifyShowerModule.shutdown() 位于1378行附近，服务正常退出时遍历并取消所有连接上的 FFmpeg 流，同时关闭 SQLite 连接。这个策略覆盖应用页面退出、切换剧集、WebSocket 异常中断、后端任务取消和后端正常停止；如果用任务管理器强杀 Python 或系统断电，因为操作系统不给 finally 执行机会，则不属于这一层可以保证的清理范围。

### 界面动画

`CS_VideoPlayerWidget` 的构造函数增加 `haveComment` 参数，默认值为 `false`。该参数用于控制通用视频播放器页面是否创建评论入口按钮和评论面板；未启用时不生成相关 DOM，也不改变原有播放器布局。番剧页面使用的 `CS_AnimeVideoPlayerWidget` 在创建内部 `videoPlayerWidget` 时同时启用剧集栏和评论功能，因此目前番剧播放页默认可以使用评论展示入口按钮。

`CS_VideoPlayerWidget.render()` 保存 `cs_createBackButtons(container)` 返回的按钮栏，并在原播放器容器外增加 `playerLayout` 弹性布局容器。评论功能启用时，`createCommentPanel()` 会在返回按钮栏左侧创建一个悬浮的 40×40 像素球形按钮，按钮沿用返回栏按钮的蓝色背景、白色图标、阴影和悬停提示，内部 SVG 使用对话气泡图形，鼠标悬停时通过 `title` 显示“显示评论”。

点击评论球形按钮后，`setCommentExpanded(true)` 把同一个评论元素从返回按钮栏移动到 `playerLayout`，放在播放器右侧。播放器容器和评论容器分别占去除间距后宽度的 60% 与 40%，最终宽度比例约为 3:2；评论容器变为白色圆角矩形并隐藏原 SVG。原播放器顶部的 50 像素间距移到外层 `playerLayout`，避免评论面板展开后把播放器顶部空白计算进评论区域高度。

展开开始前会读取 `playerLayout` 的实际高度，并把该值锁定到外层弹性布局的 `height`、`min-height` 和 `max-height`。因此整个 420 毫秒动画期间，播放器与评论面板所在区域以及下方页面内容都不会上下跳动。评论面板使用 `height: 100%` 占满这块展开前的最大高度，不再随着展开后变窄、变矮的 16:9 播放器一起缩短；播放器容器展开后设置 `align-self: center`，在固定高度的布局画布内垂直居中。收起动画结束后才解除外层高度锁定，恢复原有自适应布局。

展开后的评论矩形右上角创建蓝底白字的“收起”按钮。点击后执行 `setCommentExpanded(false)`：播放器恢复原来的 80% 宽度、1000 像素最大宽度和居中位置；评论元素重新挂回返回按钮栏左侧，恢复为蓝色球形按钮并重新显示对话图标。评论元素跨容器移动时使用 FLIP 方式计算移动前后的矩形位置，并通过 Web Animations API 连接位置、尺寸、圆角和背景色变化；不支持该 API 的浏览器仍会直接完成最终布局切换。

下面是评论元素跨容器移动时的核心实现。先在改变 DOM 归属前记录初始矩形 `panelFirstRect`，把元素移动到目标容器并应用最终样式后再读取 `panelLastRect`；两组矩形的差值用于生成反向位移和缩放。动画第一个关键帧把已经处于最终布局的元素视觉还原到原位置，随后逐渐恢复为无变换状态，因而看起来像同一个元素连续地从球形按钮移动并展开成评论面板：

```javascript
const panelFirstRect = panel.getBoundingClientRect();

this.playerLayout.appendChild(panel);
Object.assign(panel.style, {
    position: 'relative',
    width: 'calc(40% - 6.4px)',
    height: '100%',
    borderRadius: '12px',
    background: '#fff'
});

const panelLastRect = panel.getBoundingClientRect();
const deltaX = panelFirstRect.left - panelLastRect.left;
const deltaY = panelFirstRect.top - panelLastRect.top;
const scaleX = panelFirstRect.width / panelLastRect.width;
const scaleY = panelFirstRect.height / panelLastRect.height;

panel.animate([
    {
        transformOrigin: 'top left',
        transform: `translate(${deltaX}px, ${deltaY}px) scale(${scaleX}, ${scaleY})`
    },
    {
        transformOrigin: 'top left',
        transform: 'translate(0, 0) scale(1, 1)'
    }
], {
    duration: 420,
    easing: 'cubic-bezier(0.22, 1, 0.36, 1)'
});
```

播放器也使用独立的 FLIP 动画，避免先修改最终布局造成点击瞬间直接跳到屏幕左侧。展开时，最终位置和尺寸会在同一帧通过反向 `translate + scale` 映射回展开前的视觉状态，所以点击瞬间页面几乎不发生变化。播放器动画被拆为两个连续阶段：前 55% 时间保持展开前的尺寸，只逐渐向左移动；播放器到达最终左边界后，后 45% 时间再以左边中点为缩放锚点逐渐缩小到最终尺寸。这样播放器缩小时其垂直中心保持不变，并始终位于固定高度的 `playerLayout` 中央。收起时按相反次序，先在左侧居中放大，再平滑回到原来的水平居中位置。

初版 FLIP 动画曾把切换瞬间读取的 `lastRect.height` 直接写进 Web Animations 高度关键帧。由于播放器宽度本身也在进行 420 毫秒过渡，读取最终矩形时播放器仍接近展开前的大尺寸，这个过期高度会覆盖真实布局，造成动画期间评论面板高度异常，动画结束后又瞬间跳回。现在评论面板和播放器关键帧都不直接动画 `width`、`height`，只使用 `translate + scale` 表达视觉形变；实际布局尺寸由固定高度的 `playerLayout`、占满高度的评论面板和可独立缩放的播放器共同控制。

构造函数同时保存 `playerLayout`、`commentPanel`、`commentExpanded` 和当前动画等状态。播放页面清理函数会调用 `disposeCommentPanel()`，取消尚未结束的动画、移除评论元素并清空相关引用，避免退出页面或切换页面后残留 DOM 和动画回调。

### 前端界面

### 展开评论面板时

在展开评论面板时，前端向后端发送 `CS_GET_COMMENT_INFO` 请求评论信息数据，参数有对应视频的元数据文件夹路径(xxx.mp4@meta/)。后端响应评论信息数据`CS_COMMENT_INFO`，包括总共的评论数量，评论来源列表(每个来源的BV号、数据库文件路径和来源名称、评论数量、回复数量、最后更新时间、资源根目录)，评论模块的配置信息（每页评论数量，排序方式，是否标识被删掉的数据，......），评论模块阅读记录信息(上次阅读评论到什么地方)。具体过程是后端尝试读取 `xxx.mp4@meta/cmif.json` 文件，如果不存在返回总共评论数量为0即可，文件存在则读取解析。这个文件内容格式如下：

```json
[
    {
        "comment-srcfile":"cm1.db",
        "resource-folder":"",
        "basic-resfolder":"bilibili-resource",
        "src":"B站"
    },
    {
        "comment-srcfile":"cm2.db",
        "resource-folder":"",
        "basic-resfolder":"bilibili-resource",
        "src":"B站"
    },
    ......
]
```

对于每个评论来源，尝试在 `xxx.mp4@meta/` 文件夹所在目录下找到 `__COMMENT__` 文件夹。首先尝试读取 `__COMMENT__/cm-list.json` 文件，该文件内容格式如下：

```json
{
    "BVXXXXXX":{
        "file-name":"cm1.db",
        "aid":1234567891011,
        "update-time":1234567890,
        "comment-count":1000,
        "reply-count":200,
        "src-name":"动漫铥铥"
    },
    "BVXXXXXX":{
        "file-name":"cm2.db",
        "aid":1234567891012,
        "update-time":1234567990,
        "comment-count":500,
        "reply-count":100,
        "src-name":"MCE汉化组"
    },
    ......
}
```

根据 `comment-srcfile` 字段的值尝试在 `__COMMENT__/cm-list.json` 读取的内容里获取这个来源的评论数量和回复数量、最后更新时间和bv号，并核实 `__COMMENT__/` 下对应的数据库文件是否存在(不存在则跳过)，存在则以这个数据库文件的地址作为数据库路径。如果不存在这些键或不存在该文件，那么就在该文件夹下根据 `comment-srcfile` 字段的值找到对应的评论数据库文件，若不存在则跳过，如果存在则读取解析 `_metadata` 表获取这个来源的最后更新时间和bv号，读取 `main` 表和 `top` 表、`reply` 表的长度获取这个来源的评论数量和回复数量，并以这个数据库文件的地址作为数据库路径，将这些值填充到响应json里并写回 `__COMMENT__/cm-list.json` 文件；将  `__COMMENT__/cm-list.json` 中对应来源 `src-name` 字段的值作为来源名称填充到响应json里，如果 `__COMMENT__/cm-list.json` 里该来源缺少 `src-name` 字段那么其默认用bvid作为来源名，并尝试补上文件里的 `src-name` 字段；最后计算出总共的评论数量填充到响应json里；然后读取 `backend\config\classify_shower_config.json` 里 `video-config.comment-config` 字典(如果没有就加上，使用默认值)，来填充评论模块的配置信息；尝试读取 `xxx.mp4@meta/__COMMENT-RECORD__.json` 文件，该文件内容结构如下：

```json
{
    "view-time":1234567990,    // 上次查看评论的时间戳
    "last-read-src-BV":"BVXXXXXX",    // 上次阅读评论的来源BV号
    "last-read-page":1,    // 上次阅读评论读到了第几页
    "last-pagecount":10    // 上次阅读评论设置的每页评论数量
}
```
以 `xxx.mp4@meta/__COMMENT-RECORD__.json` 文件的 json 内容，填充评论模块的阅读记录信息。若文件不存在，以空值填充。

前端收到 `CS_COMMENT_INFO` 响应后，根据对应信息更新评论面板的界面显示(一共多少页可以通过本来源评论数量和每页评论数算出来)。随即根据当前的信息发送 `CS_GET_COMMENT_HTML` 请求该页的具体评论内容。这个命令的参数有要读取的数据库文件地址、增量数据库目录（直接把 `__COMMENT__/update/`的绝对目录传进去）、资源根目录、读取历史存储目录(一般是`xxx.mp4@meta/`)、排序方式、是否有关键词筛选条件及关键词值、当前页码、每页评论数量、是否标识被删掉的评论、是否只显示被删掉的评论、是否只显示大会员评论、是否按字数筛选及字数值。后端收到 `CS_GET_COMMENT_HTML` 请求响应 `CS_COMMENT_HTML` 命令。收到请求时，如果标识被删掉的评论或只显示被删掉的评论，假设数据库文件地址为`....../__COMMENT__/cm<number>.db`，后端应该以JSON格式从增量数据库目录里加载 `cm<number>.deletelist` 为已删评论列表，如果这个文件不存在则读取该来源所有增量数据库中被删掉的评论数据的rpid合并为这个列表，然后在增量数据库目录里创建文件 `cm<number>.deletelist` 并以JSON格式写入这个列表。如果“增量数据库目录”这个参数为空，则忽略“是否标识被删掉的评论、是否只显示被删掉的评论”这两个参数。将 `关联项目\bilibiliAPI\bilibili_comment_viewer\comment_viewer(DB).py` 里边的 `load_comments_from_database` 函数复制过来并改动一下使之支持 `CS_GET_COMMENT_HTML` 请求的这些参数，使用该函数从给定数据库里加载出该页所有评论的json，然后把 `comment_viewer(DB).py` 里边的 `comment_to_comment_html` 函数复制过来，然后改造一下使之能够重映射其中涉及到的各种资源到正确的目录，然后如果标识被删掉的评论，将出现在“已删评论列表”里的那些评论的背景颜色改成淡粉色。将json转化为html字符串作为`CS_COMMENT_HTML` 命令的响应数据发送给前端。与此同时将收到的有关的配置(比如是否有关键词筛选条件及关键词值、当前页码这样的就不算)存入 `backend\config\classify_shower_config.json` 里 `video-config.comment-config` 字典。

关于资源目录的确定，要根据这个来源对应 `xxx.mp4@meta/cmif.json` 的 `resource-folder` 字段的值来确定。如果为空，则默认使用 `__COMMENT__/` 文件夹的目录作为资源根目录。例如将 `./comment-resource/avatar/2119be22cebf9aae3bf3538db6dbb407618e4c2a.webp` 映射到 `....../__COMMENT__/comment-resource/avatar/2119be22cebf9aae3bf3538db6dbb407618e4c2a.webp` 目录下。

前端评论面板里的 `评论内容div` 在初始化时即放入初始html，初始html参考 `comment_viewer(DB).py` 里边的模板html，不同的是没有`.container`DIV也没有 `.header` DIV。`.comment-list` DIV 直接放到 `<body>` 里面。收到响应后将响应数据插入到`.comment-list` DIV 里边，实现评论展示。

### 切换设置和分页

如果 `来源div` 里的选择框里评论来源、选项按钮弹出悬浮窗口里的排序方式、关键词筛选的关键词值、设置菜单里勾选框 `标识被删掉的数据`、勾选框 `只显示被删数据`、勾选框 `只显示大会员评论`、勾选框 `字数筛选`、（若勾选字数筛选）可输入的下拉选择框 `只显示 xx 字 以上/以下 的评论`、每页的评论数量、当前页码这些发生了变化，重新发送 `CS_GET_COMMENT_HTML` 请求来改换评论面板 `评论内容div` 的html内容。如果当前页码为9，现在我更改每页的评论数量后所有评论只有6页了，那么当前页码就设置成6，即是设置为有效页码里距离之前页码最近的那个页码。这时后端还要额外发送一条 `CS_COMMENT_SETPAGE` 响应以设置前端当前页码，前端收到此信息更新页面控制组件外观以及当前页码标识的页码按钮，同时 `CS_COMMENT_HTML` 响应数据给的是当前设置的那个页码(第6页)的评论HTML。另外，切换页码时，要更新评论阅读记录 `xxx.mp4@meta/__COMMENT-RECORD__.json`。

### 切换视频剧集时

如果当前视频播放页的评论面板处于展开状态，那么在切换视频剧集时，评论面板里 `评论内容div` 的内容会被清空成初始化状态，重新发送 `CS_GET_COMMENT_INFO` 和 `CS_GET_COMMENT_HTML` 请求。
