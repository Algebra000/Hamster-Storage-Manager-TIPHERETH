## 保存某视频剧集上一次观看到的位置

`CS_VIDEO_DATA` 响应命令下有`auto-seek-time`键，值为用户上次观看到什么时间点。

剧集元数据目录位于视频同级，命名为 `<完整视频文件名（含扩展名）>@meta/`。例如，`xxx.mp4` 对应 `xxx.mp4@meta/`，`xxx.ts` 对应 `xxx.ts@meta/`，观看记录和评论阅读记录分别保存在各自的目录内。

该值通过读取剧集元数据目录下的文件 `__RECORD__.json`（例如 `xxx.mp4@meta/__RECORD__.json`）的内容，尝试读取`video-time`键值作为`auto-seek-time`键值，若读取失败设为0。文件`__RECORD__.json` 的内容参考示例：

```json
{
    "view-time":1778569079,
    "video-time":1708.0
}
```

然后前端部分使用`auto-seek-time`键值来初始化播放器，`new NPlayer.Player()`传入的json参数相关文档：

> “...... autoSeekTime	视频加载成功时自动跳转到的时间点（跳转后该参数会自动设为 0），你可以用这个参数实现记忆上次用户观看时间......”

然后在退出播放器页面调用的清理函数里加上通知后端保存目前观看记录的函数。new NPlayer.Player()建立的对象所拥有的属性的文档：

> ”
> ......
> currentTime: number \[get/set]#
> 获取和设置当前视频时间。\[get/set] 表示该属性可以同时被获取和设置新的值。
> “

这个保存方法除了要更新`__RECORD__.json`，还要创建或更新目录下的`__HISTORY__`文件，该文件(json)格式要记录最后一次用户访问该番剧(等视频集合)观看的是第几集(“order”键)、这个对应的视频文件相对地址、当前时间戳、以及当前视频时间。

所以后端的数据库番剧表的每一条番剧除了现有的这些项外还要加上最后一次用户访问该番剧观看的是第几集、上一次访问时间，以及看到的视频时间，这些数据通过扫描`__HISTORY__`文件得到。除此之外再加上“是否有弹幕”这一项，只要番剧的这些剧集里有一集是有弹幕的（即dm\_dir下“rmcf.json”存在）那就算这个番剧有弹幕。

## 弹幕重映射功能

弹幕重映射用于解决在视频播放时，弹幕来源的时间轴与本地视频时间不一致导致弹幕发送时机错位的问题。

### 读取并执行逻辑

`CS_VIDEO_DATA` 响应命令下有 `has-danmaku` 和 `danmaku-data` 两个键，分别表示本次是否成功生成弹幕配置，以及交给前端弹幕插件使用的数据。前端发送 `GET_CS_VIDEO_DATA` 请求后，后端根据 `rootPath` 和 `videoPath` 找到视频同级的 `<完整视频文件名（含扩展名）>@meta/` 目录，例如 `xxx.mp4@meta/`，尝试读取其中的 `rmcf.json` 文件，然后将读出的配置列表和这个目录传给 `backend/classify_shower_video.py` 里的 `make_danmaku_data(remap_config_list, dm_dir)` 方法。

文件 `rmcf.json` 的内容是一个列表，每一项指定一个弹幕源文件及其时间重映射方式，可以给同一个文件设置多项配置。内容参考示例：

```json
[
    {
        "dmsrc-file": "dm1.json",
        "time_filter": [[10, 30], [50, 70]],
        "cut_time": 5,
        "add_time": [[20, 25], [40, 50]],
    }
]
```
其中 `time_filter` 、`cut_time` 、`add_time` 这三个键值决定了该弹幕源的弹幕完整的重映射方式。在设计中这三个参数的具体含义如下：

1. `time_filter`：**弹幕筛选器**。主要具有按时间段筛选弹幕、自动将范围内的最早弹幕时间对齐到该视频(本地的要往其上加这个来源弹幕的视频，即目标视频，后续不再赘述) 0s 处这两个功能。示例中值为 `[[10, 30], [50, 70]]`，给出了10-30秒、第50-70秒这两个范围，不在范围里的弹幕会被过滤掉，然后把所有弹幕时间减去10，也就是将第10秒的弹幕移到第0秒。

    例如有6个弹幕的时间分别为 `[10, 20, 30, 40, 50, 60]`，经过 `time_filter` 后会变成 `[0, 10, 20, 40, 50]`。

    如果不希望将选择器选择范围的最早时间对齐到 0，那就额外加入一个负值范围，例如 `[-1,-1]`，这样 `[10, 20, 30, 40, 50, 60]` -> `[10, 20, 30, 50, 60]`。

    如果其中的时间范围有交集，例如 `[10, 30]` 和 `[20, 40]`，那么筛选器采取并集策略，即这两个范围实际上与 `[10, 40]` 等效。

    若 `time_filter` 为空列表，既不筛选也不移动时间起点。

2. `cut_time`：**多余片头时间**。即是网上的弹幕源视频相较目标视频在开头多出一部分片段，这部分片段的长度，单位为秒。例如同样一幅画面，在目标视频里是第0秒，在弹幕源视频里是第x秒，然后这是由于弹幕源视频多了x秒的开头，那么 `cut_time` 就是x。在目标视频里不存在的这x秒开头内的弹幕将通过抛物线映射到目标视频的开头 `[0,x/4]` 秒的区间内，然后目标视频的前x秒即原弹幕 `[x,2x]` 秒的区间内的弹幕将会通过抛物线映射被挤压到目标视频的 `[x/4,x]` 秒的区间内。

    假设某个弹幕在弹幕源视频里 $t$ 秒出现，那么其在目标视频里出现的时间 $T$ 将为:

    $$
    T =
    \begin{cases}
    \dfrac{t^2}{4x}, & t < 2x \\[6pt]
    t - x, & t \ge 2x
    \end{cases}
    $$

3. `add_time`：**空白段**。即是在连续的弹幕源列表中插入一些没有弹幕的空白时间段，原先在这些时间里以及该段时间之后的弹幕会被相应延迟，常用于弹幕源视频相较目标视频有删减的情况。

    示例中值为 `[[20, 25], [40, 50]]`，如果目标视频的第20-25秒、第40-50秒这两段被删掉了，剩下的视频段依次拼接后与弹幕源视频可以一一对应，那么这时应用该空白段后为视频添加此来源弹幕，弹幕与视频内容的对应关系将仍然是正确的。目标视频的第20-25秒、第40-50秒这两段不会出现此来源的弹幕，因为这两段在弹幕源视频里被删掉了。

以上重映射逻辑的具体实现在 `backend/classify_shower_video.py` 里的 `make_danmaku_data` 方法。以下是具体的实现逻辑：

1. 首先，后端读取文件 `rmcf.json` ，将 `dmsrc-file` 和元数据目录拼接得到弹幕源文件地址，例如 `xxx.mp4@meta/dm1.json`，以 UTF-8 编码读取该文件中的 JSON 弹幕列表。源文件不存在时输出错误信息并跳过这一项，继续处理后面的配置。每条弹幕通过 `time` 键记录播放时间，单位为秒；该值缺失或为 `null` 时补为0，可以转换成数字的值按浮点数处理，转换时发生 `ValueError` 或 `TypeError` 则按0处理。

2. 然后该方法的子函数 `apply_time_filter` 根据 `rmcf.json` 里 `time_filter` 的键值筛选需要的弹幕，该键缺省为空列表，即不筛选也不移动时间起点。如果设置了若干个 `[开始时间, 结束时间]` 区间，只保留原始时间落在任意区间内的弹幕，包含区间的两个端点；同一条弹幕即使落在多个区间内也只保留一次。同时把所有区间中最小的开始时间作为统一起点，从保留下来的弹幕时间里减去这个起点。例如上面的配置会把原始第10秒、第30秒、第50秒的弹幕分别移到第0秒、第20秒、第40秒，两个区间之间的空档仍然保留，不会把各个区间首尾拼接起来。

3. 筛选后的弹幕先按时间升序排列，再逐条使用 `apply_remap` 子函数应用 `cut_time` 和 `add_time`。先执行多余片头时间的抛物映射，将小于 `2 * cut_time` 的时间改成 `time * time / (4 * cut_time)`，其余时间再减去 `cut_time`。

    接下来执行 `add_time`，该键缺省为空列表。后端先把其中的 `[start, end]` 区间按 `start` 升序排列，再依次比较已经变换过的弹幕时间；只有当前时间严格大于 `start` 时，才增加 `end - start` 秒，等于 `start` 时不移动。每一次增加后的结果继续参与下一个区间的判断。例如上面的配置中，原始第50秒的弹幕筛选后变为40秒，裁剪后变为35秒，经过 `[20, 25]` 后变为40秒，因等于下一个区间的起点而不再增加；原始第51秒的弹幕则依次变为41秒、36秒、41秒、51秒。这些时间变换只更新弹幕的 `time` 字段，正文、来源等其他字段沿用原始内容。

### 生成 `dm-info.json` 并发送

`dm-info.json` 用于保存本视频所有弹幕来源的一些基本信息，内容参考示例：

```json
{
    "dm-src": [
        {
            "name": "B站",
            "url": "",
            "update-time": 1784354475,
            "dm-count": 3064
        },
        {
            "name": "B站",
            "url": "",
            "update-time": 1784743053,
            "dm-count": 5576
        },
        {
            "name": "B站",
            "url": "",
            "update-time": 1784731059,
            "dm-count": 1796
        }
    ],
    "dmjs-build-time": 1788278078,
    "dm-count": 12953
}
```

其中 `dm-src` 键保存所有弹幕来源的来源名称(`name`键)、URL(`url`键)、更新时间(`update-time`键)、弹幕数量(`dm-count`键)等信息。这些信息是在每个弹幕数据文件经重映射处理完后，调用`make_danmaku_data` 方法的子函数 `get_source_info` 从重映射完成的这个弹幕数据文件弹幕列表里统计出每个来源的相关信息得到的。在此之后将该文件重映射完的弹幕列表并入总输出弹幕列表。

关于子函数 `get_source_info`，它的实现逻辑是统计列表中每条弹幕的 `src` 键，将同一src划为一个来源，不同src划为不同来源。对每个来源的 `src` 键值作为来源名称(`name`键)，缺少 `src` 时使用“未知”，并统计该来源的弹幕数量填入`dm-count`键。然后 `url` 当前恒为空字符串(保留)，`update-time` 取该来源弹幕最大的 `send-time` 值（缺少 `send-time` 时按0）。

所有的弹幕数据文件执行完这一套逻辑后，再把总输出弹幕列表按变换后的时间升序排列，并创建或覆盖元数据目录下的 `dm-info.json`。将每个弹幕数据文件重映射并 `get_source_info` 获取到的列表简单合并，填入 `dm-src` 字段，`dmjs-build-time` 键保存本次生成时的整数时间戳，`dm-count` 键保存合并后的弹幕总数。重映射后的弹幕列表不写入磁盘。

最后从后端配置的 `video-config.danmaku-config` 中取得 `speed`、`fontsizeScale`、`area`，连同保存总弹幕列表的 `items` 键组成返回值，作为 `CS_VIDEO_DATA` 的 `danmaku-data`。整个 `danmaku-config` 缺失时这三个值分别为0.75、1.0、0.75；如果该字典已经存在但缺少某个键，逐键回退值分别为0.75、16、0.75。前端 `CS_VideoPlayerWidget` 收到响应后保存这份数据，在启用弹幕且插件可用时传给 `new NPlayerDanmaku(this.danmakuData)`，用于初始化播放器的弹幕插件。

如果 `rmcf.json` 不存在，或者读取配置、处理源数据、写入信息文件的过程中抛出异常，调用方会保持 `has-danmaku` 为 `false`、`danmaku-data` 为空列表；异常时同时输出失败日志。只有 `make_danmaku_data()` 正常返回后才把 `has-danmaku` 设为 `true`，因此配置列表为空、所有源文件都被跳过或筛选结果为空时，只要后续写入等步骤成功，该值仍会是 `true`，不代表弹幕数量一定大于0。

## 添加播放其他格式容器视频的支持

本功能用于播放 TS、MKV、AVI 等浏览器不能直接读取、但其中的视频编码可以由浏览器解码的文件。后端使用 FFmpeg 将选中的视频轨和音频轨实时重封装为分片 MP4（fragmented MP4，简称 fMP4），通过现有 WebSocket 发送到前端；前端使用 `MediaSource` 和 `SourceBuffer` 接收分段，交给 `CS_VideoPlayerWidget.player.video` 播放。这里的 `player` 是 NPlayer 实例，`player.video` 是它内部的 `HTMLVideoElement`，播放器控件、弹幕和观看记录仍围绕这个元素工作。

### 播放路径与编码支持

`frontend/classify_shower_video.js` 中的 `CS_VideoPlayerWidget.initPlayer()` 通过 `isNativeVideo()` 判断当前剧集的扩展名。`mp4`、`m4v`、`webm`、`ogv`、`ogg` 默认使用 `getVideoUrl()` 生成的文件地址，直接交给浏览器播放，并把上次观看位置交给 NPlayer 的 `autoSeekTime`。普通 MP4 若在视频数据响应中被标记为问题视频(比如视频时间戳信息不完全)，则同样不设置初始 `src`；其他扩展名不设置初始 `src`，在 `player.mount()` 后调用 `setupRemuxStream(this.autoSeekTime || 0)`，向后端发送 `START_VIDEO_STREAM` 以进入后端重封装流程。这个判断只决定播放路径，不代表相应容器中的所有编码都能播放；原生路径当前也不会在播放失败后自动切换到重封装。

重封装路径由后端 `ClassifyShowerModule.probe_video()` 检查视频和音频编码。当前允许的视频编码为 `h264`、`hevc`、`av1`、`vp9`，正式输出始终使用 `-c:v copy`，保留原有视频压缩数据。DivX、Xvid 等被 FFmpeg 识别为 `mpeg4` 的视频编码不在允许列表内，后端发送 `VIDEO_STREAM_UNSUPPORTED` 后返回，不创建正式流会话，也不发送媒体二进制数据。前端 `handleUnsupportedVideoStream()` 清理流状态并暂停视频，在播放器内持续显示“不支持该视频的视频编码格式”和检测到的编码名称。

音频输出统一以 AAC 为兼容目标。原音频为 `aac` 时使用 `-c:a copy`；原音频为 AMR、PCM、MP3、AC-3、Opus 等其他编码时，将选中的第一条音轨实时转为 48 kHz、128 kb/s 的 AAC-LC。没有音轨时只输出视频。这里依赖本机 FFmpeg 具有相应容器读取和音频解码能力，不能仅凭文件扩展名保证可以处理。

后端允许某个视频编码后，前端仍使用 `MediaSource.isTypeSupported(mimeType)` 检查当前浏览器是否接受该编码组合；检查失败则进入流失败清理流程。H.264 的 MIME 编码字符串由 `probe_h264_codec_string()` 从 FFmpeg 生成的 `avcC` 中读取 profile、兼容标志和 level，得到例如 `avc1.640028` 的值；提取失败时使用映射表中的默认值。其他视频编码当前使用固定映射值，因此允许列表和 MIME 检查不能代替实际解码验证。

### 关于对时间戳缺失的问题 MP4

部分 MP4 的显示时间戳缺失或异常，浏览器直接播放时可能出现画面前进后又倒退几帧、反复抖动的问题。播放页通过视频元数据中的标记决定是否启用时间戳修复。这个标记保存在视频同级的 `<完整视频文件名（含扩展名）>@meta/` 目录下的 `__meta` 文件中，例如 `xxx.mp4@meta/__meta`。文件内容为 JSON 对象，其中的时间戳标记参考示例：

```json
{
    "mp4-timestamps-valid": false
}
```

其中时间戳有效性（`mp4-timestamps-valid` 键）为 JSON 布尔值 `false` 时，表示该视频的时序已被标记为异常。后端据此让普通 `.mp4` 进入流式修复和缓冲播放路径：使用 FFmpeg 实时重封装，再逐段补写显示时间偏移，通过 WebSocket 交给前端播放。只有布尔值 `false` 会触发这条路径；值为 `true`、缺少该键、值的类型不符，或者文件不存在、读取及解析失败时，都沿用原有扩展名播放规则。字符串 `"False"`、`"false"` 和数字0均不触发修复。

这个键记录的是时间戳是否有效，而不是 `ctts` 表是否存在。没有 `ctts` 的 MP4 也可能具有正常的显示时序，不能仅因缺少该表就把标记设为 `false`。当前播放流程读取已有标记，不自动检测全片的时间戳，也不生成或改写这个标记。

后端 `ClassifyShowerModule` 收到 `GET_CS_VIDEO_DATA` 后，先解析视频路径，再调用 `read_video_playback_policy()` 读取播放策略。该方法只对 `.mp4` 检查上述标记，并解析元数据文件的实际路径，确认它没有越出视频所在目录。`__meta` 超过64 KiB时按读取失败处理。得到的策略与弹幕、上次观看位置一起通过 `CS_VIDEO_DATA` 返回，相关字段参考示例：

```json
{
    "command": "CS_VIDEO_DATA",
    "widgetId": "video-widget-example",
    "videoPath": "xxx.mp4",
    "requestId": "video-widget-example:metadata:1",
    "force-buffered-playback": true,
    "buffered-playback-reason": "mp4-timestamps-invalid"
}
```

其中强制缓冲播放（`force-buffered-playback` 键）表示是否由后端修复显示时间戳并分段发送视频，触发原因（`buffered-playback-reason` 键）为 `mp4-timestamps-invalid`；未触发时两者分别为 `false` 和 `null`。视频路径（`videoPath` 键）和请求标识（`requestId` 键）对应本次视频数据请求，前端核对后才接受响应，避免切换剧集后迟到的旧响应覆盖当前策略。前端 `CS_VideoPlayerWidget` 保存这些信息，在 `initPlayer()` 中结合扩展名决定直接播放还是建立 `MediaSource`。

需要修复时，前端调用通用提示接口 `window.frame_show_notice()`，显示“该 MP4 的显示时间戳异常，将修复时间轴并采用缓冲播放。”。提示持续6秒，背景色为 `#FFE69A`，文本颜色为 `#5C4300`，带有手动关闭按钮；切换视频或退出播放时关闭旧提示。随后仍使用 `START_VIDEO_STREAM`、`SEEK_VIDEO_STREAM`、`BUFFER_VIDEO_STREAM` 和 `CANCEL_VIDEO_STREAM` 管理播放，处理时间戳异常 MP4 时与播放其他容器时共用视频流接口。

### 流式修复问题 MP4 的显示时间戳

流式修复所需的数据由 `backend/video_timestamp_repair.py` 中的 `MP4StreamTimestampRepair` 保存，包括原 MP4 的样本时间表、文件位置和当前解码范围内的显示顺序。后端在每个 fMP4 媒体分片发送前，使用这些信息补写视频样本的显示时间偏移，再通过 `VIDEO_STREAM_CHUNK` 发送。整个过程不生成中间视频或修复缓存文件，也不改写原视频和 `__meta`。

#### 读取样本表与复用缓存

修复时间戳需要知道原文件中各帧的存放位置、解码时间和显示时间。MP4 将轨道中的一份压缩媒体数据称为一个“样本”；这里讨论的是视频样本，通常对应一帧压缩画面。样本表记录每个视频样本的大小、文件位置和时间信息，保存在原 MP4 的 `moov` 元数据中。修复器按原文件中的解码顺序，从0开始给视频样本编号；这个编号用于识别具体样本，不代表画面在屏幕上的显示次序。

后端每次收到开始播放或跳到未缓冲位置的请求，都由 `ClassifyShowerModule.start_video_stream()` 读取播放策略。确认 `mp4-timestamps-valid` 为 `false` 后，该方法调用 `cached_repair_metadata()`，查询模块内存中的 `video_repair_metadata_cache`。这个缓存保存已经从原 MP4 解析出的样本表，目的是让同一视频再次播放或跳转时复用解析结果，减少重复读取和展开时间表的开销。缓存中没有可用结果时，后端在线程池中创建 `MP4TimestampMetadata`，读取 `moov` 并解析样本表；命中缓存时，直接取出此前保存的 `MP4TimestampMetadata` 对象。

其中 `stts` 记录各视频样本的解码时长，修复器从0开始依次累加这些时长，得到每个样本在原视频轨道上的解码时间（DTS）。`ctts` 记录显示时间相对于解码时间的偏移，两者相加得到显示时间（PTS）。如果原文件没有 `ctts`，解析器先为每个样本记录偏移量0，即暂时令 PTS 等于 DTS；这只是保存原文件现有信息的方式，不表示显示顺序已经正确，后续仍需根据解码器输出的实际显示顺序计算偏移。

解析结果还包括样本大小、关键帧样本编号，以及“样本编号 → 原文件字节位置”和“原文件字节位置 → 样本编号”两组对应关系。例如，辅助解码器报告某帧来自文件中的某个字节位置时，后端通过后一组对应关系找到它是第几个视频样本；校验发送内容时，则通过前一组关系回到原文件读取对应的压缩数据。

无论样本表来自本次解析还是已有缓存，`start_video_stream()` 都将它交给新建的 `MP4StreamTimestampRepair`。同一视频后续每次开始播放或跳到未缓冲位置时，只要缓存仍有效，修复器就共享这些只读时间表和位置对应关系。表示当前处理到哪个样本的游标、辅助解码帧队列、待匹配的显示顺序记录，以及 FFmpeg 进程对象，均属于本次播放请求，单独建立，不在不同请求间共用。

缓存是否有效，由原视频和 FFmpeg 文件的签名共同决定。签名包含规范化的绝对路径、文件大小、修改时间和 ctime；后端每次准备播放时重新取得签名，只有与缓存键一致才复用样本表。首次解析结束后还会再次检查签名，如果读取期间文件发生变化，就拒绝使用本次结果并返回错误。这个准备步骤只读取元数据，跳过压缩媒体内容，不解码整部视频。解析器接受只有一路视频的普通非分片 MP4，要求样本时长为正；多段、空白或变速编辑时间轴不支持。单个 `moov` 最大为64 MiB，视频样本数量最多为200万。

关于缓存的保留与释放，`video_repair_metadata_cache` 最多保留4部视频，缓存中的视频样本合计不超过50万个。访问已有条目时更新其使用顺序，超过限制时移除最久未使用的条目；单部视频超过50万个样本时，解析结果仅供本次播放使用，不留在缓存中。同一路径写入新签名的结果时移除旧版本，模块关闭时清空缓存。切换剧集或跳转会回收旧请求的任务、进程和队列，但不清空仍有效的样本表缓存；缓存条目被移除时，正在使用它的修复器仍可完成本次处理，最后一个引用释放后才释放对应内存。媒体编码与时长的探测缓存、普通重封装使用的关键帧索引是另外两类缓存，其用途与回收规则见后文“媒体探测缓存与后台关键帧索引”。

#### 并行启动重封装与辅助解码

如果需要修复 MP4 的显示时间戳，后端在媒体编码检查通过后并行启动两个 FFmpeg 进程。主重封装进程负责读取原压缩视频、生成要发送给浏览器的 fMP4；辅助解码进程负责把画面解码出来，提供实际显示顺序。后端安排主进程启动任务后，随即调用 `MP4StreamTimestampRepair.start()` 启动辅助进程，不等待一个进程准备完成后才启动另一个。

两个进程都使用用户请求的开始时间，通过输入侧的 `-ss` 在原文件中定位到该时间附近的解码起点，这里将这种按时间定位的操作称为寻址。由于某些画面需要参考前面的画面才能解码，定位结果可能是请求时间之前的关键帧；后端保留从该关键帧开始的必要压缩数据，让辅助解码器和浏览器都能从有效起点解码。两个进程同时忽略 MP4 的编辑列表 `elst`。该列表用于描述媒体时间如何映射到播放时间，例如从媒体的哪个时间开始播放；忽略它使两个进程按相同的原始轨道时间处理数据。前述解析步骤已排除多段、空白或变速编辑，避免将复杂编辑时间轴按简单时间偏移处理。

辅助进程先解码原视频，再通过 `scale=1:1` 把辅助画面缩小为1×1像素，随后用 `showinfo` 输出显示帧编号和该帧在原文件中的字节位置。后端使用样本表中的位置对应关系，把这些帧信息转换为“实际显示顺序中的第几帧，对应原文件中的第几个视频样本”。缩放只作用于辅助进程的画面，不能省去前面的原视频解码；发送给前端的视频由主进程使用 `-c:v copy` 复制原压缩数据，保留原分辨率和画面内容。

辅助进程报告首个显示帧后，修复器检查它对应的原视频样本是否被标记为关键帧。这样可以确认当前片段从允许开始解码的位置起步，避免浏览器收到的第一帧依赖尚未发送的前置画面。检查通过后，后端从原样本表取出这个关键帧的 DTS，换算为秒，填入 `VIDEO_STREAM_READY` 的实际开始时间（`startTime` 键）；前端用它确定缓冲区和播放头在完整视频时间轴上的位置。因此，请求时间与实际开始时间可能不同，播放器从返回的实际起点开始显示画面。

主进程可能在实际起点确认之前就已生成部分 fMP4 数据。这些数据暂存在进程标准输出的操作系统管道和 Python 异步读取器的内存缓冲中；缓冲容量有限，写满后会暂停继续读取或写入，使主进程等待后端消费数据，不会把整部视频无限累积到内存。后端先确认起点并发送 `VIDEO_STREAM_READY`，然后才读取、修复和发送媒体分片，让前端先取得流标识、编码和时间起点，再接受对应的媒体数据。

关于准备阶段的回收，如果用户在 READY 发出前再次跳转、退出播放，或者准备过程失败，后端先请求停止辅助进程，并等待主进程的创建任务返回进程对象。这个对象由 Python 的 `asyncio` 返回，供后端访问进程的标准输出、标准错误和退出状态，以及调用终止方法；它就是代码中管理已启动进程的引用。后端取得对象后终止主进程，读取并丢弃管道中尚未处理的输出，等待两个进程和读取任务退出。整个回收任务受到取消保护，重复取消请求也会继续完成资源清理。

#### 按分片校验并修复显示时间

正式重封装使用相同的原文件、请求时间和忽略编辑表设置，并通过 `-copypriorss 1` 保留寻址点之前的必要样本。发送媒体分片时，`repair_segment()` 先核对样本：首个视频样本的压缩字节必须与原文件对应样本一致，各输出样本的大小必须与原样本表一致。核对失败就停止播放并返回错误，避免把辅助进程取得的显示顺序套到另一段画面上。辅助进程的帧队列最多保存128条记录，等待匹配的样本映射最多保存4096条；队列满时暂停读取辅助输出，管道随之限制继续解码，使显示顺序的获取随分片处理推进。

关于显示时间的计算，原 `stts` 中的样本时长相同、或最多相差一个轨道时间单位时，修复器把起始样本编号与解码器输出的显示帧编号相加，在原解码时间表中取出对应时间。这样既保留原时间间隔，也将时间分配给正确的显示帧。取得的时间先减去起始样本的解码时间，再换算为输出视频轨道的时间单位，并加上输出的解码起点；最后减去当前输出样本的解码时间，得到它的有符号显示时间偏移。计算使用原样本时间表，不使用平均帧率或标称帧率。

原样本时长的差异超过一个时间单位时，按变帧率视频处理。修复器保留原 `stts` 和 `ctts` 共同给出的显示时间，并沿解码器的实际显示顺序检查这些时间是否严格递增。发现时序异常时返回错误，不用平均帧率猜测缺失的时间。因此，前面的分片能够正常发送，只表示已处理范围通过检查，不表示后续全片已完成时序校验。

计算结果写入 fMP4 视频 `trun` 的 composition time offset 字段，并将 `trun` 版本设为1，以容纳负偏移。这里补写的是分片中的显示时间偏移，而不是在原 MP4 中追加一张完整的 `ctts` 表。增加或替换字段后，修复器重新计算 `moof` 长度，并调整视频和音频 `trun` 的数据偏移，保持 `mdat` 中的压缩媒体字节不变。轨道选择、音频复制或 AAC 转码、缓冲水位和前端追加分片均沿用现有流程；分片起点超过允许的缓冲范围时，先等待放行，再修复并发送这一段。

跳到已缓冲的位置时，前端直接使用已有数据；跳到未缓冲的位置时，通过 `SEEK_VIDEO_STREAM` 重建视频流，从新的请求范围继续逐段修复。回收旧流时，后端先取消输出任务和辅助帧读取任务，并立即向两个 FFmpeg 进程发出停止请求，再等待任务结束、排空管道并回收进程。辅助进程即使已有退出码，也会继续排空标准错误至 EOF；重复关闭复用同一个回收任务，通过 `asyncio.shield()` 保证再次取消播放任务不会中断回收。取消播放、退出页面、WebSocket 断开和模块关闭也会回收相关资源。


### 请求视频流与返回播放信息

视频流请求用于告诉后端当前播放器要读取哪个文件、从哪个时间开始播放。`setupRemuxStream()` 检查浏览器是否存在 `MediaSource`，然后由 `openRemuxMediaSource()` 建立媒体源，将其 Object URL 设置给 `player.video.src`，等待 `sourceopen` 后发送请求。首次播放使用 `START_VIDEO_STREAM`，跳转到尚未缓冲的位置使用 `SEEK_VIDEO_STREAM`，请求内容参考示例：

```json
{
    "command": "START_VIDEO_STREAM",
    "widgetId": "video-widget-example",
    "rootPath": "D:/番剧资源/某番剧",
    "videoPath": "01.ts",
    "startTime": 120,
    "requestId": "video-widget-example:stream:2"
}
```

其中播放器标识（`widgetId` 键）用于区分同一连接上的组件，资源根目录（`rootPath` 键）和相对视频路径（`videoPath` 键）共同定位文件，请求开始时间（`startTime` 键）以秒为单位。后端 `ClassifyShowerModule.message_proc()` 将开始和跳转请求安排为受管理的后台任务，统一交给 `start_video_stream()`，避免播放流初始化阻塞同一 WebSocket 的取消和缓冲请求；该方法先取消同一连接、同一 `widgetId` 的旧流，再通过 `resolve_video_path()` 检查文件存在、没有越出请求根目录，并在已配置资源根目录时检查文件属于其中之一。

接下来，`start_video_stream()` 读取 FFmpeg 配置和视频元数据中的播放策略，再由 `video_metadata_key()` 取得原视频和 FFmpeg 文件的签名。如果需要修复 MP4 的时间戳，后端先按签名查询样本表缓存，未命中时读取原文件建立样本表，并为本次请求创建修复器。随后通过 `cached_probe_video()` 获取媒体信息；缓存命中时直接读取结果，未命中时在线程池中调用 `probe_video()`，从 FFmpeg 标准错误输出中解析时长和编码。时长未解析到时按0处理，未探测到视频轨道则报错。

视频编码检查通过后，普通重封装在非零开始位置查询关键帧索引，索引不可用时执行 FFmpeg 定位探测。如果处理的是时间戳异常的 MP4，后端并行启动主重封装进程和辅助解码进程，通过辅助进程确认实际开始的关键帧。两种处理方式都在实际起点确定后返回 `VIDEO_STREAM_READY`，内容参考示例：

```json
{
    "command": "VIDEO_STREAM_READY",
    "widgetId": "video-widget-example",
    "videoPath": "01.ts",
    "requestId": "video-widget-example:stream:2",
    "streamId": "stream-example",
    "playbackMode": "remux",
    "timestampResult": "not-requested",
    "startTime": 121.5,
    "requestedStartTime": 120,
    "bufferHighWaterSeconds": 30,
    "duration": 1422.05,
    "videoCodec": "h264",
    "videoSupported": true,
    "sourceAudioCodec": "aac",
    "audioCodec": "aac",
    "audioTranscoded": false,
    "mimeType": "video/mp4; codecs=\"avc1.640028,mp4a.40.2\""
}
```

其中本次视频路径（`videoPath` 键）和请求标识（`requestId` 键）用于核对响应是否属于当前请求。播放处理模式（`playbackMode` 键）在普通重封装时为 `remux`，时间戳处理结果（`timestampResult` 键）为 `not-requested`；需要修复的时间戳异常问题 MP4 则分别为 `timestamp-repair` 和 `streaming`，表示随后输出的分片会逐段修复时间戳。前端核对视频路径和请求标识后才接受 `VIDEO_STREAM_READY`，准备阶段的错误和不支持响应同样携带这些标识，避免旧请求影响新媒体源。

本次流标识（`streamId` 键）在每次开始或跳转请求时重新生成；实际开始时间（`startTime` 键）用于定位缓冲区和播放头，原始请求时间（`requestedStartTime` 键）用于保留用户请求的位置。示例表示请求第120秒，关键帧探测后从第121.5秒开始输出。总时长（`duration` 键）用于设置播放器的完整时间轴，缓冲高水位（`bufferHighWaterSeconds` 键）用于控制后续数据请求。原音频编码（`sourceAudioCodec` 键）、输出音频编码（`audioCodec` 键）和音频是否转码（`audioTranscoded` 键）共同描述音频处理方式，没有音轨时两个编码字段为 `null`。`mimeType` 则供前端创建 `SourceBuffer`。

返回准备信息后，后端在 `video_streams[websocket][widgetId]` 中建立流会话，保存流标识、总时长、允许读取到的位置、唤醒事件、后台任务和 FFmpeg 进程。`stream_ffmpeg_output()` 通过 `asyncio.create_task()` 在后台运行，持续输出视频时仍能接收缓冲扩展、取消及其他页面命令。

### FFmpeg 配置与实时重封装

FFmpeg 可执行文件地址保存在相对项目根目录的 `backend/config/classify_shower_config.json` 中，由 `video-config.ffmpeg-path` 键指定。例如配置为 `C:/Tools/ffmpeg.exe`，播放时 `get_ffmpeg_path()` 展开环境变量和用户目录，并检查该文件存在；缺少配置或文件不存在时返回视频流错误，不会在代码中使用固定的机器路径。

模块的 `settings()` 安装向导依次检查已有配置、系统 PATH 中的 FFmpeg，再接受用户输入路径或下载。`classify_shower_check_ffmpeg()` 检查所需容器读取组件和音频解码组件，并使用微型样本实际验证视频流复制、PCM 转 AAC 和 fMP4 管道输出，通过后才保存可执行文件路径。运行时的媒体探测使用 FFmpeg，不依赖另外安装 `ffprobe`。

正式重封装由 `stream_ffmpeg_output()` 使用 `asyncio.create_subprocess_exec()` 启动，标准输入关闭，标准输出和标准错误分别连接管道，Windows 下隐藏命令窗口。命令只选择第一条视频轨（`-map 0:v:0`）和可选的第一条音轨（`-map 0:a:0?`），通过 `-sn -dn` 排除内嵌字幕和数据轨；页面弹幕仍由原有弹幕流程提供。

视频采用流复制，音频按前述规则复制或转码。对直接复制的 AAC，额外使用 `aac_adtstoasc` 将 TS/ADTS 所需的音频配置信息转换为 MP4 可用的形式。随后使用 `-avoid_negative_ts make_zero` 调整输出起点，并通过 `-movflags frag_keyframe+empty_moov+default_base_moof+delay_moov` 和 `-f mp4 pipe:1` 输出 fMP4。`delay_moov` 使初始化信息等待首批媒体包处理完成，避免 AAC 配置尚未得到时就发送不完整的初始化段。

普通重封装，以及时间戳异常 MP4 的首次播放，均使用 `-frag_duration 2000000`，即以2秒作为分片时长条件。如果正在播放时间戳异常的 MP4，用户又跳到尚未缓冲的位置，后端处理 `SEEK_VIDEO_STREAM` 时使用 `-frag_duration 1000000`，即以1秒作为分片时长条件，以减少首段发送前需要取得的显示顺序记录。这个参数属于本次新建的 FFmpeg 进程，因此从跳转后第一段开始，到该进程播放结束或被下一次跳转、取消操作终止为止，所有分片都使用1秒条件，不会在显示首帧后切回2秒。实际分片长度还受视频样本边界和关键帧位置影响，不保证每段恰好1秒或2秒。

生成的媒体数据经标准输出直接进入 Python 内存，再发送给前端，正常播放流程不预先生成整部临时 MP4 文件。命令也不使用 `-re` 限制为播放速度读取，允许首次播放和跳转后快速建立预缓冲；实际读取范围由前端缓冲水位请求控制。

### fMP4 分段与 WebSocket 二进制传输

后端发送给前端的媒体数据分为初始化段和媒体段。初始化段保存 `ftyp`、`moov` 等轨道与编码配置，供浏览器建立解码环境；媒体段组合 `moof` 和对应的 `mdat`，保存分片时间、样本信息和压缩媒体数据。FFmpeg 管道每次读到的字节块可能只包含半个 box，也可能包含多个 box，因此不能直接把每次读取结果当作一个完整媒体分段。

`stream_ffmpeg_output()` 每次从标准输出读取最多256 KiB，将数据累积到 `bytearray`，交给 `extract_mp4_boxes()` 按32位或64位长度字段提取完整顶层 box。读取到 `moov` 后组合并发送 `init` 段，读取到包含 `moof` 的 `mdat` 后组合并发送 `media` 段，忽略实时播放不需要的末尾随机访问索引 `mfra`。非法长度、超过128 MiB的单个 box，或结束时仍残留不完整 box、逻辑分段，都会作为流错误处理。

每个完整分段由 `pack_video_chunk()` 封装成一条 WebSocket 二进制消息，格式依次为4字节魔数 `HSV1`、4字节大端序 JSON 头长度、UTF-8 JSON 头、fMP4 分段字节。初始化段的头部参考示例：

```json
{
    "type": "VIDEO_STREAM_CHUNK",
    "streamId": "stream-example",
    "widgetId": "video-widget-example",
    "sequence": 0,
    "segmentType": "init"
}
```

其中消息类型（`type` 键）用于识别视频分段，播放器标识（`widgetId` 键）和流标识（`streamId` 键）用于确定接收者，分段序号（`sequence` 键）在同一流内从0递增，分段类型（`segmentType` 键）为 `init` 或 `media`。JSON 头后面才是实际媒体数据，不把二进制内容放进 JSON 或转换为 Base64。

`MainUI.html` 将 WebSocket 的 `binaryType` 设为 `arraybuffer`，在 `messageProc()` 中先区分二进制和文本消息。二进制分支兼容 `ArrayBuffer` 和 `Blob`，检查魔数和头长度，拆出 JSON 头与媒体字节后，依次调用 `binary_message_proc_func_list` 中注册的处理函数；文本消息继续按原有 JSON 命令分发。控制命令和媒体分段共用已有连接。

### 前端接收、预缓冲与懒加载

`CS_VideoPlayerWidget` 收到 `VIDEO_STREAM_READY` 后，由 `handleVideoStreamReady()` 保存本次流标识和时间信息，创建 `SourceBuffer`，设置 `mode='segments'`，并以实际开始时间设置 `timestampOffset`。这样从中途重封装、内部时间重新起算的分段会落在完整视频时间轴的对应位置。总时长大于0时，同时设置 `mediaSource.duration`，供 NPlayer 显示整部视频的进度条。

二进制处理函数只接受消息类型为 `VIDEO_STREAM_CHUNK`、播放器标识等于当前 `widgetId`、流标识等于 `activeStreamId` 且流尚未失败的分段。数据先放入 `streamQueue`，由 `appendNextStreamChunk()` 在 `SourceBuffer` 未更新时逐段调用 `appendBuffer()`；`updateend` 后继续处理下一段。旧流取消后迟到的数据因流标识不匹配而丢弃，不能写入新流的缓冲区。

首次播放和重新跳转时，`setInitialStreamPositionIfReady()` 检查从实际开始位置起已经连续缓冲多少秒。首次播放和普通重封装跳转的预缓冲目标为12秒；本次请求为 `SEEK_VIDEO_STREAM`，且 READY 的 `playbackMode` 为 `timestamp-repair` 时，预缓冲目标为1秒。剩余视频不足目标时以剩余时长为目标，流已经结束时也允许用现有缓冲完成初始化。数据不足期间暂停视频并保留用户播放意图，达到目标后设置 `video.currentTime`，再按原有播放意图恢复播放。后续补充缓冲仍使用10秒低水位和30秒高水位。

后续加载由 `requestMoreStreamData()` 根据当前播放位置前方的连续缓冲长度决定。默认低水位为10秒、高水位为30秒：缓冲不超过10秒时，前端发送 `BUFFER_VIDEO_STREAM`，携带当前 `streamId` 和希望放行到的位置（`bufferUntil` 键）；`waiting` 事件可强制触发补充请求。请求位置为当前播放时间加30秒，已知总时长时限制到视频末尾，并通过 `streamRequestedUntil` 避免重复请求同一范围。例如播放到第100秒、前方只剩8秒缓冲时，请求放行到第130秒。

后端 `extend_video_stream_buffer()` 核对播放器与流标识，仅在新的 `bufferUntil` 比现值大超过0.05秒时更新会话并唤醒 `flowEvent`。发送媒体段前，`read_mp4_track_timescales()` 从初始化段建立轨道时间单位映射，`read_mp4_fragment_start()` 从 `tfdt` 读取分片解码起点，再换算到完整视频时间轴。分片起点超过允许位置时，发送任务等待新请求；恢复后沿用同一个 FFmpeg 进程。限制的是分片起点，因此缓冲可能略超高水位，并不是精确截断在第30秒。

等待期间停止继续读取标准输出，管道填满后会对 FFmpeg 形成背压，避免持续把整部视频送入前端。前端 `trimOldStreamBuffer()` 还会在适合操作缓冲区时删除播放位置60秒以前的历史数据，且距离上次清理边界超过10秒才再次清理。已删除的历史位置再次跳转时需要重建视频流。

### 拖动进度条与流资源回收

检测到用户跳到未缓冲的位置后，前端把“等待跳转防抖结束”的标记 `streamSeekPending` 设为 `true`。在180毫秒防抖期间，`requestMoreStreamData()` 直接返回，不向即将取消的旧流发送 `BUFFER_VIDEO_STREAM`。

视频元素因暂时缺少可播放数据而不能继续播放时，会触发 `waiting` 事件。前端原本会调用 `requestMoreStreamData(true)` 尝试补充数据，其中 `true` 表示跳过“前方缓冲是否已高于低水位”的判断，但仍会检查流是否有效、请求范围是否重复等条件。`streamSeekPending` 为 `true` 时，这种补充请求也会暂停，避免用户已经选择新位置，前端却让旧进程继续读取和修复数据。

防抖期间若用户拖回已缓冲的位置，前端取消尚未执行的跳转定时器，并将 `streamSeekPending` 设回 `false`，恢复对当前流的正常缓冲请求。开始建立新流、播放失败、切换剧集和退出播放页时，也会取消该定时器并清除这个待跳转标记，避免旧跳转影响之后的播放。

`setupRemuxStream()` 在 `player.video` 上监听 `seeking`。目标时间已在缓冲区中时由浏览器直接跳转；目标不在缓冲区、流未失败且当前没有正在重建时，经过180毫秒防抖后调用 `openRemuxMediaSource(seekTime, 'SEEK_VIDEO_STREAM')`。前端清空旧分段队列并重建媒体源，后端取消旧任务和 FFmpeg 进程，重新生成流标识。

普通重封装不能任意从依赖其他画面的非关键帧开始，因此后端在非零开始位置调用 `cached_align_video_keyframe()`。索引可用时直接二分查找：对于 `.ts`、`.mts`、`.m2ts`，从关键帧 PTS 索引中取不早于请求时间的候选位置；对于 `.mp4`、`.m4v`、`.mov`、`.mkv`、`.webm`，从按 DTS 排序的关键帧记录中选择请求时间之前的候选记录，并读取其 PTS，没有更早记录时使用第一条。候选 PTS 比请求时间晚超过0.05秒且不超过30秒时才作为实际起点，否则沿用请求时间；这使已有输入索引的容器保留从前一个解码关键帧起步的处理行为，避免把 DTS 与 PTS 混用。

索引尚未完成、没有有效缓存或容器未启用索引时，调用 `align_seek_to_video_keyframe()` 使用 FFmpeg 的 `-ss`、`-debug_ts` 和只复制一帧的探测输出，读取实际首帧相对请求位置的延迟；延迟大于0.05秒且不超过30秒时，将请求位置加上延迟作为实际起点。没有探测到时间、延迟超出范围或探测异常时沿用原请求位置，并在异常时输出日志。实际起点还会限制到已知视频时长减0.1秒以内；正式输出将其作为输入侧 `-ss`，前端再结合 `timestampOffset` 和预缓冲完成播放位置设置。

FFmpeg 正常退出时后端发送 `VIDEO_STREAM_ENDED`，前端等队列写完且 `SourceBuffer` 不再更新后调用 `mediaSource.endOfStream()`。FFmpeg 非零退出时发送末尾错误信息；路径、探测、分段解析等异常也通过 `VIDEO_STREAM_ERROR` 返回。标准错误管道由独立任务持续读取并限制保留量，避免错误输出填满管道造成进程阻塞。前端流失败后清空待写队列、发送取消命令并释放媒体源，不再继续请求数据。

切换剧集和退出播放页时，`disposeRemuxStream()` 清除跳转定时器，移除 `seeking`、`play`、`timeupdate`、`waiting` 监听，发送 `CANCEL_VIDEO_STREAM`，中止正在更新的缓冲区并撤销 Object URL。后端 `cancel_video_stream()` 取消对应任务并等待回收完成。输出任务停止消费 stdout 后，`stop_ffmpeg_process()` 一边以每次64 KiB读取并丢弃剩余标准输出，一边终止进程、等待退出；超过2秒仍未完成时强制结束。这样缓冲达到高水位、输出管道积满时，也能继续排空管道，避免先等待退出再读取输出造成停顿。正式播放的标准错误仍由原收集任务读取；关键帧扫描停止后使用 `drain_stderr=True` 同时排空标准错误。最后回收读取任务并移除当前流会话，已经退出的进程也允许再次清理。WebSocket 断开时清理对应播放会话，模块关闭时还会取消媒体探测、关键帧扫描、辅助解码和流式修复任务(如果涉及)，并清空媒体探测、修复样本表和关键帧索引内存缓存。

### 媒体探测缓存与后台关键帧索引

媒体探测缓存 `media_probe_cache` 保存视频时长、编码、音频是否转码以及前端需要的 MIME 信息，用于减少同一文件反复播放、跳转时的 FFmpeg 探测开销。关键帧缓存 `video_keyframe_cache` 保存定位所需的两组时间数据：`decode` 是按 DTS 排序并去重的 `(DTS, PTS)` 记录，`presentation` 是按 PTS 排序并去重的显示时间。两类缓存均只存于当前模块实例的内存，不生成元数据文件，也不修改原视频。

缓存键由 `video_metadata_key()` 读取视频和 FFmpeg 文件信息得到，每份文件签名包含规范化大小写的绝对路径、文件大小、纳秒修改时间和纳秒 ctime。文件或工具签名变化后不会命中旧结果；写入同一路径的新结果时，`store_video_metadata()` 删除旧版本，缓存超过32项时淘汰最早使用的结果。读取媒体探测缓存或用于跳转的关键帧缓存时，将命中项移到末尾。缓存不能替代路径校验：每次开始和跳转仍通过 `resolve_video_path()` 解析路径、检查目录边界及文件存在性。路径已经经过 `realpath()` 解析后，边界检查使用 `is_resolved_path_within()` 比较规范化路径，不重复访问文件系统解析同一条路径；不同盘符或不同共享目录比较异常时视为不匹配。

关于媒体探测，`cached_probe_video()` 对同一签名共享 `media_probe_tasks` 中的任务。探测完成后再次核对文件签名，只有仍与原签名一致时才写入缓存，返回时复制结果字典，避免调用方修改缓存内容。等待使用 `asyncio.shield()`，因此单个请求取消不会连带取消其他请求共享的探测；模块关闭时统一取消这些任务。

关于普通重封装使用的关键帧索引，`start_video_stream()` 完成媒体检查、发送 `VIDEO_STREAM_READY` 并建立播放会话后，调用 `ensure_video_keyframe_index()` 安排后台任务，再启动正式输出。上述八种扩展名启用索引，同一签名只建立一次，最多保留32个排队或运行中的任务，并通过信号量限制为同时一个扫描进程。扫描与正式播放使用不同的 FFmpeg 进程，顺序补充播放缓冲仍沿用原播放进程；未完成索引不会阻止播放或跳转继续使用逐次探测。

`build_video_keyframe_index()` 用 FFmpeg 流复制扫描第一路视频压缩包并输出到空目标，不解码画面。它从 `-dump` 输出读取关键帧标记，从 `-debug_ts` 输出读取经过输入起点归一化的 DTS 和 PTS，逐行读取标准错误后形成两组索引。只有扫描正常结束、取得关键帧且文件签名未变化时才保存结果。扫描读取和等待退出最多允许300秒；失败后保留逐次定位方式，并在60秒内不重新安排扫描，之后的播放或跳转准备可再次尝试。索引状态记录在 `video_keyframe_status` 中，包含排队、建立中、失败及文件变化等状态，错误原因用于调试日志；后台索引不因单次跳转或播放连接断开而取消，模块关闭时统一回收。

### [DEBUG 功能]视频跳转耗时诊断

预缓冲期间另行输出 `[视频分段耗时]`，使用同一跳转请求标识、`streamId` 和 `sequence` 关联两端记录。前端记录分段接收、开始追加和追加完成，附带队列长度、排队耗时（`queueWaitMs`）、`appendBuffer()` 到 `updateend` 的耗时（`appendMs`）及连续缓冲秒数。后端记录前17个分段（序号0至16）的就绪、修复完成和发送完成，附带水位检查及等待耗时（`flowWaitMs`）、修复总耗时（`repairMs`）、其中取得显示顺序的累计耗时（`displayOrderWaitMs`）、视频样本数和发送耗时（`sendMs`）。显示顺序等待包含在修复总耗时内，不能重复相加。两端累计时间各自使用本地单调时钟，不能直接相减；这些分段日志也不会改变原跳转阶段日志的计时起点。

前端对未缓冲位置的跳转创建请求标识，通过 `SEEK_VIDEO_STREAM` 的 `debugSeekId` 传给后端，用同一标识关联两端日志。前端记录180毫秒防抖结束、MediaSource 打开并发送请求、收到 `VIDEO_STREAM_READY`、首个媒体段接收、预缓冲完成并设置播放位置，以及浏览器支持 `requestVideoFrameCallback()` 时的首帧提交显示。首个媒体段必须属于本次 READY 对应的流才计入，避免防抖期间旧流的数据污染统计；切换流、退出或失败时清理待执行的首帧回调。

后端记录请求接收、旧任务与进程回收、路径和 FFmpeg 配置检查、文件签名检查、媒体探测、关键帧定位、READY 发送、输出任务启动、进程创建、首次输出以及首个初始化段和媒体段发送。路径检查进一步拆为番剧根目录与视频完整路径规范化、两层目录边界校验、配置资源根目录规范化、视频存在性、FFmpeg 配置展开及存在性检查，便于定位网络路径的访问耗时。

日志以毫秒分别输出距上次记录的耗时与本端累计耗时。如果是修复问题MP4的情况，日志还会输出修复流关键帧日志记录辅助解码首帧确认的起点及耗时。媒体探测与关键帧定位的 `cacheHit` 表示是否使用已完成缓存；关键帧日志还返回 `indexState`、`indexError`，区分 `ready`、`building`、`queued`、`not-started`、`unsupported-container`、`queue-full`、`failed`、`file-changed`、`cancelled` 等情况。索引建立完成另行输出扫描耗时和关键帧数，其中耗时包含等待扫描信号量的时间。旧输出任务的取消日志包含此前播放或等待缓冲的间隔，真正的回收耗时应看新请求的“旧任务与 FFmpeg 进程回收完成”；回收日志另行拆分终止请求发出、主 FFmpeg 退出等待和输出管道排空、辅助帧读取任务退出和 stderr 排空、辅助进程退出及旧输出任务回收，辅助日志带有进程 ID 和队列帧数，便于定位满队列或管道等待；

耗时诊断代码分别放在 Python 的 `#[DEBUG-START]`、`#[DEBUG-END]` 和 JavaScript 的 `//[DEBUG-START]`、`//[DEBUG-END]` 标记之间，由构建脚本移除。移除诊断代码后，缓存、关键帧索引和进程回收功能仍保留。

### 界面动画

`CS_VideoPlayerWidget` 的构造函数增加 `haveComment` 参数，默认值为 `false`。该参数用于控制通用视频播放器页面是否创建评论入口按钮和评论面板；未启用时不生成相关 DOM，也不改变原有播放器布局。番剧页面使用的 `CS_AnimeVideoPlayerWidget` 在创建内部 `videoPlayerWidget` 时同时启用剧集栏和评论功能，因此目前番剧播放页默认可以使用评论展示入口按钮。

`CS_VideoPlayerWidget.render()` 保存 `cs_createBackButtons(container)` 返回的按钮栏，并在原播放器容器外增加 `playerLayout` 弹性布局容器。评论功能启用时，`createCommentPanel()` 会在返回按钮栏左侧创建一个悬浮的 40×40 像素球形按钮，按钮沿用返回栏按钮的蓝色背景、白色图标、阴影和悬停提示，内部 SVG 使用对话气泡图形，鼠标悬停时通过 `title` 显示“显示评论”。

点击评论球形按钮后，`setCommentExpanded(true)` 把同一个评论元素从返回按钮栏移动到 `playerLayout`，放在播放器右侧。播放器容器和评论容器分别占去除间距后宽度的 60% 与 40%，最终宽度比例约为 3:2；评论容器变为白色圆角矩形并隐藏原 SVG。原播放器顶部的 50 像素间距移到外层 `playerLayout`，避免评论面板展开后把播放器顶部空白计算进评论区域高度。

展开开始前会读取 `playerLayout` 的实际高度，并把该值锁定到外层弹性布局的 `height`、`min-height` 和 `max-height`。因此整个 420 毫秒动画期间，播放器与评论面板所在区域以及下方页面内容都不会上下跳动。评论面板使用 `height: 100%` 占满这块展开前的最大高度，不再随着展开后变窄、变矮的 16:9 播放器一起缩短；播放器容器展开后设置 `align-self: center`，在固定高度的布局画布内垂直居中。收起动画结束后才解除外层高度锁定，恢复原有自适应布局。

展开后的评论矩形右上角创建蓝底白字的“收起”按钮。点击后执行 `setCommentExpanded(false)`：播放器恢复原来的 80% 宽度、1000 像素最大宽度和居中位置；评论元素重新挂回返回按钮栏左侧，恢复为蓝色球形按钮并重新显示对话图标。评论元素跨容器移动时使用 FLIP 方式计算移动前后的矩形位置，并通过 Web Animations API 连接位置、尺寸、圆角和背景色变化；不支持该 API 的浏览器仍会直接完成最终布局切换。

下面是评论元素跨容器移动时的核心实现。先在改变 DOM 归属前记录初始矩形 `panelFirstRect`，把元素移动到目标容器并应用最终样式后再读取 `panelLastRect`；两组矩形的差值用于生成反向位移和缩放。动画第一个关键帧把已经处于最终布局的元素视觉还原到原位置，随后逐渐恢复为无变换状态，因而看起来像同一个元素连续地从球形按钮移动并展开成评论面板：

```javascript
const panelFirstRect = panel.getBoundingClientRect();

this.playerLayout.appendChild(panel);
Object.assign(panel.style, {
    position: 'relative',
    width: 'calc(40% - 6.4px)',
    height: '100%',
    borderRadius: '12px',
    background: '#fff'
});

const panelLastRect = panel.getBoundingClientRect();
const deltaX = panelFirstRect.left - panelLastRect.left;
const deltaY = panelFirstRect.top - panelLastRect.top;
const scaleX = panelFirstRect.width / panelLastRect.width;
const scaleY = panelFirstRect.height / panelLastRect.height;

panel.animate([
    {
        transformOrigin: 'top left',
        transform: `translate(${deltaX}px, ${deltaY}px) scale(${scaleX}, ${scaleY})`
    },
    {
        transformOrigin: 'top left',
        transform: 'translate(0, 0) scale(1, 1)'
    }
], {
    duration: 420,
    easing: 'cubic-bezier(0.22, 1, 0.36, 1)'
});
```

播放器也使用独立的 FLIP 动画，避免先修改最终布局造成点击瞬间直接跳到屏幕左侧。展开时，最终位置和尺寸会在同一帧通过反向 `translate + scale` 映射回展开前的视觉状态，所以点击瞬间页面几乎不发生变化。播放器动画被拆为两个连续阶段：前 55% 时间保持展开前的尺寸，只逐渐向左移动；播放器到达最终左边界后，后 45% 时间再以左边中点为缩放锚点逐渐缩小到最终尺寸。这样播放器缩小时其垂直中心保持不变，并始终位于固定高度的 `playerLayout` 中央。收起时按相反次序，先在左侧居中放大，再平滑回到原来的水平居中位置。

初版 FLIP 动画曾把切换瞬间读取的 `lastRect.height` 直接写进 Web Animations 高度关键帧。由于播放器宽度本身也在进行 420 毫秒过渡，读取最终矩形时播放器仍接近展开前的大尺寸，这个过期高度会覆盖真实布局，造成动画期间评论面板高度异常，动画结束后又瞬间跳回。现在评论面板和播放器关键帧都不直接动画 `width`、`height`，只使用 `translate + scale` 表达视觉形变；实际布局尺寸由固定高度的 `playerLayout`、占满高度的评论面板和可独立缩放的播放器共同控制。

构造函数同时保存 `playerLayout`、`commentPanel`、`commentExpanded` 和当前动画等状态。播放页面清理函数会调用 `disposeCommentPanel()`，取消尚未结束的动画、移除评论元素并清空相关引用，避免退出页面或切换页面后残留 DOM 和动画回调。

### 展开评论面板时

在展开评论面板时，前端向后端发送 `CS_GET_COMMENT_INFO` 请求评论信息数据，参数有对应视频的元数据文件夹路径(xxx.mp4\@meta/)。后端响应评论信息数据`CS_COMMENT_INFO`，包括总共的评论数量，评论来源列表(每个来源的BV号、数据库文件路径和来源名称、评论数量、回复数量、最后更新时间、资源根目录)，评论模块的配置信息（每页评论数量，排序方式，是否标识被删掉的数据，......），评论模块阅读记录信息(上次阅读评论到什么地方)。具体过程是后端尝试读取 `xxx.mp4@meta/cmif.json` 文件，如果不存在返回总共评论数量为0即可，文件存在则读取解析。这个文件内容格式如下：

```json
[
    {
        "comment-srcfile":"cm1.db",
        "resource-folder":"",
        "basic-resfolder":"bilibili-resource",
        "src":"B站"
    },
    {
        "comment-srcfile":"cm2.db",
        "resource-folder":"",
        "basic-resfolder":"bilibili-resource",
        "src":"B站"
    },
    ......
]
```

对于每个评论来源，尝试在 `xxx.mp4@meta/` 文件夹所在目录下找到 `__COMMENT__` 文件夹。首先尝试读取 `__COMMENT__/cm-list.json` 文件，该文件内容格式如下：

```json
{
    "BVXXXXXX":{
        "file-name":"cm1.db",
        "aid":1234567891011,
        "update-time":1234567890,
        "comment-count":1000,
        "reply-count":200,
        "src-name":"动漫铥铥"
    },
    "BVXXXXXX":{
        "file-name":"cm2.db",
        "aid":1234567891012,
        "update-time":1234567990,
        "comment-count":500,
        "reply-count":100,
        "src-name":"MCE汉化组"
    },
    ......
}
```

根据 `comment-srcfile` 字段的值尝试在 `__COMMENT__/cm-list.json` 读取的内容里获取这个来源的评论数量和回复数量、最后更新时间和bv号，并核实 `__COMMENT__/` 下对应的数据库文件是否存在(不存在则跳过)，存在则以这个数据库文件的地址作为数据库路径。如果不存在这些键或不存在该文件，那么就在该文件夹下根据 `comment-srcfile` 字段的值找到对应的评论数据库文件，若不存在则跳过，如果存在则读取解析 `_metadata` 表获取这个来源的最后更新时间和bv号，读取 `main` 表和 `top` 表、`reply` 表的长度获取这个来源的评论数量和回复数量，并以这个数据库文件的地址作为数据库路径，将这些值填充到响应json里并写回 `__COMMENT__/cm-list.json` 文件；将  `__COMMENT__/cm-list.json` 中对应来源 `src-name` 字段的值作为来源名称填充到响应json里，如果 `__COMMENT__/cm-list.json` 里该来源缺少 `src-name` 字段那么其默认用bvid作为来源名，并尝试补上文件里的 `src-name` 字段；最后计算出总共的评论数量填充到响应json里；然后读取 `backend\config\classify_shower_config.json` 里 `video-config.comment-config` 字典(如果没有就加上，使用默认值)，来填充评论模块的配置信息；尝试读取 `xxx.mp4@meta/__COMMENT-RECORD__.json` 文件，该文件内容结构如下：

```json
{
    "view-time":1234567990,    // 上次查看评论的时间戳
    "last-read-src-BV":"BVXXXXXX",    // 上次阅读评论的来源BV号
    "last-read-page":1,    // 上次阅读评论读到了第几页
    "last-pagecount":10    // 上次阅读评论设置的每页评论数量
}
```

以 `xxx.mp4@meta/__COMMENT-RECORD__.json` 文件的 json 内容，填充评论模块的阅读记录信息。若文件不存在，以空值填充。

前端收到 `CS_COMMENT_INFO` 响应后，根据对应信息更新评论面板的界面显示(一共多少页可以通过本来源评论数量和每页评论数算出来)。随即根据当前的信息发送 `CS_GET_COMMENT_HTML` 请求该页的具体评论内容。这个命令的参数有要读取的数据库文件地址、增量数据库目录（直接把 `__COMMENT__/update/`的绝对目录传进去）、资源根目录、读取历史存储目录(一般是`xxx.mp4@meta/`)、排序方式、是否有关键词筛选条件及关键词值、当前页码、每页评论数量、是否标识被删掉的评论、是否只显示被删掉的评论、是否只显示大会员评论、是否按字数筛选及字数值。后端收到 `CS_GET_COMMENT_HTML` 请求响应 `CS_COMMENT_HTML` 命令。收到请求时，如果标识被删掉的评论或只显示被删掉的评论，假设数据库文件地址为`....../__COMMENT__/cm<number>.db`，后端应该以JSON格式从增量数据库目录里加载 `cm<number>.deletelist` 为已删评论列表，如果这个文件不存在则读取该来源所有增量数据库中被删掉的评论数据的rpid合并为这个列表，然后在增量数据库目录里创建文件 `cm<number>.deletelist` 并以JSON格式写入这个列表。如果“增量数据库目录”这个参数为空，则忽略“是否标识被删掉的评论、是否只显示被删掉的评论”这两个参数。将 `关联项目\bilibiliAPI\bilibili_comment_viewer\comment_viewer(DB).py` 里边的 `load_comments_from_database` 函数复制过来并改动一下使之支持 `CS_GET_COMMENT_HTML` 请求的这些参数，使用该函数从给定数据库里加载出该页所有评论的json，然后把 `comment_viewer(DB).py` 里边的 `comment_to_comment_html` 函数复制过来，然后改造一下使之能够重映射其中涉及到的各种资源到正确的目录，然后如果标识被删掉的评论，将出现在“已删评论列表”里的那些评论的背景颜色改成淡粉色。将json转化为html字符串作为`CS_COMMENT_HTML` 命令的响应数据发送给前端。与此同时将收到的有关的配置(比如是否有关键词筛选条件及关键词值、当前页码这样的就不算)存入 `backend\config\classify_shower_config.json` 里 `video-config.comment-config` 字典。

关于资源目录的确定，要根据这个来源对应 `xxx.mp4@meta/cmif.json` 的 `resource-folder` 字段的值来确定。如果为空，则默认使用 `__COMMENT__/` 文件夹的目录作为资源根目录。例如将 `./comment-resource/avatar/2119be22cebf9aae3bf3538db6dbb407618e4c2a.webp` 映射到 `....../__COMMENT__/comment-resource/avatar/2119be22cebf9aae3bf3538db6dbb407618e4c2a.webp` 目录下。

前端评论面板里的 `评论内容div` 在初始化时即放入初始html，初始html参考 `comment_viewer(DB).py` 里边的模板html，不同的是没有`.container`DIV也没有 `.header` DIV。`.comment-list` DIV 直接放到 `<body>` 里面。收到响应后将响应数据插入到`.comment-list` DIV 里边，实现评论展示。

### 切换设置和分页

如果 `来源div` 里的选择框里评论来源、选项按钮弹出悬浮窗口里的排序方式、关键词筛选的关键词值、设置菜单里勾选框 `标识被删掉的数据`、勾选框 `只显示被删数据`、勾选框 `只显示大会员评论`、勾选框 `字数筛选`、（若勾选字数筛选）可输入的下拉选择框 `只显示 xx 字 以上/以下 的评论`、每页的评论数量、当前页码这些发生了变化，重新发送 `CS_GET_COMMENT_HTML` 请求来改换评论面板 `评论内容div` 的html内容。如果当前页码为9，现在我更改每页的评论数量后所有评论只有6页了，那么当前页码就设置成6，即是设置为有效页码里距离之前页码最近的那个页码。这时后端还要额外发送一条 `CS_COMMENT_SETPAGE` 响应以设置前端当前页码，前端收到此信息更新页面控制组件外观以及当前页码标识的页码按钮，同时 `CS_COMMENT_HTML` 响应数据给的是当前设置的那个页码(第6页)的评论HTML。另外，切换页码时，要更新评论阅读记录 `xxx.mp4@meta/__COMMENT-RECORD__.json`。
