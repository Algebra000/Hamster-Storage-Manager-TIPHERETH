# 评论下载工具使用说明

本工具用于下载 B 站视频评论及配套图片资源，也可以按本地视频的弹幕来源批量更新弹幕和评论。目录中的四个脚本分别用于：

| 脚本 | 用途 | 主要输出 |
| --- | --- | --- |
| **bili-comment-downloader.py** | 单个视频的评论下载，保存为 JSON | `comment.json`、`resources-URL.json`、`comment-resource/` |
| **bili-comment-downloader(DB).py** | 单个视频的评论下载，按页写入 SQLite 数据库 | `comment.db`、`resources-URL.json`、`comment-resource/` |
| **srcURL-build.py** | 交互式建立弹幕来源及时间轴重映射配置，供批量下载器使用 | `dm-srcURL.json` |
| **srcURL-downloader-CM.py** | 按任务清单下载弹幕，并根据来源下载、合并评论和保存更新历史 | 各视频的弹幕文件、评论配置及共享的 `__COMMENT__/` 目录 |

只下载一个视频的评论时，选择前两个脚本之一；为仓鼠存储管理器中的多个本地视频批量更新时，使用后两个脚本配合完成。

## 一、运行环境

需要 Python 3 环境。脚本及目录中自带的精简版 **bilibili_api** 使用以下第三方包：

```text
httpx
aiohttp
colorama
pycryptodomex
```

如本机尚未安装，可执行：

```sh
python -m pip install httpx aiohttp colorama pycryptodomex
```

SQLite 使用 Python 自带的 `sqlite3`，无需另外安装数据库服务。

运行前先把当前工作目录切换到本工具目录。在 PowerShell 中执行：

```powershell
Set-Location "D:\你的项目路径\仓鼠存储管理器_brch3\工具链\评论下载工具"
```

在 Windows 命令提示符（CMD）中执行：

```bat
cd /d "D:\你的项目路径\仓鼠存储管理器_brch3\工具链\评论下载工具"
```

请替换为本机实际路径。保留目录中自带的 **bilibili_api/**；批量下载还需保留 **bilibili-resource.zip**，用于补齐基础评论资源。

## 二、准备 B 站登录凭证

在工具目录准备 **cookie.json**，内容如下：

```json
{
    "SESSDATA": "这里填写 SESSDATA",
    "bili_jct": "这里填写 bili_jct",
    "buvid3": "这里填写 buvid3"
}
```

这些值来自已登录 B 站账号的浏览器 Cookie。打开浏览器开发者工具，在“应用”中的 Cookie 列表里复制对应字段。图示可参考 [弹幕资源批量更新工具使用说明](../弹幕资源批量更新工具/使用说明.md)。Cookie 属于账号凭证，请勿发送给他人或提交到 Git 仓库。

四个脚本均读取当前工作目录的 **cookie.json**。凭证失效或访问权限不足时，可能下载失败，也可能只取得部分评论。

需要输入网址的三个交互脚本支持以下形式：

```text
https://www.bilibili.com/video/BVxxxxxxxxxx
https://www.bilibili.com/video/BVxxxxxxxxxx?p=2
https://www.bilibili.com/bangumi/play/ep123456
```

请使用完整视频网址；裸 BV 号、短链接和 `ss` 页面不属于这些脚本的解析格式。评论按 BV 对应的稿件获取，同一 BV 的不同分 P 共用评论来源；弹幕则区分分 P。

## 三、使用 bili-comment-downloader.py 下载 JSON 评论

### 1. 运行脚本

在工具目录执行：

```sh
python bili-comment-downloader.py
```

出现“请输入视频评论所在视频的B站BV号URL,空输入退出”后，粘贴目标视频的完整网址并按 Enter。直接按 Enter 则退出。一次运行处理一个视频。

### 2. 等待评论和资源下载

脚本先分页获取主评论和置顶评论，再处理子评论、收集图片地址，将评论中的资源地址改为本地相对路径，最后下载头像、表情、评论图片等资源。

当前 JSON 版本会先在内存中累计评论。它只在主评论已有子评论列表且数量不足时继续补抓子评论；若接口没有提供初始子评论列表，则不会进一步补抓。取得的数据范围以实际接口响应和下载日志为准。

### 3. 查看输出

文件保存在当前工具目录：

```text
评论下载工具/
├── comment.json
├── resources-URL.json
└── comment-resource/
    ├── avatar/
    ├── emoji/
    ├── picture/
    └── ...
```

- **comment.json**：评论列表，子评论位于各条评论的 `replies` 中，置顶评论带有 `is_top` 标记。
- **resources-URL.json**：按类别保存的资源下载地址。
- **comment-resource/**：下载到本地的头像、表情、图片等资源，按类别分目录存放。

再次运行会覆盖 **comment.json** 和 **resources-URL.json**；资源下载会跳过已存在的同名文件。需要保存多个视频时，每次完成后先把评论文件、资源清单和资源目录一起归档，保留它们的相对位置。

## 四、使用 bili-comment-downloader(DB).py 下载数据库评论

### 1. 运行脚本

在工具目录执行，文件名中的括号需要用引号保护：

```sh
python "bili-comment-downloader(DB).py"
```

按提示输入完整视频网址，空输入退出。一次运行处理一个视频。

### 2. 下载方式

该版本每处理完一页评论便写入并提交数据库，无需把全部评论正文一直保存在内存中。它会补抓数量不足的子评论，并对接口重复返回的置顶评论去重。子评论获取失败时，会提示并保存当前已经取得的内容。

### 3. 查看输出

```text
评论下载工具/
├── comment.db
├── resources-URL.json
└── comment-resource/
```

**comment.db** 是 SQLite 评论数据库，包含主评论、置顶评论、回复及对应的用户和内容数据。资源清单和资源目录的用途与 JSON 版本相同。

数据库生成完成后会替换当前目录中的同名 **comment.db**；这不是历史增量更新。下载另一个视频前，如需保留现有结果，应把数据库、资源清单和资源目录一起归档。需要自动维护多个来源及历史版本时，使用第六节的批量下载器。

这两个单视频下载脚本不会自动生成 **cmif.json**，也不会自动建立批量下载器使用的 **__COMMENT__/** 目录结构。

## 五、使用 srcURL-build.py 建立批量下载来源

### 1. 确定本地视频的元数据目录

对于 `classify_shower` 模块，本地视频 **第一集.mp4** 对应同级的 **第一集.files/**：

```text
某个番剧目录/
├── 第一集.mp4
└── 第一集.files/
```

来源构建脚本生成的是 **dm-srcURL.json**，最终应放入对应的 **第一集.files/**。批量下载器会从弹幕来源中提取 BV，再建立评论来源。

### 2. 运行并录入来源

```sh
python srcURL-build.py
```

1. 输入视频的 B 站完整网址。
2. 在“是否需要重映射时间轴”处，直接按 Enter 跳过；输入任意内容则进入配置。
3. 继续输入其他来源，或在网址提示处直接按 Enter 结束录入。
4. 在“是否确认保存”处，直接按 Enter 保存；输入任意内容则退出而不保存。

脚本在当前工具目录读写 **dm-srcURL.json**。如果已有有效来源列表，会在其基础上追加；自动分配 **dm1**、**dm2** 等不重复名称，并按 BV 与分 P 的组合去重。若已有文件不是有效 JSON，会询问是否新建列表，空输入同意新建，有输入则退出。

### 3. 配置时间轴重映射

需要对齐本地视频与 B 站弹幕时间轴时，按提示依次填写：

- **保留时间范围**：如 `0h30m0s-1h0m0s`，直接按 Enter 保留全部。当前交互一次填写一个范围。
- **片头扣除时间**：填写秒数，直接按 Enter 使用 `0`。
- **本地视频中被网站源删减的片段**：如 `0h30m0s-0h31m0s 0h40m0s-0h41m0s`，多个范围用空格隔开，直接按 Enter 跳过。

这些配置作用于弹幕时间轴。生成文件示例：

```json
[
    {
        "src": "B站",
        "BV": "BVxxxxxxxxxx",
        "p": 1,
        "name": "dm1",
        "rmcf": {
            "dmsrc-file": "dm1.json",
            "time_filter": [],
            "cut_time": 0,
            "add_time": [],
            "add_time_text": "(此处为B站删减片段)"
        }
    }
]
```

保存后，将 **dm-srcURL.json** 移到目标视频的 **xxx.files/**。为下一个本地视频建立来源前，确认工具目录中没有遗留上一个视频的来源列表，否则脚本会继续追加到旧列表。

## 六、使用 srcURL-downloader-CM.py 批量更新弹幕和评论

### 1. 准备任务清单

在工具目录准备 **basepath.json**。顶层是列表，每项是一个已有 **dm-srcURL.json** 的视频元数据目录：

```json
[
    "D:/视频/番剧/第一集.files",
    "D:/视频/番剧/第二集.files"
]
```

也可以使用反斜杠，但在 JSON 字符串中必须双写：

```json
[
    "D:\\视频\\番剧\\第一集.files",
    "\\\\NAS-SERVER\\video\\番剧\\第二集.files"
]
```

这里填写 **xxx.files** 目录，不是视频文件路径，也不是番剧父目录。

### 2. 运行下载器并选择处理方式

确认工具目录中存在 **cookie.json**、**basepath.json**、**bilibili_api/** 和 **bilibili-resource.zip**，然后执行：

```sh
python srcURL-downloader-CM.py
```

启动后会依次询问：

| 提示 | 直接按 Enter | 输入任意内容 |
| --- | --- | --- |
| 是否自动构建弹幕目录并下载对应评论 | 自动构建弹幕、更新重映射配置并下载评论 | 每个目录下载弹幕后，再分别询问是否构建弹幕、是否下载评论 |
| 是否默认覆盖已经损坏的文件 | 对统一 JSON 读取逻辑检测到的损坏文件，用默认空列表或空字典覆盖 | 保留损坏文件，并报告错误 |

第一项选择手动后，在后续的弹幕构建、评论下载提示中，仍然是空输入执行、有输入跳过。弹幕下载阶段会先执行，即使随后跳过弹幕构建或评论下载也一样。

损坏文件选项不覆盖全部读取流程：**cookie.json**、**basepath.json** 和最初读取的 **dm-srcURL.json** 仍需事先保证格式有效；损坏的 **rmcf.json** 在构建阶段会另行询问是否覆盖。

### 3. 弹幕处理结果

每个 **xxx.files/** 中生成或更新：

- **raw/dm1.json**、**raw/dm1-2.json** 等：各次下载的原始弹幕快照。
- **dm1.json** 等：合并历史快照及已有最终文件后的弹幕数据。
- **rmcf.json**：播放器使用的时间轴重映射配置。

弹幕来源未变化时按 `dmid` 去重；检测到同名来源的 `oid` 发生变化时，会显示警告并按“视频时间 + 弹幕文本 + 发送时间”去重。

### 4. 评论来源和共享目录

程序从 **dm-srcURL.json** 中提取 BV，合并到该视频的 **cm-srcURL.json**，按 BV 去重，并保留原评论来源中手工补充的其他 BV。来源名称会重新编号为 **来源1**、**来源2** 等。

评论数据集中存放在 **xxx.files** 的父目录下的 **__COMMENT__/**，同一父目录中的多个视频共用这一目录。示例结构如下：

```text
某个番剧目录/
├── 第一集.mp4
├── 第一集.files/
│   ├── dm-srcURL.json
│   ├── cm-srcURL.json
│   ├── cmif.json
│   ├── dm1.json
│   ├── rmcf.json
│   └── raw/
│       ├── dm1.json
│       └── dm1-2.json
├── 第二集.mp4
├── 第二集.files/
└── __COMMENT__/
    ├── cm-list.json
    ├── cm1.db
    ├── resources-URL.json
    ├── comment-resource/
    ├── bilibili-resource/
    ├── raw/
    └── update/
        ├── cm1.db
        ├── cm1-2.db
        └── cm1.deletelist
```

首次下载时尚无 **cm1-2.db**，后续更新才会生成增量文件。多个 BV 来源分别分配 **cm1.db**、**cm2.db** 等名称。

| 文件或目录 | 用途 |
| --- | --- |
| **xxx.files/cm-srcURL.json** | 此视频对应的评论来源列表 |
| **xxx.files/cmif.json** | 此视频引用哪些评论数据库及资源目录 |
| **__COMMENT__/cm-list.json** | BV 与数据库文件的映射、来源名称、更新时间及评论数量 |
| **__COMMENT__/cm1.db** | 合并历史结果后供读取的评论数据库 |
| **__COMMENT__/update/cm1.db** | 该来源首次下载的历史基库 |
| **__COMMENT__/update/cm1-2.db** 等 | 后续更新的增量数据库，编号递增 |
| **__COMMENT__/update/cm1.deletelist** | 根据历次增量记录维护的缺失评论 ID 清单 |
| **__COMMENT__/raw/** | 本轮更新的临时评论数据库，处理后会清理 |
| **__COMMENT__/resources-URL.json** | 合并保存的评论资源地址清单 |
| **__COMMENT__/comment-resource/** | 下载的头像、表情和评论图片等 |
| **__COMMENT__/bilibili-resource/** | 从工具目录的压缩包中补齐的基础评论资源 |

同一次运行中，同一 **__COMMENT__/** 目录下的相同 BV 在成功下载后不会重复抓取，其他剧集仍会登记相应的 **cmif.json** 引用。

### 5. 再次更新

保留任务清单和已有输出，再次运行同一命令即可。对于已有评论来源，程序先由历史基库及增量重建合并库，再重新抓取当前评论，记录新增、变化及缺失信息，更新合并库和缺失清单。

后续下载仍会分页抓取当前评论；“增量”指保存更新结果的方式。历史中已有但本次未取得的评论会保留在合并库中，缺失情况另行记录。因此缺失记录不能直接等同于确认被删除，也可能受本次获取范围影响。

**__COMMENT__/raw/** 是评论临时目录，与 **xxx.files/raw/** 中保留的弹幕历史快照用途不同。需要保留评论更新历史时，应一并保存 **__COMMENT__/update/** 和 **cm-list.json**。

## 七、常见问题

### 找不到 cookie.json 或 basepath.json

先进入本工具目录再运行，检查文件名是否误带 `.txt` 后缀。两个单视频评论下载器和来源构建器不需要 **basepath.json**，只有批量下载器读取它。

### 网址解析失败

使用完整的 BV 视频网址或 `ep` 番剧播放网址，必要时去掉无关参数。番剧网址解析还需要联网取得对应 BV，检查登录凭证及访问权限。

### 提示路径不存在或 dm-srcURL.json 不存在

检查 **basepath.json** 中的每一项是否指向实际存在的 **xxx.files/**，并确认来源文件已经放入其中。只有 **cm-srcURL.json** 不能代替批量下载入口所需的 **dm-srcURL.json**。

### 评论、子评论或图片没有全部下载

检查是否出现凭证、网络、限流或子评论获取失败提示。脚本取得的是接口本次返回的数据；数据库版本在子评论补抓失败时仍可能保存已取得的部分内容。单视频下载器重新运行会覆盖同名结果，需保留旧结果时先归档；批量更新器会维护历史库。

### 缺少 bilibili-resource.zip

把工具自带的压缩包放回 **srcURL-downloader-CM.py** 所在目录，再运行批量下载器以补齐基础评论资源。

## 八、批量使用流程

1. 在工具目录准备有效的 **cookie.json**。
2. 运行 **srcURL-build.py**，录入一个本地视频的来源并确认保存。
3. 把生成的 **dm-srcURL.json** 移到该视频的 **xxx.files/**。
4. 对其他视频重复第 2～3 步。
5. 将需要更新的元数据目录写入 **basepath.json**。
6. 运行 **srcURL-downloader-CM.py**，按需要选择自动处理和损坏文件处理方式。
7. 检查各目录的下载日志、**cmif.json** 及共享的 **__COMMENT__/** 输出，留意失败或数据不完整提示。
